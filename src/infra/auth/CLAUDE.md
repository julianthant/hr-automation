# Auth Module

Seven independent login flows for UCSD systems. Each system uses different SSO/auth — never share browser sessions between them.

Kernel workflows invoke these via `SystemConfig.login` in `defineWorkflow({ systems: [...] })`:

```ts
systems: [{
  id: "ucpath",
  login: async (page) => {
    const ok = await loginToUCPath(page);
    if (!ok) throw new Error("UCPath authentication failed");
  },
}],
```

`Session.launch` in `src/core/kernel/session.ts` calls each `login` with 3-attempt retry. There is one global auth strategy — no per-workflow `authChain` knob:

- **1 system** → fast path: `bringToFront` → `login` → done. No settle, no stagger.
- **≥2 systems** → **parallel-staggered with concurrency cap**:
  1. Every system's SSO form is navigated + filled in parallel via the optional `prepareLogin` hook (see `kualiNavigateAndFill`, `ucpathNavigateAndFill` etc.).
  2. After all forms are filled, a `settleMs` pause (default **2000 ms**) before the first Submit click — gives the operator a moment to look at the phone.
  3. Submit clicks fire with a `staggerMs` gap (default **5000 ms**) between each, so Duo push notifications arrive evenly spaced (avoids the cached multi-prompt collision documented below).
  4. At most `maxConcurrentDuos` (default **1**) Duo pends at any moment. With ≥2 systems, additional ones wait until a slot frees on approval — the operator never sees more than 1 queued prompt on their phone.

Tuning knobs live on `LaunchOpts` (`staggerMs`, `settleMs`, `maxConcurrentDuos`) and are primarily for tests. Production callers don't pass them.

The ≥2-system parallel-staggered path is exercised live (real concurrent Duos, not stubbed) by `tests/live/session-launch-multi.test.ts` (opt-in `npm run test:live`; kuali + old-kronos at the production default knobs). `tests/integration/core/mock-workflow.test.ts` still asserts the staggered ORDERING with stubbed logins for the CI pool.

## Login Flows

Eight UCSD Shibboleth SSO flows, all gated by Duo MFA and all sharing one auth
path: `fillSsoCredentials` → `clickSsoSubmit` → `pollDuoApproval` /
`requestDuoApproval`. They land on the same `a5.ucsd.edu` Duo prompt, so the
hands-off WebAuthn path (below) covers every one of them identically.

**`loginToI9` lives in `src/systems/i9/login.ts`, not this module** — it adds the

**Smoke test:** `npm run test-login` (default UCPath + CRM). Add `--all` to sweep
every Duo flow, or `--systems ucpath,kuali,ukg,…` for a subset; each runs in a
fresh browser with a per-system pass/fail table. Prefix with

## Hands-off Duo via WebAuthn (opt-in)

> **Full reference:** [`docs/engineering/hands-off-duo-webauthn.md`](../../../docs/engineering/hands-off-duo-webauthn.md)
> — enrollment, the two-phase factor model, the six Duo flows, testing, and a
> failure-modes table. Read it before debugging a hands-off Duo issue.

`HR_AUTOMATION_DUO_WEBAUTHN=1` makes every login approve Duo automatically with
no phone push, using credentials enrolled once as independent Duo security keys.
**Chromium-only**, entirely opt-in, and always falls back to manual Duo on any
failure.

Critical invariants (full detail + failure-modes table in the reference doc):

- **Three steps, armed early.** `armDuoWebAuthn` (one CDP authenticator per
  transport + CTAP2 shim for CRM) / `beginDuoWebAuthn` (factor select) /
  `finishDuoWebAuthn` (persist signCount + tear down). Armed at **`clickSsoSubmit`**
  (before the prompt — CRM auto-fires on load), reused in `pollDuoApproval`,
  finished on **every** exit path.
- **Two factors — UCPath rejects the security key.** Touch ID (`internal`) for most
  apps; ACT CRM offers **only** a security key (`usb`). Preference is Touch ID
  first, security key fallback (security-key-first makes UCPath `/error`).
- **⚠️ `selectDuoFactor` is two-phase — never click during the auto-fire.** Duo
  auto-fires the ceremony on load; the authenticator answers it with no click
  (**Phase 1** grace — wait for `hasSigned` / the trust screen, *don't touch the
  prompt*). Clicking "Other options" mid-ceremony **aborts it → UCPath `/error`**.
  **Phase 2** (Escape + "Other options" → factor) is for CRM. Gate "auto" on
  `hasSigned`, **not** the URL (pre-prompt the page is still on `a5.ucsd.edu`).
  Never reload the prompt (desyncs Duo's challenge).
- **signCount is load-bearing.** Persisted monotonically on every exit. If the
  local counter falls **at/below** Duo's server-side counter, Duo rejects the next
  assertion as a clone ("signs but never completes", prompt hangs on "Use Touch
  ID"). A `kill -9` mid-ceremony is the classic trigger, but a manual bump landing
  slightly low (or any drift the `+10` reserve can't cover) does it too — **this
  DOES happen in normal production**, not only under aggressive testing (observed
  2026-06-05 on a real OCR-verify run; recovered on the auto-retry). The poll loop
  now **self-heals**: on a signed-but-incomplete assertion it calls
  `resyncDuoWebAuthnSignCounts()` (`+100`, larger than the per-arm `+10` reserve so
  one retry clears a multi-step drift) and takes a **shortened ~30s manual window**
  (`DUO_WEBAUTHN_FALLBACK_MANUAL_SECONDS`) instead of the full 180s — no push was
  sent, so the long wait only stalls before the kernel re-arms from the bumped
  counter. Manual resync (bump every counter in `.auth/duo-webauthn.json`, e.g. to
  1000) is still the fix if the auto-resync somehow can't keep up.
- **Enroll:** `npm run duo:webauthn:enroll` (`--security-key` for a usb device).
  **Secret:** `.auth/duo-webauthn.json` (EC P-256 private keys) is gitignored —
  never commit or log it.

## Selector Pattern

All UCSD SSO forms use 3-level fallback selectors:
1. Accessibility label (e.g., `"User name (or email address)"`)
2. Alternate label (e.g., `"Username"`)
3. HTML attribute (e.g., `input[name="j_username"]`)

Submit button: always `button[name="_eventId_proceed"]` (avoids collision with "Enroll in Two-Step Login" nav link).

## Gotchas

- **Duo MFA is manual** — automation pauses and polls for user phone approval
- **Duo serialization** — historically all sessions submitted Duo prompts strictly sequentially because simultaneous prompts collided. The kernel now uses one global parallel-staggered chain for any ≥2-system workflow (5s submit gap, 2s pre-submit settle, 1-Duo concurrency cap). The legacy `authChain` field was removed on 2026-05-27 — there is no opt-out per workflow; tuning lives on `LaunchOpts` for tests.
- UCPath may redirect back to campus discovery page after Duo — retry loop (3x) handles this
- UKG `ukgNavigateAndFill` returns `true | false | "already_logged_in"` (string return for persistent session detection)
- UKG is the only flow with network error retry logic (5s backoff for transient errors)
- ACTCrm may land on `act-crm.my.site.com` OR `crm.ucsd.edu` after Duo — both are checked
- Debug screenshots saved to `.auth/debug-*.png` (ACTCrm flow only)
- "Enroll in Two-Step Login" nav link has `role="button"` containing "Login" — causes selector collisions if not using `button[name=...]`

- **2026-07-01: ISS-005 ROOT-CAUSED + FIXED — the first-attempt "factor not found" flake was `selectDuoFactor`'s factor-detection deadline elapsing PRE-PROMPT (slow SSO→Duo transition), mis-read as "no factor" → dead ~180s manual stall.** The 2026-06-25 diagnostic caught the next occurrence live (a CRM daemon auth): `factor-detection diagnostic — deadline elapsed … onMethodList=false useTouchId=false useSecurityKey=false trustScreen=false otherOptions=false | url=…/tritON/…/SSO?execution=e1s3 | links=[… Get Help | Register | Reset password …]` — at give-up the page was STILL on the UCSD SSO page (all Duo screens absent, only SSO login-page chrome present) because the Duo prompt hadn't rendered within the 20s factor window (the first SSO→Duo transition is the slowest — cold caches). **Fix (`duo-webauthn.ts`, commit `d250edb9`):** at the factor deadline, distinguish "prompt not rendered yet" (KEEP WAITING to `promptRenderCap` = `max(factorWindow, 20_000) + DUO_FACTOR_PROMPT_RENDER_GRACE_MS` [env `HR_DUO_PROMPT_RENDER_GRACE_MS`, default 25s]) from "prompt up but no matching factor" (the real give-up), gated by an inline `duoPromptRendered()` check. The factor window is now `DUO_FACTOR_TIMEOUT_MS` (env `HR_DUO_FACTOR_TIMEOUT_MS`, default 20s — env-tunable so the guard can be exercised by shrinking the window). Strictly safer: worst case ~45s before the SAME manual fallback; best case (the flake) it catches the slow-rendering prompt and approves hands-off. **Verification:** `HR_AUTOMATION_DUO_WEBAUTHN=1 scripts/duo-firstattempt-soak.sh crm` — 5/5 normal + 3/3 @1.5s + 3/3 @200ms forced windows = 11/11 hands-off, 0 flakes, 0 regressions; the guard's recovery-on-real-slow-render can't be forced live (CRM auto-fire signs before the deadline even at 200ms), so it is pinned by unit test and will be confirmed by the next real occurrence (now a recovery, not a stall). `selectDuoFactor` takes an injectable `now?: () => number` (defaults to `Date.now`) purely so the timing-dependent guard is driven deterministically over virtual time. Pins: `tests/unit/infra/auth/duo-webauthn.test.ts` (pre-prompt recovery / real give-up without extending / promptRenderCap bound).
- **2026-06-25: ISS-005 — the intermittent first-attempt "factor not found" flake now has a prompt-state diagnostic + a repro harness (it left no evidence of WHY).** The 2026-06-17 Fix A/B/C closed the DOMINANT cause (idle-refresh reloading the prompt mid-Duo). The residual flake — `selectDuoFactor` giving up on the FIRST attempt of a system ("Duo WebAuthn factor not found at the prompt — falling back to manual Duo" → a ~180s manual-Duo timeout, since no push is sent on a WebAuthn prompt → attempt 2 recovers hands-off) — is rare and non-deterministic, and crucially logged NOTHING about the prompt's actual state, so the cause (label/transport mismatch? screen not yet rendered? wrong sub-screen?) was un-diagnosable. **Instrumentation (`duo-webauthn.ts`):** `snapshotDuoPromptState(page, reason)` is called at BOTH of `selectDuoFactor`'s give-up sites (method-list-open-but-no-matching-factor after the 3s grace; and deadline-elapsed) and logs `url + onMethodList/useTouchId/useSecurityKey/trustScreen/otherOptions + the literal link labels present`. Purely observational — locator reads only (NO `page.evaluate`, per the `__name` keep-names browser-eval gotcha in `src/core/CLAUDE.md`) and it NEVER throws (a snapshot failure must not perturb the manual-Duo fallback). **Harness (`scripts/duo-firstattempt-soak.sh [SYSTEM] [ITERATIONS]`):** loops `test-login` over ONE system N times — each iteration a fresh browser = a fresh first attempt — SERIAL (Duo signCount is global server state; never parallelize), tallies "factor not found" occurrences, and prints the diagnostic line for any flaked iteration. Per-iter logs under `generated/.duo-soak/<ts>/` (gitignored). **Status:** NOT reproduced this session — 13 consecutive clean first-attempt hands-off auths (Kuali ×2 via `separations-collect`, the 3-system separations dry-run ×2 = 6, CRM ×5 via the soak), 0 flakes. The flake remains intermittent; the diagnostic is now in place to explain the NEXT occurrence (production or a longer soak). Re-enrollment (`npm run duo:webauthn:enroll`) is still the fix only if "factor not found" degrades to CHRONIC (the dead-credential signature is "signs but never completes" with the counter already far ahead — a different failure than this first-attempt give-up).
- **2026-06-17: Idle-refresh reloaded the page mid-Duo — the dominant "all workers failing" cause under 8 parallel workers. Three fixes: guard the idle timer across the full auth chain, re-arm on a stale CDP, and a fail-fast Duo queue.** The per-system idle-refresh timer (`Session`, `src/core/kernel/session.ts`) reloads a page after 5 min of automation inactivity (30s tick). Its only guard was `idleGuard` (true while a `ctx.step` body runs), wired in `makeCtx` — which runs *after* authentication. So during the ENTIRE auth chain (`Session.launch` → `loginWithRetry` → `pollDuoApproval` → `waitForDuoTurn` in the Duo queue) the guard was false, and an idle tick could fire `page.reload()` mid-Duo. That reload (1) navigated the Duo prompt away → auth failed, and (2) destroyed the CDP virtual authenticator while `armDuoWebAuthn`'s `armedByPage` WeakMap (keyed by the surviving `Page` object) still reported the page as armed → `armDuoWebAuthn` early-returned `true` → "Duo WebAuthn factor not found at the prompt" → manual fallback → 180s timeout → retry. **Fix A (primary, `session.ts`):** a private `authInProgress` flag, set from before `loginWithRetry` until every system's readiness settles, checked in `tickIdleRefresh` + `scheduleIdleReload` alongside `idleGuard` — no idle reload can fire while auth is in progress (1-system path resets in an inline `finally`; ≥2-system path resets when the un-awaited login IIFEs' combined `allSettled` resolves; a `forWorker` child defers to the parent's window via `isAuthInProgress()`). See `src/core/CLAUDE.md` Per-System Idle-Refresh. **Fix B (defense-in-depth, `duo-webauthn.ts`):** before `armDuoWebAuthn` early-returns on `armedByPage.has(page)`, it now PROBES the stored CDP session (`cdp.send("WebAuthn.enable")`, which is idempotent); if the probe throws (target destroyed by a reload), it deletes the stale entry, releases its lock, detaches, and re-arms fresh — so even a reload that slips past Fix A self-heals instead of returning a phantom "armed". **Fix C (`tracker/sessions/duo-queue.ts`):** `waitForDuoTurn` (refactored into the injectable `runDuoQueueTurn`) gained (1) a 300s wall-clock max-wait (`DUO_QUEUE_MAX_WAIT_MS`) — a worker that can't reach the head of the queue fails fast and retries instead of blocking the pool; and (2) a time-based stale advance (`DUO_QUEUE_STALE_REQUEST_MS = 200s`, just above the 180s manual UCPath timeout) — a head-of-queue `duo_request` that is PID-alive but older than the threshold is wedged, so it's `duo_timeout`'d and the queue advances (the existing dead-PID advance stays as the fast path). Age comes from the event's own `timestamp` (the request may belong to another process), not a local clock. Pinned by `tests/unit/core/session.test.ts` (idle reload suppressed during auth, fires after), `tests/unit/infra/auth/duo-webauthn.test.ts` (stale-CDP re-arm), `tests/unit/tracker/sessions/duo-queue.test.ts` (live-but-stale advance + max-wait throw). **Operator action if "factor not found" persists AFTER this fix:** the enrolled Duo WebAuthn credential itself may be dead (chronically rejected even with the counter far ahead) — re-enroll via `npm run duo:webauthn:enroll` (and `-- --security-key` for CRM/usb), per the resolution lesson below. **Live verification still required** — unit tests can't drive a real concurrent-8-worker Duo; confirm a real multi-worker run no longer reloads mid-Duo.

(9) **A factor enrolled at the Duo account level is not accepted by every app's policy.** When the security key was made the *preferred* factor, a live `test-login` showed UCPath navigating `prompt → all_methods → /frame/v4/error` — UCPath rejects the security key — and the spent SAML challenge can't be recovered mid-flow (a Touch-ID retry needs a fresh navigation). So `selectDuoFactor` takes factors in **preference order, Touch ID first, security key only as the fallback**, and reveals the full options list before settling for the fallback so a default screen doesn't pre-empt the preferred factor. Net: UCPath → Touch ID, CRM → security key (its only factor). Do **not** force security-key-first; it breaks UCPath. **Verified end-to-end via `test-login` 2026-06-02: both hands-off, no phone push** — UCPath approved via Touch ID, CRM via Security key, signCounts advanced + persisted. signCounts are persisted per credential (monotonic max) on **every** `pollDuoApproval` exit path via `finishDuoWebAuthn`; after manual experiments (or an errored ceremony, which can advance the counter without persisting) bump the file above what Duo last observed or the next assert is rejected as a clone.

- **2026-04-29: Pre-announce grace window suppresses cached-trust false positives.** `pollDuoApproval` runs a silent pre-check loop first (default `DUO_PRE_CHECK_MS = 2000ms`, sampled every `DUO_PRE_CHECK_INTERVAL_MS = 500ms`), checking only `urlMatches` + optional `successCheck`. If the URL transitions to success during that window, log `"Duo skipped (cached trust)"` and return — no voice cue, no waiting log. If the window elapses without auto-success, the announce phase fires and the main poll loop runs as before. Tunable via `preCheckMs` / `preCheckIntervalMs` on `DuoPollOptions`; set `preCheckMs: 0` to announce immediately.

- **2026-06-03: `finishDuoWebAuthn` must fire on the ABORT/throw path, not only on timeout/success.** The 2026-06-02 lesson's "signCounts persist on **every** `pollDuoApproval` exit path" had a hole: the abort checkpoints (`throwIfAborted` in `duo-poll.ts`) and `requestDuoApproval`'s pre-poll queue wait (`waitForDuoTurn` in `tracker/sessions/duo-queue.ts`) threw straight out, abandoning the authenticator armed at `clickSsoSubmit` mid-ceremony. Fix: wrap the poll loop in `try { … } catch (err) { await finishDuoWebAuthn(page); throw err }` (idempotent — success-path calls unaffected) plus the symmetric guard in `requestDuoApproval`. Surfaced by the ≥2-system live `Session.launch` test: two browsers each arming an `internal` authenticator collided (Chrome allows one `internal` per environment — gotcha #1 above), the first ceremony stalled past its 25s grace into the 180s manual poll = the pool `testTimeout`, which `kill -9`'d it mid-flight → desync (which then failed the *next* live flow). That test (`tests/live/session-launch-multi.test.ts`) now arms a 90s internal abort under the pool timeout so a stall unwinds through this clean teardown instead of a hard kill. Pinned by `tests/unit/infra/auth/duo-poll-abort-teardown.test.ts`. **Multi-system hands-off does work** once signCount is in sync + stale per-pid UKG profiles are cleared (verified live 2026-06-03: kuali + old-kronos via `Session.launch`, 37s).
- **2026-06-05: signCount drift hits production — poll loop now self-heals (`resyncDuoWebAuthnSignCounts` + shortened fallback).** A real OCR-verify run (UCPath via delegated Person Lookup) hung on "Use Touch ID": the hands-off WebAuthn assertion **signed** (`Duo: asserting via WebAuthn (auto)`) but Duo never completed (clone-rejection — the local counter had drifted ~1 below Duo's server counter), so the 25s grace elapsed → fell back to a manual "approve on your phone" poll that **could not work** (no push is ever sent on a WebAuthn-only prompt) → the full 180s timed out → attempt 2 recovered hands-off (the `+10` reserve leapfrogged the counter on attempt 1's exit). So this is NOT only a `kill -9` failure mode — a small organic/manual drift triggers it in normal use. Two fixes (both opt-in-WebAuthn-only, manual flow byte-for-byte unchanged): (1) **auto-resync** — on a signed-but-incomplete assertion, `pollDuoApproval` calls `resyncDuoWebAuthnSignCounts()` (`DUO_WEBAUTHN_SIGNCOUNT_RESYNC = 100`, deliberately > the `+10` per-arm reserve so a single retry clears a multi-step drift) so the kernel's next attempt re-arms above Duo's counter; (2) **fail-fast fallback** — that path now uses a shortened `DUO_WEBAUTHN_FALLBACK_MANUAL_SECONDS` (30s) window instead of 180s, just long enough for the operator to hand-rescue the visible browser via "Other options → Duo Push", then it returns false so the kernel retries. Net: the ~3-min stall becomes ~30s and the retry succeeds hands-off deterministically. Decision NOT taken: seeding the CDP authenticator from the *reserved* (`+10`) value — the `reserveDuoWebAuthnSignCounts` test pins "persists a counter window **without mutating the CDP seed credentials**" on purpose (the reserve is on-disk crash headroom; the *next* run already seeds from the bumped file, spacing assertions ~+10/run), so changing the seed would fight a deliberate design and wouldn't address a drift already > +10. Pure helper pinned by `tests/unit/infra/auth/duo-webauthn.test.ts`; the loop change is live-only (run `HR_AUTOMATION_DUO_WEBAUTHN=1 npm run test-login` to verify hands-off still approves).
