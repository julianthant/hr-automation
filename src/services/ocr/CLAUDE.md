# OCR Service

Schema-bound OCR primitive used by OCR-backed workflows. Prep workflows default to per-page parallel OCR across configured vision providers; whole-PDF OCR is operator-triggered only.

## Contracts

- `ocrDocument` returns `OcrResult<T[]>`; whole-PDF results are never cached.
- Per-page OCR dispatches pages across all configured keys/providers/models with concurrency capped by `OCR_PAGE_CONCURRENCY`; a page paces itself within each cell's limits and falls back across the model chain, then other keys, before failing.
- Per-page failures stay visible as failed pages; the pipeline should not silently fall back to whole-PDF on partial failure.
- Whole-PDF OCR is reached through `/api/ocr/reocr-whole-pdf`.

## Usage tracking (per-page) — `usage-tracker.ts`

The per-page pool's admission control is `UsageTracker`, **not** the old flat-60s-after-429 scheme. It tracks live windows per `(provider, key, model)` cell — RPM, TPM, RPD (UTC daily) — plus a cooldown and a dead flag. `reserve()` only hands out a cell with headroom on all three windows now, charging it optimistically so concurrent runs see the spend; `commit()` reconciles the estimate with the real `prompt_tokens`; `penalize()` applies the server's own retry signal.

- Limits seed from `provider-limits.ts` (free-tier, best-effort, env-overridable) and are corrected at runtime by parsed `Retry-After` / `x-ratelimit-reset-*` / Gemini `RetryInfo` (`rate-limit-headers.ts`). Pool `callOcr` throws `OcrHttpError` (status + headers + body) so classification is precise.
- rate-limit → cooldown = server delay (or exponential backoff + jitter); quota → cooldown until ~UTC midnight + cell parked as daily-exhausted; auth → dead; transient → short backoff.
- State persists at `<cacheDir>/ocr-usage-state.json`, one in-memory instance per `cacheDir` (concurrent runs share throttle state). Default `cacheDir` is `.tracker/runtime`. Persistence is durable/merge-safe: `reserve()` and `penalize()` schedule a short debounced flush, `runOcrPerPage` flushes in `finally`, and every **dirty** flush re-reads + merges the on-disk cells before atomic tmp+rename (compact JSON; `max` RPD count for the same day, latest cooldown, OR dead flag) so dashboard and daemon processes do not clobber each other. A clean `flush()` cancels any pending debounce and skips disk I/O.
- `getOcrKeyStatuses` (`/api/ocr/key-status`) reports each pool key's worst cell state + summed daily count from this file.

`KeyRotation` (`rotation.ts`) still backs the **whole-PDF** path (`index.ts`) and Gemini text helpers (disambiguation/lookup-suggestions), persisting `rotation-state-{provider}.json`. Those text helpers should share that rotation path, not hand-roll key loops.

## Providers — `provider-limits.ts`

The vision pool is config-driven: `visionProviderConfigs()` lists **Gemini → Groq → Mistral → OpenRouter → SambaNova** by priority, each with a model **fallback chain** (free-tier limits are per-model, so one key exhausted on its primary model can still use the next). Override any chain with `OCR_<PROVIDER>_MODELS` (comma list) or the legacy single `OCR_<PROVIDER>_MODEL`. Defaults verified live 2026-06-02; whole-PDF path stays Gemini-only.

- **Cerebras** is excluded: no Cerebras-hosted model accepts image input (text-only). Useful only for text post-processing, not OCR.
- **Cohere** is excluded by choice: `command-a-vision` now does image OCR, but it's a single trial key (~1k calls/month).
- **OCRSpace** is excluded: free tier caps at 1 MB / 3 pages — too small for heavy PDFs.

## Tests

Use `__setCacheDirForTests` and `__setProviderForTests` to isolate cache paths and stub providers. Reset both after each test.

## Form Specs

`forms/` holds one `OcrFormSpec` per form type, all registered in `forms/registry.ts` `FORM_SPECS` (oath, emergency-contact, verify). Specs own the prompt, record schemas, `matchRecord`, `needsLookup`, carry-forward, and the optional approve targets / `enrichRecords` hook.

- **`oath` / `emergency-contact`** — write paths: `rosterMode:"required"`, declare `approveTo` (and oath also `approveDocumentTo`), fan out downstream daemon rows on approve.
- **`verify`** — read-only completeness report for a MIXED oath+EC PDF: `rosterMode:"optional"`, `needsLookup → null`, NO approve targets. All enrichment lives in its `enrichRecords` hook (delegates to person-lookup for EID/active/CRM dates and i9-lookup for the I-9 signer; mirrors `src/workflows/ocr/force-research.ts`). The hook stamps **`personLookupStatus`/`personLookupTraceId`** and **`i9LookupStatus`/`i9LookupTraceId`** per record at dispatch/outcome; `watchChildRuns.onProgress` patches + `emitProgress()` as EACH child finishes, so the dashboard updates eagerly instead of waiting for the whole person or I-9 batch. Pure helpers `buildVerifyChecks` / `applyPersonLookupToVerifyRecord` / `applyI9ToVerifyRecord` are unit-tested. The `officialSigner` check renders **"Unable to access"** (not "— not found") when the i9-lookup came back `i9Status: "unable-to-access"` (record exists but out of the operator's scope): `applyI9ToVerifyRecord` stamps `record.officialSignerStatus`, and `buildVerifyChecks` sets `check.unavailable` on the `missing` signer check (`VerifyRecordView` shows a Lock + warning tone, retry still offered). Those same helpers back the per-record retry: a FAILED check is re-runnable individually from the review pane via `runVerifyRelookup` (`src/workflows/ocr/verify-relookup.ts` → `/api/ocr/verify-relookup`), which re-fans ONE lookup (person or i9) for ONE record and re-patches. Full contract + the orchestrator hooks it relies on: `src/workflows/ocr/CLAUDE.md` (verify + verify-relookup lessons).

## Lessons Learned

- **2026-06-11: EC `approveTo.canFanOut` gates on EID-completeness (F12), mirroring oath.** The EC fan-out enqueues one downstream EC child per approved record, and the EC daemon navigates UCPath **by EID**. EC's `canFanOut` previously returned `true` for any EC-classified record, so a blank/invalid-EID record fanned out a child guaranteed to fail at navigation (and desynced per-record itemIds from what actually ran). It now also requires `normalizeUcpathEmployeeId(record.employee?.employeeId)` to match `/^\d{5,}$/` — the EC analogue of oath's `hasOathSignerInput` EID check. Pinned by `emergency-contact.test.ts` (blank + too-short EID → no fan-out).
- **2026-06-08: Verify enrichment logs per-record status transitions.** OCR review bugs are hard to reconstruct from only the final `records` JSON. `forms/verify.ts` now logs one line when each person-lookup / i9-lookup child is stamped `pending`, one line when each child outcome patches the record (`completed`/`failed`, child status, itemId, traceId, and i9 access status when present), timeout lines for missing outcomes, and a final `[verify/enrich] complete` summary with person/i9 completed/failed/pending counts. These are ordinary `category:"ocr"` log lines (no new stable `event` names) so future incidents can search the OCR run log by `[verify/i9] record N` and reconstruct whether two records were in the same lookup status at the same time. Pinned by `tests/unit/services/ocr/forms/verify-enrich-progress.test.ts`.
- **2026-06-08: Verify paper EID and resolved EID are separate fields.** The completeness report must not label a person-lookup-resolved EID as "(on paper)". `matchRecord` now snapshots the OCR paper value into `paperEmployeeId` before enrichment can mutate `employeeId`; `buildVerifyChecks` uses `paperEmployeeId` for the paper side and `employeeId` for the resolved/found side. Historical rows without `paperEmployeeId` are conservative: if they already carry a `personLookupStatus`, the EID is treated as looked up rather than paper-present. Pinned by `tests/unit/services/ocr/forms/verify.test.ts`.
- **2026-06-08: UsageTracker flushes must merge with disk before writing.** The dashboard process and daemon processes share `.tracker/runtime/ocr-usage-state.json`. A stale in-memory `UsageTracker` instance writing its full snapshot can otherwise erase another process's RPD/cooldown/dead state and retry exhausted keys. A dirty `flush()` re-reads the file, merges per cell (`rpdCount=max` when `rpdEpochDay` matches, newer day wins across days; `cooldownUntilMs=max`; `dead=OR`), updates the local map, and writes compact JSON via temp file + rename. `reserve()`/`penalize()` mark dirty and schedule a short unref'd debounce; a clean `flush()` cancels the timer and skips disk I/O; the per-page runner still calls `flush()` in `finally` as the end-of-run hard stop. Pinned by `tests/unit/services/ocr/usage-tracker.test.ts` stale-instance merge + clean no-op cases.
- **2026-06-07: OCR-pass schemas must TOLERATE `null` on cross-form fields, and form-kind is orthogonal to record SHAPE.** Two coupled gotchas from the EC/oath wrong-form classification work:
  - **Schema-tolerance (F13).** The classify-then-extract prompts tell the model to NULL the *opposite* form's fields on a wrong-form page (an EC/unknown page in an oath run nulls `printedName`/`employeeSigned`; an oath/unknown page in an EC run nulls `employee`/`emergencyContact`). But `z.string().optional()` / `z.boolean().optional()` REJECT an explicit `null` (they allow only `undefined`), and a non-nullable object field rejects `null` outright. So a *correctly-classified* wrong-form page failed `finalize()` → `per-page.ts` (~336-352, the "loud schema-drop") then flipped the whole page to `success:false` → silent data loss of the page the feature was built to KEEP. Fix (mirrors the 2026-06-04 `documentType` tolerant-coercion precedent — never drop a record over one field): oath `printedName`/`employeeSigned` → `.nullable().optional()`; EC `employee`/`emergencyContact` → `z.preprocess((v) => v ?? {}, PermissiveSubSchema)` so a `null` coerces to a defaulted object and downstream `record.employee.X` reads stay null-safe. A prompt-only fix would be WEAKER (restart-gated, future-runs-only, hostage to model variance). Pinned by safeParse regression tests in the oath/EC form test files.
  - **SHAPE vs `formKind` are two axes (F6).** A record's *shape* (which fields exist) is set by the RUN that produced it — an oath run always yields oath-shaped records (`printedName`/`employeeId` top-level), an EC run yields `employee`/`emergencyContact`-shaped records — regardless of the model's per-page `formKind` classification. `readonly-record.ts` (dashboard) must branch on SHAPE to decide which fields to READ, and on `formKind` to decide whether to show a wrong-form HINT. Branching the field-reads on `formKind` was the bug: an EC-shaped record classified `oath` read undefined oath fields → empty card, no hint. The wrong-form hint is now symmetric across BOTH directions. See `src/dashboard/CLAUDE.md` (2026-06-07).
  - **Carry-forward (F4).** Both `oath.applyCarryForward` and `emergency-contact.applyCarryForward` now carry the v2 `formKind` forward (neither pins its own kind) — EC previously hardcoded `formKind: "emergency-contact"`, contradicting its own "carry v2 formKind forward" comment. The cross-kind guard above each still rejects merging two DIFFERENT *known* kinds; this only affects the tolerated same-page re-classification.
  - **Log readability (F9).** `describeOcrRecord` (`per-page-pool.ts`) reads the name across `printedName → employee.name → emergencyContact.name → employeeId → employee.employeeId` so an EC row no longer logs as `emergency-contact: —` (its name is nested under `employee`).
- **2026-06-06: OCR provider "done" logs are a readable summary, not a raw-JSON dump.** `per-page-pool.ts` previously logged (Gemini) `[ocr/gemini] <model> done (<N>c): <first 200 chars of raw JSON>` at `success` level — the dashboard rendered it as an unreadable, panel-clipped blob; the OpenAI-compat providers logged no "done" line at all. Both paths now **parse first, then log** `[ocr/<provider>] <model> → <summarizeOcrResponse(json)>` — a one-liner of record count + each record's `formKind: printedName` (EID fallback, then `—`; capped at 4 records + `+N more`). On a parse failure a `warn` keeps the truncated raw for diagnosis (`parseOcrResponse`). `summarizeOcrResponse` is exported and unit-tested (`tests/unit/services/ocr/per-page-pool.test.ts`). The full parsed data still flows downstream to the review pane — only the log line changed. **Gotchas:** affects FUTURE runs only (SSE backend does not hot-reload — restart `npm run dashboard`); historical `.tracker/logs/*.jsonl` entries keep their raw text (logs are an audit trail, not rewritten). Readability is fixed at the SOURCE, not by the dashboard reverse-engineering log strings.
- **2026-06-06: verify oath "Authorized Official Signer" comes from the "Signature of Authorized Official" line — NOT "Signature of Officer or Employee".** The UC State Oath has TWO signature lines: *Signature of Officer or Employee* (the employee taking the oath) and *Signature of Authorized Official* (the witness/official, usually blank on filed forms). `VERIFY_OCR_PROMPT` (`forms/verify.ts`) didn't name the lines, so the model copied the employee's own signature into `paperOfficialName`/`officerSigned` → the completeness report showed the employee's name under "AUTHORIZED OFFICIAL SIGNER (on paper)" and, because `officerSigned` read true, `enrichRecords` SKIPPED i9-lookup (`if (rec.officerSigned === true) continue`) → no I-9 lookup + no I-9 thumbnail in `RecordScreenshotStrip`. Fix: the prompt now explicitly maps `employeeSigned` → "Signature of Officer or Employee", `officerSigned`/`paperOfficialName` → "Signature of Authorized Official" ONLY. With a blank official line, `officerSigned=false` → i9-lookup runs → signer looked up from the I-9 (intended source) + the I-9 thumbnail appears. Prompt-only (no schema/test-asserted text); affects FUTURE runs — re-upload/re-OCR to re-extract. **Verified 2026-06-06** by re-OCRing the actual failing page (Goiset, page 5) per-model: `gemini-2.5-flash-lite` reproduced the bug 3/3 on the OLD prompt (`officerSigned:true`/`paperOfficialName:"Umag"`) and returned blank 3/3 on the NEW prompt; `gemini-2.5-flash` never had the bug (the original buggy run landed on a smaller model). NEW prompt also returns blank on groq `llama-4-scout`, `mistral-medium`, sambanova `llama-4-maverick` — robust across the whole vision pool, so the prompt fix is sufficient; do NOT rename the `officerSigned` field (the lexical collision with "Signature of **Officer** or Employee" is what the prompt now counters explicitly). Gotcha: the dashboard SSE backend does NOT hot-reload — a prompt edit needs a full `npm run dashboard` restart before any re-OCR picks it up, and already-extracted records keep the stale value until re-OCR'd.

- **2026-06-04: `documentType` must be a TOLERANT coercion, not a strict enum — a strict enum drops the WHOLE record.** The vision prompt shows the model the page-format codes (signin/upay585/upay586/unknown), so models emit a format name (`"upay586"`) as `documentType` instead of the abstract `"expected"`. `z.enum(["expected","unknown"])` rejected it, and per-page `finalize()` discards the ENTIRE record on any single-field failure → an otherwise-perfect oath row (name, EID, both signatures) vanished and the operator saw **0 records to approve** (the `Invalid option: expected one of "expected"|"unknown"` warn in `.tracker/logs/ocr-*.jsonl`). Fix: shared `DocumentTypeSchema` (`forms/shared.ts`) `z.preprocess`es any non-`"unknown"` value → `"expected"` (case-insensitive), replacing all 5 strict-enum sites (oath ×2, EC ×2, verify ×1); the oath prompt now also says "do NOT put the format name here". `documentType` is display-only (log + badge + `OcrReviewPane.isApprovable`'s `!== "unknown"`), so coercion is semantically exact. Same theme as the 2026-05-03 rowIndex/employeeSigned default injection below — never drop a valid record over one field. Pinned by `tests/unit/services/ocr/forms/oath.test.ts`.
- **2026-06-03: Approval-signal treats hard OCR prep failure as terminal, not pending.** `subscribeToApproval` now resolves only on `done step=approved`, rejects operator discards as `OcrDiscardedError` (`failed step=discarded`), and rejects any other OCR `failed` row as `OcrApprovalFailedError`. This keeps born-at-upload oath-upload rows from waiting forever in `wait-approval` when the OCR pipeline itself fails before the operator can approve/discard.
- **2026-06-03: Per-page limiter rebuilt as a proactive usage tracker + multi-model fallback.** The old per-page path tracked throttle state for Gemini keys only (via `KeyRotation`) and waited a flat 60s after any 429; Mistral/Groq/SambaNova keys had zero throttle memory, and the OpenAI-compat path discarded the response headers. Replaced with `usage-tracker.ts` (windowed RPM/TPM/RPD per `(provider, key, model)`, proactive admission, header-driven cooldowns, exponential backoff + jitter, persisted to `ocr-usage-state.json`) + `rate-limit-headers.ts` (parses `Retry-After` / `x-ratelimit-reset-*` / Gemini `RetryInfo`) + `provider-limits.ts` (config-driven model fallback chains). Pool entries now carry a model chain and `callOcr(imagePath, prompt, model)` returns `{ json, promptTokens }`, throwing `OcrHttpError` on non-2xx. Two stale model defaults were dead and failing 100%: Mistral `pixtral-12b-2409` (removed) and SambaNova `Llama-3.2-90B-Vision-Instruct` (removed 2025-04). OpenRouter (7 free keys) wired into the pool. Gemini `callOcr` moved from the streaming SDK to a REST `generateContent` call so status/body/`usageMetadata` are captured. Whole-PDF (`index.ts`) still uses `KeyRotation`. Probes: `scripts/ocr/probe-providers.ts` (key validity) + `scripts/ocr/probe-vision.ts` (free-tier callability + token cost).
- **2026-05-19: Oath approve payloads normalize OCR names before daemon enqueue.** Queue rows should show display-case names, while raw OCR records remain in prep payloads for review.
- **2026-05-18: Oath UPAY585 EIDs may be handwritten in the top page margin.** Prompts must scan the whole page, not only printed boxes.
- **2026-05-01: Per-page is the only auto path.** Failed pages surface to review; whole-PDF is a manual recovery action.
- **2026-05-03: Per-page runner injects rowIndex and employeeSigned defaults.** Provider omissions should not drop otherwise valid records.
- **2026-05-15: Disambiguation uses OCR key rotation.** Future Gemini text helpers should do the same.
