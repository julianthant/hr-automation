# Control Module

Workflow control plane handlers that sit above both the workflow kernel (`src/core/`) and tracker observability (`src/tracker/`).

Dashboard HTTP routes should stay thin: parse/validate request bodies, call this module, then map results back to route-specific response shapes. Do not put cancel/retry/delete/bump blast-radius logic in `src/tracker/dashboard/`.

## Boundaries

- `src/control/` may import from `src/core/`, `src/tracker/`, `src/services/`, `src/infra/`, and workflow handlers when an existing in-process retry path requires it.
- `src/core/` must not import `src/control/`.
- Tracker Hono routes may import `src/control/` as HTTP adapters. Other tracker modules should keep observability concerns local unless there is a deliberate control-plane path.
- OCR discard was moved with the action engine instead of leaving `control/actions` dependent on the dashboard OCR barrel. The handler still imports narrow tracker OCR helpers for abort flags and parent metadata reads.

## Cancel contract (Contract 5 — Unified Cancel)

There is one cancel mechanism:

- The daemon constructs and registers one per-run `RunHandle` (controller + `Session`) when it claims the task; `runOneItem` consumes that exact caller-owned handle. In-process `runWorkflow` / standalone `runOneItem` calls still own their handle lifecycle. The signal is exposed as `ctx.signal`; the Page proxy races async Playwright calls against it without injecting unsupported options into Playwright arguments.
- Every cancel trigger routes through `runRegistry.cancel(runId, { reason })`: the daemon `cancel_task` worker command (issued by `buildCancelRunningHandler` for running rows, or by `buildCancelQueuedHandler` for queued rows that get claimed mid-cancel), the HTTP `/cancel-current` route, the dashboard in-process cancel route (`buildCancelRunningHandler` → direct registry call when no daemon owns the task), and the browser-disconnect handler. `cancel` aborts the controller (any in-flight Playwright promise rejects with an AbortError within ms), writes the SQLite cancel audit when the handle carries in-process `control` metadata, and schedules a watchdog that hard-kills chromium after `hardKillAfterMs` if the run has not unregistered. An aborted Playwright call also poisons the page so `Session` replaces it before reuse. The stepper maps the abort to `CancelledError('cancelled')` → `step: "cancelled"` on the terminal row.
- The stepper's between-step probe reads `controller.signal.aborted` as the synchronous-checkpoint when no Playwright call is in flight. Both paths produce the same terminal-row shape: `status: "failed"`, `step: "cancelled"`, `error: "Cancelled by user before step 'cancelled'"`.
- **Gone (2026-05-23):** `buildForceStopTaskHandler`, the `ForceStopTaskRequest` type, the `CancelMode = "cooperative" | "force"` type, the `/api/task/force-stop` route, the daemon's `/force-current` route, `createInterruptInFlightWork`, and the dashboard's Force Stop button transport. The Page proxy makes them all redundant — cancel propagates fast enough through the signal that the about:blank navigation trick is unnecessary.
- The browser normally stays alive. The poisoned Page is replaced in its existing context; only an unclosable page/replacement failure escalates to context close or hard kill and fails loud.

`performWorkflowAction({ action: "cancel", ... })` in `actions/perform-workflow-action.ts` dispatches by target status only: `t.status === "running"` → `buildCancelRunningHandler`; otherwise → `buildCancelQueuedHandler`. No mode switch.

## Retry contract (Contract 2 — Uniform Retry)

Retry is **uniform kernel behavior**, not a per-workflow capability:

- Every retry assigns a new `runId`, re-runs the handler from step 0, and feeds the workflow the **pristine original input** the task was first enqueued with — never accumulated state from a prior run.
- The pristine input lives in `tasks.original_input_json` (SQLite, migration 11). `enqueueTasks` writes it on INSERT and preserves it on adopt-existing via `COALESCE`. `retryTaskFromAttempt` deliberately resets `input_json ← original_input_json` so the daemon's claim path hands the handler the original payload.
- `reEnqueueEntry` (`ops/retry.ts`) implements a three-way split for input resolution: (1) **SQLite-happy** — `findOriginalInputForRunId` returns the pristine original input, used directly; (2) **SQLite-null-original** — row exists but `original_input_json` is null, returns a structured error (bug, not legacy state, since migration 11 always stamps at enqueue); (3) **SQLite-pruned** — task record deleted by cleanup, falls back to JSONL reconstruction via `findEntryInput` + `mergeAccumulatedTrackerStrings` + `enqueueFromHttp`. `findEntryInput` is also used for edit-and-resume `prefilledData`, which legitimately needs to fold previously-extracted fields into the prefill channel. It uses a raw SQLite snapshot before mapped task reads so a corrupt row with both columns null returns a structured error instead of throwing while parsing `input_json`.
- The new pending row carries `data.__retriedFrom = <prior runId>` for dashboard provenance and uses `ops/emit-inherited.ts` to preserve prior display metadata + row archetype while emitting the fresh retry `runId`.
- SQLite-backed retries requeue an existing task row rather than calling `ensureDaemonsAndEnqueue`, so they must call `ensureDaemonsAvailable` after emitting the retry pending row. Otherwise a retry with zero alive daemons sits queued until the dashboard orphan sweep marks it failed with "No alive daemon available".

There is **no `supportsRetry` flag**, no `WorkflowDoesNotSupportRetryError`, no per-workflow gate. If a workflow's step has irreversible side effects, the workflow is responsible for probing live system state before re-executing (the standard pattern is `findExistingTerminationTransaction`-style; see `src/workflows/separations/`). Known idempotency gaps are documented per-workflow in `src/workflows/{onboarding,work-study,oath-upload,old-kronos-reports}/CLAUDE.md` → "Retry safety".

## Enqueue supersede (one active run per queue row)

A fresh dashboard input run supersedes any prior non-terminal run for the same row — "only 1 run can be queued at a time for a queue row; a new run cancels the old ones." `buildSupersedePriorRunsHandler` (`ops/supersede.ts`) is the primitive: given the items about to be enqueued, it cancels every prior non-terminal **root** run for each `(workflow, itemId)` via the existing `buildCancelQueuedHandler` / `buildCancelRunningHandler`.

- **Wiring:** the `/api/enqueue` route injects it as `enqueueFromHttp`'s `supersedePriorRuns` option, which the kernel fires from `onPreparedItems` — after stable itemIds/runIds are assigned but BEFORE the new pending row + task are written, so `listActiveRootTasksForItem` sees only prior runs (the new runIds ride `exceptRunIds` as belt-and-braces). `src/core/` provides only the callback seam; the cancellation stays in `src/control/`.
- **Scope:** ROOT runs only (`parent_run_id IS NULL`) — a delegated OCR/batch member is never disturbed by a re-issued root run. Both queued and in-flight prior runs are cancelled (in-flight → cooperative `cancel_task` via `cancelRunning`); narrow `RUNNING_STATES` in `ops/supersede.ts` to dial back to queued-only.
- **Why here and not the retry path:** retry already enforced one-run-per-item (`ACTIVE_STATES_BLOCKING_RETRY` + task-row reuse); only the fresh-enqueue path lacked the guard. Only `/api/enqueue` injects the callback — delegated / fan-out enqueues that call `ensureDaemonsAndEnqueue` directly never supersede.
- **Best-effort:** a supersede failure (prior run already terminal in the race window, missing tracker row) is logged and skipped; the new run always proceeds. Pinned by `tests/unit/control/supersede.test.ts` + `tests/unit/core/enqueue-dispatch-supersede.test.ts`.

## Lessons Learned

- **2026-07-15: Cancellation and deletion derive task blast radius from the control DB atomically.** `requestCancelTask` returns only `accepted | already-terminal | not-found` from one transaction and never rewrites a terminal task to `cancel_requested`; accepted results carry a disposition for requested, repeated, or cancelled-before-run outcomes. Tree actions traverse recursive `tasks.parent_run_id`; projection-only display rows may be included, but any task-backed `runs.parent_run_id` disagreement is an operator-facing error rather than a silent union. Delete computes the recursive task/dependency subtree and rejects any non-terminal member in the same `BEGIN IMMEDIATE` transaction before deleting tasks, projection rows, JSONL, or screenshots. Pinned by `task-store.test.ts`, `resolve-targets.test.ts`, and `delete.test.ts`.
- **2026-07-01: Cancelling a stranded display-only OPERATION coordinator terminalizes the coordinator row instead of dead-ending (ISS-006).** An `operation` coordinator is a display row with **no SQLite task of its own** (by design — see `actions/types.ts` `treeExcludeRoots`). The single-row × already fell back from the "task not found in SQLite control store" error to a **descendant tree-cancel** (`cancelDescendantTargets` walks `runs.parent_run_id`). But when a coordinator has **no live descendants** — members already terminal, or completed/never projected into `runs` (e.g. a CLI / file-queue run that drained members via `.tracker/daemons/<wf>.queue.jsonl` without emitting SQLite tasks + member tracker rows) — the tree walk returned `[]`, so cancel surfaced the coordinator's own "task not found" and **stranded the row in the queue forever** (a `pending` row offers no delete affordance, so there was no working way to clear it). Fix: `cancelResolvedTarget` now, when `direct` is task-not-found + `runId` present + **zero** descendant results, calls `terminalizeStrandedCoordinator(t, deps)` — it reads the prior tracker row (`findInheritedPriorEntry`) and, **only if** it is an `operation` archetype (`resolveRowArchetype`) that is **non-terminal**, emits the standard operator-cancel terminal row (`emitDashboardCancelTrackerRow` → `failed` + `step:"cancelled"`) so the projection drops it out of the queue; otherwise returns `null` and the original error still surfaces. **Guards (each prevents a false positive):** no prior row → keep the honest 404 (never fabricate a phantom terminal row); non-`operation` archetype → a normal single/preview row's task-not-found is a real error or an enqueue race, not this case; already-terminal prior → never overwrite a real done/failed. Generalizes to **every** operation-coordinator workflow (oath-signature / emergency-contact / onbase + any multi-person input-run anchor), not the one that surfaced it. The `scope:"tree"` + `treeExcludeRoots` "Cancel remaining" path (`buildOperationTreeCancelRequest`) is unaffected — it excludes the coordinator root and only touches members. Pinned by `dashboard-hono-ops.test.ts` ("terminalizes a stranded operation coordinator …" + "still 404s a genuinely missing item …"), red→green.
- **2026-06-24: Per-instance stop must not synthesize a `workflow_end` the daemon will emit itself (ISS-004 double-end).** `buildStopDaemonInstanceHandler` computed `alreadyEnded` from session events read at the START (before `stopDaemon`) and then unconditionally synthesized `workflow_end(failed)` to close the session card. On the GRACEFUL path (`target` found → `stopDaemon(target, force, reassign:true)`), `stopDaemon` returns when the `/stop` HTTP response completes — but the daemon emits its OWN `workflow_end(done)` ~64ms LATER during teardown. So the card got two conflicting ends: synthesized `failed`, then the daemon's `done`. Last-write-wins rendered correctly (cosmetic), but the `failed` was spurious — a clean reassigned stop is `done`, not `failed`. Fix: `shouldSynthesizeStopInstanceEnd` (exported, unit-tested) gates the synthesis — `alreadyEnded` → never; graceful path (`daemonWillEmitOwnEnd = Boolean(target)`) → poll a fresh `readSessionEvents` for the instance's own `workflow_end` within a grace window (`DAEMON_OWN_END_GRACE_MS=1000`, `pollMs=50`) and synthesize ONLY as a fallback if it never lands; direct-kill/unreachable → synthesize immediately (the daemon can't emit its own end — same path as F8b below). **Test seam, not a soak leg:** the graceful path needs a live daemon + real `/stop` HTTP, and `daemon-teardown-soak.test.ts`'s harness both POSTs `/stop` directly (bypassing this handler) AND uses a `td-child` workflow absent from `INSTANCE_LABELS` (so `workflowNameFromInstance` → null, the handler can't resolve the instance) — so the decision logic is pinned at its seam in `dashboard-ops.test.ts` (`shouldSynthesizeStopInstanceEnd (ISS-004 …)`), red→green across all four branches. Same teardown-state-machine nest as F8b / VQ-003 (`docs/engineering/daemon-teardown-state-machine.md`).
- **2026-06-07: Per-instance stop's direct-kill fallback fails the in-flight claim immediately (fail-loud over recovery-sweep).** `buildStopDaemonInstanceHandler` resolves the instance's daemon via `workflow_start.pid` → live lockfile → graceful `/stop`. When there's NO live lockfile match (`target` undefined, race or lockfile already unlinked) it falls back to a raw `process.kill(pid)`, bypassing the daemon's graceful reassign/fail cleanup. That used to leave the daemon's in-flight claim orphaned until a peer's dead-worker recovery sweep re-queued it — an unbounded, invisible wait. Fix (F8b): on the direct-kill path, `failDirectKilledInstanceClaim` reads the killed daemon's in-flight claim from the worker store (`listWorkers(workflow)` matched by `pid` → `currentTaskId`), and if the task is still in-flight (not already terminal) fails it loud — `markItemFailed` (queue audit) + `taskStore.markTaskFailed` + an `emitInheritedRow` terminal row — so the operator gets an immediate Failed row. Best-effort: no-ops when no claim is found or the prior tracker row is missing; never overwrites an already-terminal task. (`taskStore`+`workerStore` share one control DB via `openControlStores`, so close ONCE.) **(Extended 2026-06-24:** the direct kill also bypassed the daemon's QUEUED sweep, so its never-claimed queued items sat `queued` until the ~5-min dashboard orphan sweep — the no-process analogue of E2E-105. `failDirectKilledInstanceQueue` now also fails them, but ONLY when no peer is available for hand-off (`filterPeersAvailableForHandoff(alive minus pid)` empty) so a surviving peer still absorbs them; cross-process-safe via `markItemFailedIfActive` so a concurrent recovery can't double-terminalize.)** Pinned by `dashboard-ops.test.ts` "direct-kill fallback fails the daemon's in-flight claim (F8b)" — gotcha: the session `workflowInstance` label must use the workflow's `INSTANCE_LABELS` value (e.g. `"Separation 1"`, singular — `separations` → `"Separation"`), or `workflowNameFromInstance` returns null and the handler never finds the start event.
- **2026-05-27: SQLite retry must start or wake a daemon.** `retryTaskFromAttempt` only resets the existing task row to `queued`; it does not pass through the normal HTTP enqueue path that guarantees a daemon. Keep `ops/retry.ts` wired to `ensureDaemonsAvailable` after the pending retry row is emitted.
- **2026-05-27: `emitInheritedRow` fails loud when the prior row is missing.** Cancel, retry, and OCR discard inherit display metadata and row archetype from the existing tracker row. If the lookup finds nothing, throw `PriorTrackerRowNotFoundError` — do not stamp a fallback archetype. Callers return operator-facing errors (`404` cancel, `400` discard, `{ ok: false }` retry) instead of emitting a misleading replacement row.
- **2026-05-24: Control-layer replacement rows should use `emitInheritedRow`.** Cancel, OCR discard, and retry pending rows are replacement/status rows, not fresh workflow output. Route them through `ops/emit-inherited.ts` so they preserve prior display metadata, inherit `parentRunId` unless explicitly overridden, and keep the prior row archetype final after caller data is merged.
- **2026-05-24: Retry corruption checks must avoid mapped task reads.** `TaskRow` mapping parses `tasks.input_json`, so retry control code that is classifying missing-input corruption should read the raw SQLite columns first; otherwise a row with both `original_input_json` and `input_json` null throws before the handler can return its structured operator-facing error.
- **2026-05-22: Workflow control moved out of tracker.** `src/tracker/` owns JSONL/projection/SSE observability. Operator action dispatch and low-level cancel/retry/delete/queue handlers live in `src/control/` because they mutate SQLite control state, enqueue work, issue worker commands, and also need tracker audit/projection reads. Keep future workflow control behavior in this module and leave dashboard routes as adapters.
