# sharepoint-download Workflow

Kernel workflow for pulling a shared SharePoint / Excel Online file to a local `.xlsx`. Used by:

- The **dashboard queue-header download dropdown** — always visible regardless of which workflow is selected. Each menu item is one row from `registry.ts`. Selecting an option hits `POST /api/sharepoint-download/run { id }` via `buildSharePointRosterDownloadHandler()`; the dropdown itself is populated by `GET /api/sharepoint-download/list` via `buildSharePointListHandler()`. Downloads land in `data/rosters/<YYYY-MM-DDTHH-MM-SS>-<suggested>.xlsx` (overridable per-spec via `spec.outDir`, or handler `options.outDir`).
- **emergency-contact roster download** — `scripts/download-roster.ts` calls `downloadSharePointFile()` directly with a positional SharePoint URL arg, saving into `data/rosters/`. Does NOT go through the kernel — no dashboard context, no tracker row.
- **`tsx src/workflows/emergency-contact/scripts/download-roster.ts <url>`** — standalone CLI wrapper for ad-hoc downloads into `data/rosters/`. Also bypasses the kernel (no dashboard context).

## Kernel registration (2026-04-22 promotion)

`workflow.ts` calls `defineWorkflow({ name: "sharepoint-download", ... })`, so importing this directory (from `src/tracker/dashboard.ts` at server start) auto-registers the workflow. Effects:

- Appears in the TopBar workflow dropdown alongside onboarding / separations / etc. Selecting it filters the LogPanel + Queue to this workflow's runs.
- Per-run tracker row (`.tracker/sharepoint-download.jsonl` + `sharepoint-download-<date>-logs.jsonl`) with pending → running → done/failed lifecycle — same as every other kernel workflow.
- Live Session-panel box emitted by `withTrackedWorkflow` + `Session.launch` observers. Browser chip flips idle → authenticating → authed → duo_waiting → authed based on the real `systems[].login` lifecycle.
- DONE / FAILED pill + automatic SIGINT cleanup (tracker writes a `failed` row on `kill`).
- Instance names generated by `generateInstanceName("sharepoint-download")` → "SharePoint Download 1", "SharePoint Download 2", ...

The **emergency-contact standalone CLI** deliberately bypasses the kernel — it calls `downloadSharePointFile()` directly. No dashboard context, no tracker row, silent on `sessions.jsonl`. CLI runs have no UI to surface into.

## URL injection

`SystemConfig.login` is `(page, instance?) => Promise<void>` — the kernel does not pass `input` to the login function. To thread the per-run URL in, `workflow.ts` keeps a module-level `pendingLandingUrl` that the shared queue sets via `_setPendingLandingUrl(url)` immediately before starting a queued job, and clears in `.finally()`.

**Safety:** the module-level SharePoint queue in `handler.ts` serializes all runs across ids, so `pendingLandingUrl` can never be overwritten mid-run. If that queue is ever dropped (e.g. enabling multi-browser concurrency), this pattern breaks — thread the URL via a per-runId `WeakMap` instead. This is the ONLY place in the repo using module-level state to pass data into `systems[].login`; other workflows have hardcoded auth URLs (UKG_URL, UCPath URL, etc.).

## Auth reuse

All auth logic is shared with every other system. Do NOT re-implement:

- `fillSsoCredentials` + `clickSsoSubmit` from `src/infra/auth/sso-fields.ts` — UCSD Shibboleth.
- `requestDuoApproval` from `src/tracker/sessions/duo-queue.ts` (kernel path) or `pollDuoApproval` from `src/infra/auth/duo-poll.ts` (non-kernel fallback). Both handle "Try Again" push-timeout retries and the "Yes, this is my device" trust prompt automatically.
- `microsoft.*` / `kmsi.*` / `excelOnline.*` / `fileMenu.*` selectors from `src/systems/sharepoint/selectors.ts` — see `src/systems/sharepoint/CLAUDE.md` for the step-by-step flow.

## Download location

The dashboard path and the emergency-contact standalone CLI both save under `data/rosters/` (`PATHS.dataRostersDir`). Roster *reads* still fall back to legacy `.tracker/rosters` + `.tracker/sharepoint` via `resolveRosterDirs`. All use `Playwright download.saveAs(outPath)` rooted inside the project tree — nothing ever lands in `~/Downloads`. If you see an xlsx in `.playwright-cli/`, it's a selector-mapping artifact from the interactive `playwright-cli` tool, not a production download; delete it.

## HTTP behavior — fire-and-forget

Clicking a dropdown item returns 202 immediately with `{ok, id, label, status: "launched" | "queued"}`. The frontend toasts "Started" for the current job and "Queued" when it will run after an already active SharePoint job. Operator observes:

- **Sessions panel:** live workflow box with the browser chip, Duo chip glowing during phone tap, DONE/FAILED pill on exit.
- **LogPanel:** pick "SharePoint Download" in the TopBar dropdown — per-step log lines stream in via the kernel's log-context wrapper.
- **Queue panel:** a tracker row appears for this run; picking it loads the run detail in LogPanel. `filename` + `path` detail fields are filled in after `saveAs`.

Post-launch failures (auth timeout, Duo timeout, Excel click miss) mark the tracker row FAILED. The HTTP caller is already gone by then and doesn't receive a body for those — the Session/Queue panels are the canonical status sources.

## Concurrency

Module-level serial queue in `handler.ts`. Concurrent fresh invocations **across ids** enqueue behind the current job instead of launching parallel browsers. `requestSharePointDownload({ mode: "wait" })` joins the newest current/queued job so OCR-backed run modals can wait for an already-requested roster; `mode: "fresh"` always queues a new job. Intentionally not keyed by `id` — downloading onboarding and a future separations roster in parallel would still compete for the same phone tap.

## Adding a new spreadsheet

1. Append a `SharePointDownloadSpec` to `SHAREPOINT_DOWNLOADS` in `registry.ts` — pick a URL-safe `id`, a short `label`, optional `description`, and a dedicated `envVar` name.
2. Add a commented example line to `.env.example` so operators know the var exists.
3. That's it. The dropdown auto-populates, the POST handler auto-routes by `id`, no backend or frontend edits needed.

If the registry grows past ~6 entries consider switching the dropdown to grouped menus (`DropdownMenuGroup` + a `group` field on the spec).

## Gotchas

- **Endpoints matter.** The dashboard fetches `GET /api/sharepoint-download/list` on mount and `POST /api/sharepoint-download/run` with `{ id }` on click. POST returns 202 (not 200) — frontend must treat 202 as success. The pre-kernel shape returned 200 with `{path, filename}`; that was dropped 2026-04-22 when the run became fire-and-forget.
- **Missing env var is OK.** The dropdown still renders the item; it's just disabled with an "unset" hint and a tooltip pointing at the env var name. Only clicking a configured item launches a browser. Unknown `id` in the POST returns 404 with the list of valid ids — that can only happen if the frontend and backend registry go out of sync (stale bundle).
- **Don't remove the serial queue** without also rewiring the `pendingLandingUrl` closure in `workflow.ts` — they're coupled by "only one run at a time" semantics. Parallel runs would otherwise race for the same `pendingLandingUrl`.

## Lessons Learned

- **2026-05-02: Per-spec `filenameBase` for stable saved filenames.** Default save shape is `<YYYY-MM-DDTHH-MM-SS>-<sharepoint-suggested>.xlsx`, which means the filename can change run-to-run if SharePoint's suggested name shifts (rename, version bump). When downstream code keys off filename — the dashboard's `/api/rosters` lists newest xlsx, the modal's "Use latest roster" picks `.sort().at(-1)!` — a stable, recognizable prefix is preferable. Spec entries can now set `filenameBase: "OnboardingRoster"`; downloads land as `OnboardingRoster-<YYYY-MM-DDTHH-MM-SS>.xlsx`. Threading: spec → schema input → `captureExcelDownload` opts. Both call sites (`buildSharePointRosterDownloadHandler` and the OCR orchestrator's `rosterMode=download` path) forward it. Specs without `filenameBase` keep the original `<stamp>-<suggested>` shape — back-compat preserved.
- **2026-04-22: UCSD federates SharePoint through ADFS, not Shibboleth.** First-pass `loginToSharePoint` reused the Shibboleth SSO detection + `fillSsoCredentials` helper that all other UC systems (UCPath / CRM / Kuali / Kronos) use. For SharePoint / OneDrive, Microsoft AAD actually redirects to `ad-wfs-aws.ucsd.edu/adfs/ls/` — a different SSO front-end with different form field names (`input[name="UserName"]` / `input[name="Password"]` / `#submitButton`). Shibboleth-scoped detection missed it, the code logged "No SSO redirect — possibly already authenticated via cached cookies", and the run failed at the post-auth URL check. Fix: added `adfs.*` selectors to `src/systems/sharepoint/selectors.ts` and a new `handleAdfsLogin` branch in `download.ts`. Detection is URL-prefix based (Shibboleth OR ADFS) so warm-cookie fast-paths still work. See `src/systems/sharepoint/LESSONS.md` for the full write-up.
- **2026-04-22: Fire-and-forget workflows need special `pidAlive` handling.** The Sessions-rail filter is `pidAlive || crashedOnLaunch`. For spawned-child workflows `pidAlive` flips false naturally when the child process exits. But this workflow runs IN-PROCESS inside the dashboard server (fire-and-forget `runWorkflow()` in the HTTP handler), so the recorded pid equals the dashboard's own pid — `process.kill(pid, 0)` always succeeds while the dashboard is up, pinning the workflow box to the rail forever (even for DONE runs, but especially glaring for FAILED ones). Fixed in `rebuildSessionState` by flipping `pidAlive=false` when the start pid equals `process.pid` AND `finalStatus !== null`. Regression guard: `tests/unit/tracker/session-events.test.ts` — search for "in-process workflows". If you ever add another in-process kernel workflow to the dashboard server, no code change is needed — the check is generic.
- **2026-04-22: Kernel promotion reversed the 2026-04-22 morning "keep it non-kernel" decision.** First iteration kept this directory OUT of the kernel registry so it wouldn't show in the workflow dropdown — the argument was "operator utility, not an HR record." That argument failed two user-visible tests: (a) operators couldn't see per-run logs because the LogPanel is keyed by kernel-registered workflow name, and (b) the hand-rolled session-events emission in `download.ts` drifted from what the Sessions reducer expected, so the workflow box intermittently didn't render. Both problems disappeared the moment we let `defineWorkflow()` + `withTrackedWorkflow` + `Session.launch` observers drive the events. Cost was small: one module-level variable (`pendingLandingUrl`) to inject the per-run URL into `systems[].login`, and 50 lines of custom session-event plumbing deleted. Lesson: non-kernel "utilities" that own a browser + Duo tap are usually better off as kernel workflows — the visibility you get for free outweighs the "this isn't really an HR record" philosophical objection.
- **2026-04-22: Dropdown + registry beats single-purpose button.** First cut was a single `Download onboarding spreadsheet` button hardcoded to `ONBOARDING_ROSTER_URL`. Folded into a `SHAREPOINT_DOWNLOADS` registry + `DropdownMenu` the same day — future spreadsheets (separations roster, kronos report links, etc.) are a one-liner in `registry.ts` + one env var. Handler split into `buildSharePointListHandler` (cheap, synchronous) feeding the dropdown on mount and `buildSharePointRosterDownloadHandler` (expensive, fire-and-forget kernel launch) for the actual click. Concurrency lock stays id-agnostic because it's gating the Duo-tap resource, not a per-spreadsheet queue.
- **2026-04-22: Fire-and-forget for long-running operator-triggered runs.** Holding the HTTP socket open during a 2-3 min browser automation (including Duo wait) is always wrong — clients time out, proxies drop the connection, and the operator has no way to tell progress from a stalled handshake. Respond 202 with `{status: "launched"}` and let the Session / Log / Queue panels carry the live state. Applies to any future dashboard-triggered kernel workflow — not just this one.
