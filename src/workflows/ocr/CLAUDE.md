# OCR Workflow — `src/workflows/ocr/`

The "prep phase" of any form-based workflow. Operator uploads a PDF → OCR
runs the per-form Zod-bound LLM extraction → roster match → person-lookup
enrichment (person-lookup OWNS verification — there is no separate
`verification` step) → review row in the OCR tab. Then the lifecycle SPLITS on
delegation:
- **Delegated** run (`parentRunId`, an OCR-as-sub-step of a target workflow):
  parks at `awaiting-approval` until the operator approves/discards/reuploads;
  on approve, writes the terminal OCR row and fans out downstream daemon rows.
- **Standalone** run (no `parentRunId`): has no downstream consumer (approval ≡
  delegation), so it completes terminal `done` right after person-lookup — the
  operator reads a READ-ONLY ✓/✗ completeness card (no editing, no Approve, no
  parked "review"). A failed lookup's per-record ↻ re-opens the done row.

**Approve fan-out is form-spec driven, with TWO independent targets:**
- `approveTo` (**per-record**) — one downstream row per approved record.
  emergency-contact → an EC daemon row; oath → an oath-signature EID signer row;
  onbase-emergency-contact → an OnBase import row.
  An optional `approveTo.canFanOut(record)` skips a selected-but-incomplete
  record (oath: no resolved EID) so the per-record itemIds stay in sync with
  what is actually enqueued.
- `approveDocumentTo` (**once-per-document**) — exactly one downstream row per
  approved PDF, handed `perRecordItemIds` (the itemIds the per-record fan-out
  produced) so it can wait on exactly those rows. oath → one oath-upload ticket
  row that waits for all the signer rows before filing.

A spec may declare either, both, or neither. With neither, the approve route
just writes the terminal OCR row and the owning workflow consumes it. The two
oath targets run on DIFFERENT daemons, so neither waits on its own daemon's
children (the OCR-hub fan-out that fixes the oath single-worker deadlock).
Fanned-out children parent under the delegating run (`childParentRunId =
parentRunId`). Approve REQUIRES a delegated run: a standalone approve is
rejected 400 fail-loud (approval ≡ delegation; the legacy standalone
both-targets fan-out was removed 2026-06-11 per the no-legacy policy).

**Runtime intent gate (operation model).** Spec presence is the contract for
*what can* fan out, but the once-per-document `approveDocumentTo` (oath-upload
ticket) is additionally gated at approve time by `data.operationWorkflow` on the
OCR row. An `oath-signature` operation run signs only (no ticket); an
`oath-upload` operation run skips the new ticket because its born-at-upload
task files it. `approveTo` (per-record signers) always fans out. Since the
standalone-approve removal (2026-06-11) the `spec.approveDocumentTo` branch has
no live producer — every real delegating parent stamps an operation intent that
suppresses it; the spec contract stands for a future delegating parent that
doesn't. See the 2026-06-03 operation-tracking lesson.

**Kernel-registered, NOT daemon-mode.** No browsers, no Duo. Runs in the
dashboard's Node process via fire-and-forget `runWorkflow` from
`/api/ocr/prepare`. Same shape as `sharepoint-download`.

**Archetype:** `preview` — the prep parent is an OCR review/approval row;
child/delegated scope is represented by `parentRunId`. Lookup wait behavior is
owned by the OCR orchestrator and SQLite task dependencies, not by child row
archetype.

### Row archetypes emitted

| Row                                | RowArchetype      | Dashboard surface              |
|------------------------------------|-------------------|--------------------------------|
| OCR prep parent (awaiting-approval) | `preview` | OCR review card |
| `person-lookup` children | `single` + `parentRunId` plus runtime-policy delegated grouping | Batch surface even for one delegated OCR person |
| Approved downstream children (`approveTo` / `approveDocumentTo` forms) | natural child shape + `parentRunId` (the OCR run when standalone) | Nested under the OCR card |

## Person Lookup dependency mode

The first OCR `person-lookup` fan-out uses SQLite task dependencies. The OCR
handler still returns at `awaiting-approval`; the scheduler patches records as
child lookup runs finish. If dependency setup fails before queue append, OCR
falls back to the old `watchChildRuns` path. Force-research and whole-PDF
re-OCR still use `watchChildRuns` during Phase 2; whole-PDF re-OCR also
awaits `spec.enrichRecords` when present (verify must not skip it — see the
2026-06-08 re-OCR lesson).

Retrying a failed dependency child must keep the original child task id. The
dashboard retry path uses the failed run id to create a new task attempt, then
reopens the corresponding `ocr-eid-lookup` / `ocr-active-check` dependency to
`pending`. Those are legacy dependency-kind names, not workflow names; the
retried child workflow is still `person-lookup`. Keeping the task id stable
keeps the OCR preview blocked from approval while the retry is queued/running
and lets the scheduler patch `data.records` when the retry finishes.

## Adding a new form type

1. Create the `OcrFormSpec` object (oath/EC/verify/i9 live in `src/services/ocr/forms/`).
   Mirror oath/EC for prompt + match. Add `approveTo` to enqueue one downstream
   daemon row per approved record; add `approveDocumentTo` to additionally
   enqueue one row per PDF (e.g. a ticket/upload row that waits on the
   per-record rows). A **read-only** form (gather-info, no UCPath write) declares
   NEITHER — no Approve button shows. As a standalone run it completes `done`
   after person-lookup (same as oath/EC standalone); the operator reads the
   read-only report. See `verify`.
2. Add a record renderer component in `src/dashboard/components/ocr/`
   (e.g. `MyFormRecordView.tsx`) and wire it: register a config in
   `src/dashboard/lib/ocr-downstream-registry.ts` (`registerOcrDownstream` +
   route it in `resolveOcrConfigForEntry`), then `setOcrDownstreamRenderer(...)`
   in `OcrReviewPane.tsx`. Renderer routing is the downstream registry keyed by
   `data.formType` — there is no per-spec renderer id (the old dead
   `recordRendererId` field + `record-renderers.tsx` were removed 2026-06-06).
3. Add the spec to `FORM_SPECS` in `src/services/ocr/forms/registry.ts`.
4. Run modal's picker auto-populates from `GET /api/ocr/forms`.
5. For cross-system enrichment the generic roster/eid-lookup pipeline doesn't
   cover, implement `enrichRecords` on the spec (return `null` from
   `needsLookup` to suppress the generic eid-lookup fan-out). See the verify
   lesson below.

## Lessons Learned

- **Lesson maintenance rule:** Search this section plus the downstream form workflow docs before adding OCR lessons. Merge old per-form prep behavior into the current shared OCR orchestration model.
- **2026-07-09: Fail-loud re-audit of the orchestrator (2026-07-01 campaign findings a–e).** Five hardening fixes in `orchestrator.ts`, all pinned by `orchestrator.test.ts` + `orchestrator-enrichment-warnings.test.ts`: (a) a STANDALONE run with ZERO extracted records now THROWS (`refusing to complete a standalone prep with nothing to review`) instead of completing a terminal `done` read-only card that hides total extraction failure; a DELEGATED zero-record run still parks at awaiting-approval (retry/manual-fill/discard recover there). (b) Second-opinion adoption has a positive-identity gate: when the ORIGINAL reading ranks ≥ 2 (usable EID or roster candidates), a re-read sharing zero substantive name tokens (`namesShareIdentityToken`, exported) is NOT adopted — kept + `different person` warning; every adoption stamps a `Second-opinion re-read adopted: "old" → "new"` review warning so the swap is never silent. (c) LLM enrichment failures (disambiguateMatch, lookup suggestions) push a warning onto the RECORD (`Auto-disambiguation failed…` / `Lookup-suggestion enrichment failed…`) so a failed enrichment is distinguishable from "found nothing" at review; the disambiguation test lives in `orchestrator-enrichment-warnings.test.ts` because it must `vi.mock` the dynamically-imported disambiguate module. (d) The 250ms-debounced progress `emitSnapshot` runs OFF-STACK in a timer; `writeTracker` throws the operator-discard error under a pending abort, which used to escape as an uncaught exception — the timer now skips its best-effort emit when the abort flag is set and never lets an emit error escape (the awaited path owns the discard unwind). (e) The roster read is bounded (`withTimeout` 60s/attempt) + retried 3× with backoff (`loadRosterWithRetry`) and then THROWS naming the roster path — never proceeds into matching with a missing/partial roster (which would mis-classify every record as unmatched).
- **2026-07-01: EC contact-field normalization is a gated post-match phase (EC forms only).** After second-opinion / before the post-match snapshot, `emergency-contact` and `onbase-emergency-contact` runs call `normalizeEmergencyContactRecord` (`src/services/llm/normalize-contact.ts`) per record: phones → `(XXX) XXX-XXXX`, US state → USPS code, ZIP → `NNNNN[-NNNN]` are **deterministic rules** (no LLM); a free-text `relationship` the rule table can't map and one-line address strings fall through to the shared free-tier LLM pool (`completeJson`) — which only fires on the rare messy value, so common forms never touch an API key. Changes are **surfaced as review `warnings`** (via `summarizeNormalizationChanges`), never a silent rewrite — the operator confirms at the approval gate, same "suggest, human confirms" contract as OCR extraction. The phase mutates `records` in place and reuses the existing post-match `emitSnapshot` (no new emit → no orchestrator-test count ripple), and is wrapped in `raceOcrPrepWithDiscard`. Un-normalizable values (partial phone, unknown state) are left untouched, and pool exhaustion / no-keys degrades to "no change" (the LLM call returns null). Oath carries no contact fields, so it's skipped. Pinned by `tests/unit/services/llm/normalize-contact.test.ts`; the shared LLM client contract is in `src/services/llm/CLAUDE.md`.
- **2026-06-12: Loading-phase placeholder records are form-spec-shaped (`OcrFormSpec.placeholderFields`), closing E2E-004 — which was a shape flip, not a null-writer.** The orchestrator seeds one placeholder record per rendered page before extraction; the skeleton was hardcoded OATH-shaped (`printedName:""`/`employeeId:""` top-level) for EVERY form type, so an EC run's record shape flipped mid-run (placeholder oath-shape → extracted `employee.*` shape). E2E-004's ledgered "post-lookup re-stamp nulls printedName/employeeId" was a PROJECTION ARTIFACT of that flip — exhaustive scan of every persisted artifact (both trackers' rows/sessions/debug, both SQLite stores, all API dumps) found ZERO null emissions; post-extraction EC identity lives under `employee.name`/`employee.employeeId` and survives every emission, but dumping EC-shaped records through oath-shaped keys renders `null`. The oath-shaped placeholder ALSO crashed `EcRecordView` (unguarded `record.emergencyContact.X` reads) when the Preview tab was open mid-extraction on a delegated EC run. Fix: specs declare `placeholderFields()` returning the form-specific skeleton (EC: nested `employee`/`emergencyContact`); the orchestrator owns the shared meta fields and keeps the oath-shaped default for specs without the hook (oath, verify — verify's `VerifyRecordView` tolerates it via `checks ?? []`). The lookup merge path was already null-safe (E2E-014: EID-keyed patches fill only a BLANK `employee.employeeId`, never overwrite; `looksLikeEid` requires ≥5 digits, so empty can't be written). Pinned by `orchestrator.test.ts` (EC placeholders EC-shaped + NO emission carries top-level oath keys + identity survives terminal; oath keeps its default) and `ocr-continuation.test.ts` (EC-shaped continuation patch writes nested, never stamps top-level keys, never clobbers a present EID).
- **2026-06-12: E2E fix batch — the orchestrator re-stamp set gained `dryRun` + `ocrSessionId`/`ocrRunId`; the approve fan-out resolver keys by the LOGICAL input and fails loud; discard cascade-cancels child tasks AND the dependency anchor; the anchor terminalizes at the release site.** Four coupled contracts:
  - **Re-stamp set (E2E-016/E2E-012).** `writeTracker` stamps `dryRun: "true"` (when `input.dryRun`) and the row's own `ocrSessionId`/`ocrRunId` on EVERY self-emitted row. `dryRun` is the durable bridge `readDryRun` walks — without it a dry-run operation fanned out members performing REAL UCPath saves. The `ocr*` identity stamps make the queue-row × on an OCR review row route through the DISCARD proxy (`buildRowCancelDispatchArgs`), which unwinds the prep and mirrors the parent operation row — a generic running-cancel left the coordinator parked at "awaiting review" forever. Pinned by `orchestrator.test.ts` (dryRun + ocr identity on every row).
  - **Approve fan-out itemIds (E2E-015/E2E-018, BM-1 family).** `buildFanOutItemIdResolver` (approve.ts, exported) keys by `JSON.stringify` of the LOGICAL (pre-`__runtimeOptions`) input — `ensureDaemonsAndEnqueue`'s idFn strips the kernel channels via `splitPrefilled` before invoking `deriveItemId`, so the old wrapped-input keying missed every lookup and the constant `ocr-fallback-…-r0` fallback collapsed N members into ONE queue row (and made wait-signatures' per-item attribution unrecoverable). Values are queues (duplicate-JSON records keep distinct ids); a miss THROWS → `failed step=approve-failed`, never a colliding fallback. wait-signatures stays per-ITEM by design — a retried signer reuses its itemId under a new runId and must still satisfy the wait.
  - **Discard cascade (E2E-010).** `buildOcrDiscardHandler` cancels the prep's still-queued delegated child TASKS (`cancelQueuedChildTasksForParentRun`) and its `task_kind=ocr` anchor — `deleteDelegatedChildrenForRun` only removes display rows, so daemons claimed orphan lookups for discarded preps. The queued-ticket side is covered by oath-upload's tree-scoped cancel (see its CLAUDE.md).
  - **Anchor lifecycle (E2E-003).** The `task_kind=ocr` dependency anchor terminalizes (`done`) when its last dependency settles — BOTH in the OCR scheduler tick AND in `releaseParentsForChildren` (core/task-store), because the daemon's generic settle usually wins the race; previously the release flipped it to `queued` where no daemon ever claims an `ocr` task (a zombie per prep, done or failed). Pinned by `task-store.test.ts` + `scheduler.test.ts`.

- **2026-06-07: A generic run cancel (`ctx.signal`) now interrupts a RUNNING OCR prep — the orchestrator bridges the signal to the prepare-abort flag.** Every prep-phase interruption in the orchestrator (`raceOcrPrepWithDiscard`, the `shouldAbort` callbacks) polls the in-process `isOcrPrepareAbortRequested(sessionId, runId)` registry — and ONLY the OCR discard route (`/api/ocr/discard-prepare`) set it. So a generic control-layer cancel (dashboard per-row ×, daemon stop, the Tier-1 `rt.cancel`) that aborts `ctx.signal` was **silently ignored** by the orchestrator: `opts.signal` was received (handler + stub both pass `signal: ctx.signal`) but never wired to anything. For a DELEGATED run it didn't bite (it parks in the signal-aware `subscribeToApproval` wait, which the handler converts to a `CancelledError` at `workflow.ts`), but a STANDALONE `verify` run blocks in its `enrichRecords` → `watchChildRuns` (which is NOT handed `ctx.signal`) and so hung until `watchChildRuns`' multi-hour timeout — the run never reached terminal cancelled. Fix (`orchestrator.ts`, two edits): (1) at entry, when `opts.signal` aborts, call `requestOcrPrepareAbort(id, runId)` so the existing polls unblock; (2) in the outer catch, when the discard-abort error fired AND `opts.signal?.aborted` (a generic cancel, NOT a UI discard — the discard route leaves the signal un-aborted, which is how the two are told apart), **rethrow** instead of returning `{status:"discarded"}`, so the daemon's `mapEscapedHandlerError` (on the cancel-requested run) maps it to a `CancelledError` + `step:"cancelled"` terminal — the standalone-prep analogue of the delegated `subscribeToApproval` cancel. The daemon-dispatched enrichment children are independent runs: the parent cancel does NOT propagate (the `enrichRecords` promise is orphaned by the `Promise.race`, not aborted) — only the parent reaches terminal cancelled. Pinned by `tests/delegation/ocr-verify-lookup.test.ts` (cancel-mid-enrichment: previously hung the full 30s → now terminal `failed`/`step:cancelled` in ~3s). **(2026-06-11 residual fix, Task A2):** every enrichment `watchChildRuns` (verify `enrichRecords` ×2, force-research, retry-page, whole-PDF re-OCR, verify-relookup ×2) now threads `shouldAbort: () => isOcrPrepareAbortRequested(sessionId, runId)`, AND on the resulting discard-abort cascade-cancels the still-queued person-lookup / i9-lookup children via `cancelQueuedChildTasksForParentRun` (tracker `tasks/store.ts`) before rethrowing — otherwise a daemon would still claim and run the un-claimed children after the operator gave up. The standalone dashboard-process OCR prep also registers on the unified `runRegistry` (browserless handle, no `session`) so the queue-row Cancel × actually aborts the run instead of falling into cancel.ts's stale-tracker no-op branch (Task A1).

- **2026-06-04: Approval ≡ delegation — only DELEGATED OCR runs (`parentRunId`) show Approve.** _(PARTLY SUPERSEDED 2026-06-06: a standalone run no longer "inspect-and-discards" while parked at `awaiting-approval`/"Review" — it COMPLETES `done` after person-lookup and the operator reads a read-only card. Rationale (operator's mental model): approval exists to release extracted data to **downstream steps that consume it**.
