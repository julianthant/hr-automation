# Separations Workflow

Multi-system employee termination: extracts data from Kuali Build, reads the New Kronos timecard for the last physical punch + sick/holiday days, creates the UCPath termination transaction, fetches Job Summary, and fills Kuali finalization fields. **3 browsers — Kuali, New Kronos, UCPath** (Old Kronos was removed from separations 2026-06-18; the `old-kronos` system module still exists for `old-kronos-reports`).

**Kernel-based.** Declared via `defineWorkflow` in `workflow.ts` and executed through `src/core/runWorkflow` (single-doc) or `src/core/runWorkflowBatch` (multi-doc sequential mode). The kernel owns browser launch, auth-chain orchestration, per-doc tracker entries, SIGINT cleanup, and screenshot-on-failure. The public start path is dashboard input run (`InputRunPanel` → `/api/enqueue`), which enqueues one or more `{docId}` items to any alive separation daemon (or spawns one). `runSeparation` and `runSeparationBatch` are preserved for in-process use (tests, scripts).

## What this workflow does

Given one or more Kuali document IDs, for each doc: launch 3 tiled browsers (Kuali, New Kronos, UCPath); **`authChain: "parallel-staggered"`** — every SSO form is filled in parallel, then submits are spaced (`staggerMs`, default 5s) so up to **three Duo prompts overlap** on the phone (approve in any order); extract separation data from Kuali; **fetch the UCPath Workforce Job Summary (identity-aware: found/not-found + detail-page name) and conditionally verify identity (the `identity-check` step — now BEFORE kronos-search) — see "Conditional name↔EID verification" below: it skips on a clean name match, corrects the Kuali name in place on a close spelling variant, and delegates to person-lookup only on a very different / not-found name (dynamic timeline); check for an existing UCPath termination transaction (the `transaction-check` step) — see "Transaction check" below; fill the Kuali department/payroll from the Job Summary (`ucpath-job-summary`, now BEFORE kronos-search); then — only for HDH (Housing/Dining/Hospitality) employees, the ones timekept in New Kronos — run a 2-way parallel fetch (New Kronos timecard + Kuali timekeeper name fill) via `ctx.parallel` (non-HDH skips it — see "Department gate" below);** reconcile dates (see "Date model" below); create the UCPath termination transaction (unless an approved duplicate already exists — then reuse it); write the transaction ID back to Kuali and save.

## Conditional name↔EID verification (2026-06-18 — READ THIS)

The `identity-check` step (now **BEFORE** `kronos-search` + `transaction-check`; gated on the Workforce Job Summary result, which is **fetched inline just before the step** rather than inside kronos-search — see the 2026-06-22 reorder lesson) searches UCPath **by the Kuali EID first**, then branches on how the Job Summary detail-page name compares to the Kuali name via **`classifyNameSimilarity`** (`src/services/matching/match.ts`) — an **order-insensitive token alignment** returning `same` / `similar` / `different`. It runs person-lookup ONLY on a very-different / not-found name; a close spelling variant is fixed in place; a clean match skips. The gate:

| Job Summary outcome | identity-check |
|---|---|
| **Found** + name tier **`same`** (identical tokens, order/format-insensitive) | **SKIPPED** — EID trusted, name correct, no person-lookup |
| **Found** + name tier **`similar`** (close spelling variant — Kuali "Balmaceda, Jaden" vs UCPath "Jayden Balmaceda") | **RUNS** → trust the EID, **correct the misspelled Kuali name in place** (`correctNameSpelling` + `updateEmployeeName`); NO person-lookup, NO EID change, NO re-fetch |
| **Found** + name tier **`different`** (the valid-format-but-wrong-person Perez `10694136` case) | **RUNS** → delegate by name → if the resolved EID **DIFFERS**, **PAUSE for operator EID approval** (no silent override — see "EID approval review" below); if it matches the Kuali EID, proceed |
| **Not found** + EID is **< 8 digits** (incomplete) | **RUNS** → delegate by name → if the resolved EID **DIFFERS**, **PAUSE for operator EID approval**; if it matches, proceed |
| **Not found** + EID is a **complete 8 digits** | **RUNS → FAILS LOUD** (no lookup — operator fixes the upstream record) |
| txn # prefilled, OR kronos-search skipped (edit-resume / "Transactions only") | **SKIPPED** — no Job Summary gate; the operator prefilled/asserted the data |

- **Why three tiers (the Jaden→Jayden fix):** the old binary gate scored `scoreNameMatch("Balmaceda, Jaden", "Jayden Balmaceda")` = **0** — its fuzzy tier runs Levenshtein on the UNSORTED joined tokens, so the First-Last vs Last-First order inflated the distance past 0.85. That delegated a person-lookup BY the misspelled name "Jaden", found nothing, and **failed loud** even though the EID was correct. `classifyNameSimilarity` aligns token-by-token (order-insensitive), so a one-letter first-name typo lands in `similar` (fix the name, keep the EID), not `different` (doomed name search).
- **`similar` correction preserves Kuali's "Last, First" format** — `correctNameSpelling` swaps only the misspelled token for the UCPath spelling verbatim (it does NOT reconstruct from "First Last", which would mangle compound last names). The corrected name is written to the Kuali form via `updateEmployeeName` and stamped to `ctx.data.name`.
- **The name correction writes even in dry-run** — like the timekeeper-name fill bundled into `kronos-search`, the `similar` branch calls `updateEmployeeName` against the UNSUBMITTED Kuali draft (it commits nothing; the dry-run terminal still skips `kuali-finalization`, so the document is never finalized/submitted).
- **Dynamic timeline:** the no-action cases call `ctx.skipStep("identity-check")` → the step renders **skipped**. `similar` runs but does NOT add a delegated child row (it's a Kuali write, not a person-lookup). `different` / not-found run AND surface a delegated person-lookup child row, then either proceed (resolved EID matches) or PAUSE for approval (resolved EID differs).
- **A DIFFERENT resolved EID no longer auto-overrides — it PAUSES (see "EID approval review" below).** The name is NOT silently authoritative anymore: `resolveSeparationEid` returns `verified` (resolved EID matches the Kuali one) or `needs-approval` (it differs); on `needs-approval` the handler skips every downstream step and ends the run `done` with `data.eidApproval="pending"`. There is therefore **no EID-correction re-fetch on the first pass** (the old `different`→override→re-fetch path is gone — a differing EID pauses before any re-fetch). An **unresolvable** name still FAILS LOUD (never proceeds unverified). Pinned by `match.test.ts` (`classifyNameSimilarity`/`correctNameSpelling` tiers) + `resolve-eid.test.ts` (verified vs needs-approval vs fail-loud) + `dry-run.test.ts` (pause wiring + the eidPreApproved re-run) + `steps.test.ts` (order).

## EID approval review (2026-06-29 — READ THIS)

When `identity-check` resolves an EID by name that **differs** from the one on the Kuali form, the run does **NOT** silently take the name-derived EID and submit a termination. Doing so once **terminated the wrong person**: a graduating student's Kuali doc carried EID `10833507` ("Hernandez, Jose Santos" — a student, job *STDT 3*, consistent with "Graduated/No longer a Student"), but the UCPath detail name rendered "Santos Hernandez" → `different` → a name search on the common name "Hernandez, Jose" resolved a *career* maintenance worker (`10401814`, *BLDG MAINT WORKER SR*, employed since 2016), and the override filed a real termination (`T002173685`) against him.

So a resolved-different EID now **PAUSES into an operator review** instead:

- **Pause** (`resolveSeparationEid` → `needs-approval`): the handler `ctx.skipStep`s `transaction-check`/`ucpath-job-summary`/`kronos-search`/`ucpath-transaction`/`kuali-finalization`, stamps `data.eidApproval="pending"` + both candidates' context (original Kuali EID's UCPath name/dept/payroll from the inline Job Summary; proposed EID's name/dept/payroll from person-lookup's CRM-sourced result data), and **returns cleanly (`done`)** so the 3 browsers release and the daemon claims the **next queued doc** — the queue is never blocked. A separations run can't *park* (it holds 3 live browsers), so this is terminate-and-re-enqueue, NOT the OCR in-process `subscribeToApproval` park.
- **Display:** `separationsStatusExtensions` (`src/domain/separations-status.ts`, registered in `queue-row-status-index.ts`) maps `data.eidApproval` → derived status `awaitingApproval` (amber "Awaiting Approval") / `dismissed` (neutral). The dashboard `EidApprovalBanner` (`log-panel/`) renders both candidate identities side by side so the operator sees which person is which.
- **Approve** (`POST /api/separations/approve-eid`, `control/ops/separations-eid-approval.ts`): re-enqueues the doc as a **fresh** run carrying ONLY `prefilledData.eidApproved=<chosen EID>` (original / proposed / manually-typed). The handler forces that EID over extraction (the `eidPreApproved` gate, right after `kuali-extraction`), **skips the identity-check gate** (no re-pause — even a "keep original" choice whose name still mismatches), and otherwise runs fully fresh (the approved person's Job Summary + Kronos + transaction). Deliberately NOT the `/api/run-with-data` accumulated-strings merge — that would prefill the dates (skipping the approved person's Kronos read) and carry the stale `eidApproval=pending` forward.
- **Dismiss** (`POST /api/separations/dismiss-eid`): stamps the paused row `eidApproval="dismissed"` (neutral terminal, NOT a failure) and re-queues nothing — the operator fixes the Kuali form by hand.
- **`verified`** (person-lookup confirms the SAME EID) proceeds unchanged; an unresolvable name still FAILS LOUD.

This supersedes the prior "name is authoritative — take the name-derived EID" rule. Pinned by `resolve-eid.test.ts`, `dry-run.test.ts` (pause + eidPreApproved re-run), `separations-status.test.ts`, `separations-eid-approval.test.ts`.

In batch mode (`runWorkflowBatch`) or daemon mode, all three systems authenticate once per session startup; the browsers are reused for every doc, with `session.reset(id)` run between docs to restore a clean starting state.

## Transaction check (2026-06-22 — READ THIS)

The `transaction-check` step runs **AFTER `identity-check`** (so it searches with the verified EID — person-lookup runs only inside `identity-check`) and **BEFORE `kronos-search`**. It opens **SS Smart HR Transactions** (`src/systems/ucpath/ss-smart-hr.ts` — `findTerminationTransactionStatus`, reusing the `ssSmartHRTransactions.*` search selectors mapped 2026-04-24), searches by EID, and finds the row whose Action = **TER**.

**Two INDEPENDENT concerns, decoupled (2026-06-24 — READ THIS).** `runTransactionCheck` does NOT route the pending delete through the effdt-gated SS Smart HR search anymore:

1. **Approved-reuse (SS Smart HR search, effdt-gated).** An employee can be terminated for a PRIOR job, leaving an old TER that is NOT this separation. So the newest TER is **drilled into** (`transactionResultRow` → Transaction Details), its **effective date** read (`Effdt: YYYY-MM-DD` strip, `Start Date` cell fallback), and compared to the **Kuali separation date** (passed in from the handler): only a TER within **`SEPARATION_TERMINATION_WINDOW_DAYS` (14, "a week or two")** is REUSED. A TER outside the window is a prior termination → the search returns `found:false` (`priorTerminationSkipped`) → a fresh transaction is created. The window decision is the pure, unit-pinned `isWithinSeparationWindow`; if the effdt can't be READ it returns `priorTerminationSkipped` + `log.warn` (never reuses an unverifiable TER). The effdt gate now governs **only this reuse decision** — it no longer gates the pending delete. **Drill-in selector LIVE-VERIFIED 2026-06-24** (`playwright-cli`): the SS Smart HR Transaction ID column is a display-only `<span>`, not a link — the clickable target is the result ROW `<tr id^="trPTS_CFG_CL_STD_RSL">`. The original screenshot-authored `transactionResultLink` (a `getByRole("link")`) timed out and silently reused an APPROVED prior-job TER — Micah Roye / EID 10797079: TER `T001928408` Effdt **2025-07-01** reused for an **06/17/2026** separation. `transactionResultRow` filters that row by the txn-id; the `Effdt:` read now succeeds.

2. **Pending sweep (in-progress grid, DATE-AGNOSTIC).** On EVERY path that leads to a fresh create, `deletePendingTransaction` deletes **all** pending "Terminat" rows for this EID from the Smart HR **"Transactions in Progress"** grid — **regardless of effective date**, independent of what the SS Smart HR search returned. This is the real duplicate guard: a prior run can leave a pending termination whose computed effdt DIFFERS from this run's, and BOTH date-keyed backstops miss it (the SS Smart HR effdt gate above AND `ucpath-transaction`'s exact-effdt `findExistingTerminationTransaction`), so a second create produces a visible duplicate (Erick Guzman 10779506: 06/14 + 06/20). The in-progress grid only holds UNPROCESSED transactions, so any termination there for this person is a superseded prior attempt; an approved prior-job TER is processed and not in this grid, so the sweep can't touch it.

Branch summary:

| Situation | Action |
|---|---|
| **Approved TER within window** | **reuse it** — grab the `T#`, **SKIP `ucpath-transaction`** (no new create), and file the **duplicate-termination comment** (`buildDuplicateTerminationComment`) into the Kuali Timekeeper/Approver Comments. NO pending sweep (nothing is created, and the approved row isn't in the in-progress grid). This is option **A** (full run, only the transaction *creation* is replaced). |
| **anything else** (no TER / Pending / Denied / Error / prior-job skipped) | **sweep the in-progress grid** of any pending "Terminat" row for this EID (`deletePendingTransaction`, all matches, date-agnostic), then proceed to create. `pending-deleted` when ≥1 row was removed, else `none`. |

- **Comment** (Image 7, two lines, both `-<initials> <today>`): `Duplicate termination. Re Kuali Form #<docId>.` + `EE termination approved on UCPath.` — initials from `getInitials(getTimekeeperName())`, date from `todayMmDdYyyy()`, form # = docId. Built in the handler, stamped onto `ctx.data.comments` (append-joined), filed by the append-aware `fillTimekeeperComments` in `kuali-finalization`.
- **Dry-run:** the search runs read-only; the **sweep is the only mutation and is guarded** — `runTransactionCheck(ctx, eid, { dryRun })` reports "would delete any pending termination from the in-progress grid" without touching UCPath (returns `pending-skipped-dryrun` when a Pending TER was visible, else `none`). An approved-duplicate `T#` is stamped into the dry-run snapshot so the operator can preview the reuse.
- **Skipped** only on the txn-prefilled resume path (UCPath already has the transaction; nothing to check).
- **Results-grid parse is dual-pass + unit-pinned (2026-06-24):** the live `scanSsSmartHrResults` now only collects a cell-text matrix from the grid; the parse is the pure `parseSsSmartHrRows` — **header-keyed first, then a header-INDEPENDENT pattern pass** (a row carrying a T-id + a status keyword, plus a 3-letter action code when present). This fixed the live miss where an APPROVED TER for EID 10759273 ("Ava Tolles") wasn't found by the header-only scan, so transaction-check wrongly created a duplicate that UCPath then rejected (the "UCPath did not recognize Empl ID" failure). Both passes + `pickTerminationRow` are unit-tested (`tests/unit/systems/ucpath/ss-smart-hr.test.ts`). The in-progress-grid **delete checkbox + `#ICOK` confirm-dialog are LIVE-VERIFIED 2026-06-24** (playwright-cli — see the pending-sweep lesson below). **STILL NEEDS LIVE VERIFY:** the **SS Smart HR search** results-grid `<tr>` cells collect cleanly (a debug log lists every scanned `T#=action/status`) — that's a different page from the in-progress grid and was not exercised in the 2026-06-24 live pass.

## Date model (2026-06-22 rework — READ THIS)

The old "Kuali separation date is authoritative, never overridden" model is **gone** (it was wrong — operator-confirmed). Both dates are now derived from the New Kronos timecard. The reconciliation is:

- **Last Day Worked** = New Kronos **last physical punch** (`getSeparationTimecardData().lastPunchDate`). It OVERRIDES the Kuali LDW when they differ (the timecard is ground truth for physical work). Falls back to `kualiData.lastDayWorked` when New Kronos returned no punch (`lastPunchDate === null`) OR kronos-search was skipped (edit-and-resume prefill / "Transactions only" preset).
- **Separation Date** = the **last day the employee was PAID for** (worked OR on paid leave) = `max(lastDayWorked, last sick date, last holiday date)` via `computeSeparationDate(lastDayWorked, sickDates, holidayDates)` — **but ONLY when a New Kronos timecard was actually READ.** "Usually the same as the last day worked unless the employee has sick hours or holiday pay." With a timecard read + **no leave** it collapses to the Last Day Worked; a timecard read that returned **no punch** (HDH found-but-empty / not-found) still derives (via `lastDayWorked`) to the **Kuali Last Day Worked**. **When `kronos-search` was SKIPPED** (non-HDH department, or the edit-and-resume prefill / "Transactions only" preset) there is **no timecard to derive from, so the Kuali Separation Date is kept VERBATIM** — NOT re-derived to the LDW. Re-deriving on a skip produced a spurious "Updated Separation Date … per Kronos timesheet" write-back + comment for non-HDH employees whose Kuali sep date differs from their LDW even though Kronos was never read (2026-06-24, Bookstore "Nakagawa, Matthew K", 06/15→06/14). So: timecard read → DERIVED; kronos skipped → Kuali's date verbatim (`separationDateChanged` is then false → no write-back, no comment).
- **Termination Effective Date** = Separation Date + 1 day (`computeTerminationEffDate`), **recomputed from the reconciled separation date** (an early `kualiTermEffDate` from Kuali's claimed date is used only for the extraction logs).
- **Sick / Holiday days** (`getSeparationTimecardData().sickDates` / `.holidayDates`) now **both extend the Separation Date AND drive the comment clause**.

Both dates are written back to Kuali when they differ from the requester's entry: `updateLastDayWorked` (gated on `ldwChanged`) and `updateSeparationDate` (gated on `separationDateChanged`). Each gets an audit comment in the Timekeeper/Approver Comments field — `buildDateChangeComments` (LDW) + `buildSeparationDateChangeComment` (separation date), newline-joined in `kuali-finalize.ts`. Write-backs are **live-only** (the dry-run terminal returns before any Kuali write).

Comment wording (`buildTerminationComments`): `Termination eff <eff>. Last Day Worked <ldw>.` + an **optional SINGLE leave clause** + ` Kuali form #<docId>.`. `<ldw>` is the **physical Last Day Worked**, NOT the separation date — sick/holiday leave extends the **separation date** (and thus `<eff>`), never the LDW. Only **one** leave clause is ever emitted: with a single leave type, its clause (sick `Sick Leave on <latest>.` — the **latest sick date only, never a range**; holiday `Holiday Pay on <d>.` / `Holiday Pay from <first> to <last>.`); when a person has **BOTH** sick leave and holiday pay, only the **LATEST** of the two is reported — the leave day that actually determines the separation date — **never both** (holiday wins a strictly-later date, sick wins ties). Date-change audit notes: `Updated Last Day Worked from <a> to <b> per Kronos timesheet. -<II>` and `Updated Separation Date from <a> to <b> per Kronos timesheet. -<II>`.

## Department gate — skip Kronos for non-HDH (2026-06-24 — READ THIS)

Only **Housing/Dining/Hospitality (HDH)** employees are timekept in **New Kronos**, so there is no timecard to read for anyone else. The step order was changed so the Workforce Job Summary department gates the timecard read:

- **New step order:** `kuali-extraction → identity-check → transaction-check → ucpath-job-summary → kronos-search → ucpath-transaction → kuali-finalization`. `ucpath-job-summary` (the Kuali department/payroll fill) moved AHEAD of `kronos-search` (it was after) so the department is resolved + filled before the timecard read.
- **The gate:** the department comes from the Workforce Job Summary already fetched inline before `identity-check` (`getJobSummaryIdentity`). After `transaction-check`, a NON-HDH department **skips `kronos-search`**: the Last Day Worked falls back to the Kuali LDW and the **Separation Date is kept verbatim from the Kuali form** (no timecard was read, so it is NOT re-derived to the LDW — see "Date model"; this means **no separation-date write-back and no "per Kronos" comment** for non-HDH employees). HDH membership uses the canonical **`isAcceptedHdhDepartment`** (`src/domain/hdh/departments.ts`) — a department-**description** keyword match (`housing`/`dining`/`hospitality`, case-insensitive), the same matcher person-lookup uses for HDH disposition. It is intentionally NOT a single dept-code (`000412`) match — HDH spans many sub-department codes, but they share those keywords in the description.
- **Job Summary is date-correct ACROSS EVERY TAB (2026-06-24):** `getJobSummaryIdentity` is passed the Kuali separation date, and **both** the Work Location tab (department) **and** the Job Information tab (Job Code → Kuali Payroll Title Code/Title) pick the effective-dated row with the **latest Effective Date at-or-before the separation date** via the shared, pure, unit-pinned `pickEffectiveDatedRow` (`pickWorkLocationRow` is a thin wrapper; `extractJobInfo` now scans ALL job-coded rows + their effective dates and applies the same rule). The "most recent on or before the separation date" rule is **not Work-Location-only** — it governs everything we extract from Workforce Job Summary, so a transfer OR a post-separation promotion/reclassification resolves to the department + payroll title of the job actually being separated (and the HDH/non-HDH kronos skip decision stays accurate). Falls back to the latest row (no separation date) or the first row (no readable dates → legacy behavior, no regression). Job Information reads the Effective Date in-row, with the same count-exact frozen-column zip fallback Work Location uses. See `src/systems/ucpath/LESSONS.md` (2026-06-24). **NEEDS LIVE VERIFY:** confirm a per-row Effective Date is read on the live Work Location AND Job Information grids (logs show a non-empty `eff=` per row).
- **FAIL-SAFE:** kronos is skipped ONLY on a **positive** non-HDH determination — Job Summary found the person AND returned a **non-empty** department AND it isn't HDH. When the department is unknown (no Job Summary fetch ran — prefill/preset/txn paths — or it came back empty) kronos **still runs**; silently skipping an actual HDH employee's timecard would produce wrong dates.
- **Non-HDH still fills the department** into Kuali (`ucpath-job-summary` runs for everyone with fillable Job Summary data); only the Kronos timecard read is skipped.
- **Dry-run:** `ucpath-job-summary` is skipped in dry-run (no Kuali dept fill — unchanged behavior), but the department gate still reads the department and an HDH timecard read still runs as part of the dry-run READ path. The dept FILL moving before the timekeeper-name + date write-backs is safe — the same Kuali department dropdown already survives the later `kuali-finalization` edits today (it is written, then more fields are filled, then the form is saved). **NEEDS LIVE VERIFY:** confirm on a real Kuali separation form that filling the department first, then the timekeeper name + dates, doesn't reset the dropdown.

## Parallel-staggered auth (kernel)

`authChain: "parallel-staggered"` replaces ad-hoc promise chains from the pre-kernel era:

- `prepareLogin` fills every system's SSO form **in parallel**.
- `submitLogin` runs on a stagger so Duo prompts from Kuali, New Kronos, and UCPath **overlap** — the operator approves them in any order. Wall-clock auth is dominated by the slowest Duo plus stagger spacing, not three serial Duos.
- `ctx.page(id)` still awaits each system's ready promise, so Phase-1 `ctx.parallel` tasks start as soon as **that** system's Duo clears.

The old `interleaved` pattern (blocking first Duo + background chain) is **not** what ships today — see `defineWorkflow` in `workflow.ts`.

## 3-browser tiling

```
[ Kuali ] [ New Kronos ] [ UCPath ]
```

Screen 2560x1440. `Session.launch` with `tiling: "auto"` detects actual screen dimensions via CDP on the first browser, then uses `computeTileLayout(i, 3)` + `Browser.setWindowBounds` to position each window (tile count is derived from `systems.length`, so dropping Old Kronos re-tiles to 3 automatically).

## Gotchas

- **Employee name is normalized to the display convention at extraction (2026-06-24).** Kuali stores the name ALL-CAPS, no space after the comma (`"NAKAGAWA,MATTHEW K"`). `runKualiExtract` runs it through `displayPersonName` (`src/domain/identity/person-name.ts`) → `"Nakagawa, Matthew K"` before stamping `ctx.data.name`, so the dashboard header, comments, and the identity-check name compare all carry the standard "Last, First M" form — not raw caps. Idempotent + order-preserving (keeps "Last, First"); the edit-and-resume prefill path normalizes too. `classifyNameSimilarity` is order/case-insensitive, so this does not change identity-check verdicts.
- **3 Duo authentications** — with parallel-staggered auth they **time-overlap** (not strictly one-at-a-time). Phase-1 work still starts per browser as soon as **that** browser's Duo completes.
- **Date reconciliation** — see "Date model" above. LDW = New Kronos last physical punch (overrides Kuali when it differs, falls back to Kuali LDW when absent); Separation Date = `max(LDW, last sick date, last holiday date)` = the last day paid (DERIVED from the timecard, not Kuali); sick/holiday extend the separation date AND drive the comment clause. Both dates are written back to Kuali when changed (`updateLastDayWorked`/`updateSeparationDate`, live-only, each with an audit comment). The old "Separation Date = Kuali, authoritative, never overridden" model is removed.
- **Termination effective date** = separation date + 1 day (computed, not from form).
- **Voluntary vs Involuntary** — `isVoluntaryTermination()` in `src/systems/kuali/navigate.ts`. "Never Started Employment", "Graduated/No longer a Student", and "Appointment Expired" are involuntary; all others voluntary. Template is `UC_VOL_TERM` or `UC_INVOL_TERM` accordingly. ("Appointment Expired" is a literal UCPath `INVOL_TERM` reason code — it maps to itself in `REASON_CODE_MAP`, not to a `Resign - …` voluntary code.)
- **Reason-code mapping** — exact match → fuzzy match → fallback. VOL_TERM uses `"Resign - ..."` codes; INVOL_TERM uses codes like `"No Longer Student"`.
- **`computeKronosDateRange` ±1 month** — narrower windows missed timecards. `Date.setMonth()` overflow on 31st-day inputs slightly under-expands (Mar 31 − 1mo targets Feb 31 → Mar 3); harmless given the buffer. Pinned by `tests/unit/workflows/separations/schema.test.ts` — don't "fix" without considering test impact. ## Dry-run boundary

`SeparationInputSchema` carries an optional `dryRun` flag (mirrors onboarding /
oath-signature / emergency-contact). Unlike onboarding — which has a SINGLE
irreversible write (the UCPath Smart HR submit) at its last step — separations
has **two** committing mutations: the UCPath Smart HR submit
(`clickSaveAndSubmit`, inside `ucpath-transaction`) and the Kuali finalization
save (`runKualiFinalize`, inside `kuali-finalization`). So the dry-run terminal
sits **earlier**, right after date reconciliation and **before
the Kuali date write-backs**: it `skipStep`s `ucpath-transaction` /
`kuali-finalization`, captures a
`separations-dry-run-before-submit` screenshot, stamps `status: "Dry Run
Complete"` + `dryRun: true` (plus the reconciled read data for the detail panel),
logs `DRY RUN: reached UCPath Smart HR transaction … submit + Kuali finalization
skipped`, and returns succeeded / `done`. (`ucpath-job-summary` — the Kuali
dept/payroll fill — now runs BEFORE the terminal but skips itself on the `dryRun`
branch, so the dry-run path still does no department fill.)

What still runs in dry-run: 3-system auth (**3 Duos**), Kuali extraction, the
inline Job Summary identity gate + `identity-check`, the `transaction-check` SS
Smart HR search (its delete is guarded — see "Transaction check"), the
**department gate** (reads the Job Summary dept to decide the HDH/non-HDH kronos
skip — see "Department gate"), the 2-way New-Kronos/Kuali parallel fetch (HDH
only), and date reconciliation — the entire READ path.
The residual writes are both on the **unsubmitted** Kuali draft and commit
nothing (the doc is never finalized), the same way onboarding's search-first I-9
create runs in its dry-run: the timekeeper-name fill bundled into `kronos-search`,
and the `similar` identity-check name correction. The load-bearing no-mutation proofs
are: **no UCPath transaction exists** (`clickSaveAndSubmit` never called → no
`transactionNumber`, no UCPath-submitted screenshot) and **the Kuali document is
never finalized** (`runKualiFinalize` skipped). Live mode (no `dryRun`) is
unchanged.

Dashboard exposure: separations is a dashboard **input-run** start surface
(`INPUT_RUN_REGISTRY`, `supportsDryRun: true`) — typed doc id(s), comma-separated
→ sequential batch — with a per-page-load dry-run toggle in the input panel's
run-settings gear that folds `dryRun: true` onto each enqueued docId.
