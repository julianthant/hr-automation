# Onboarding Workflow

Automates full UC employee hiring: extracts data from ACT CRM, validates with Zod, searches UCPath for duplicates, searches I9 before creating a profile, creates Smart HR transactions.

**Kernel-based (daemon mode default).** Each alive daemon is one long-lived single-worker Session (3 browsers: CRM + UCPath + I9; **3 Duos** — I-9 became a UCSD SSO + Duo flow via the UCOP portal on 2026-07-01) that claims emails from the shared SQLite `tasks` queue via an atomic transaction. `.tracker/daemons/onboarding.queue.jsonl` is append-only audit/history — not read for state (queue authority is SQLite). The public start path is the dashboard input run (`DASHBOARD_INPUT_RUN_WORKFLOWS` + `INPUT_RUN_REGISTRY`); there is no package-script launch path.

The kernel owns browser launch, auth chain, per-item `withTrackedWorkflow` wrapping, SIGINT cleanup, screenshot on failure. Daemon mode wraps the same `runOneItem` primitive — per-item tracker output is byte-identical to single-mode `runWorkflow`.

## Retry safety

**Duplicate-hire probe (2026-07-01 — the idempotency gap is now CLOSED).** Contract 2 makes retry a uniform kernel behavior: a retry re-runs the handler from step 0 with the pristine original input, so the `transaction` step's UCPath Smart HR submit could fire twice if the first run succeeded server-side but failed before writing the terminal tracker row (network blip after submit). The retry re-reaches the transaction step because person-search still returns "new hire" — an *unprocessed* Smart HR hire creates no searchable person record yet.

The fix lives in this workflow (not the kernel): the `transaction` step now probes the UCPath Smart HR list for an existing in-flight HIRE before re-submitting, via `findExistingHireTransaction` (`src/systems/ucpath/ss-smart-hr.ts`). It runs **after the dry-run guard, before `buildTransactionPlan(...).execute()`**. If (and only if) a HIGH-CONFIDENCE duplicate is found it logs, stamps `status: "Already Submitted"` + `existingHireTxn`, screenshots `onboarding-existing-hire-transaction`, and RETURNS without submitting. Mirrors separations' effdt-gated `findExistingTerminationTransaction`.

- **Keyed by NAME, not EID.** A brand-new hire has no Empl ID (the Person ID column renders "NEW" until the transaction processes), so the probe searches the **SS Smart HR Transactions** page by the person's DISPLAY name (`buildHireSearchName` → **`"First Last"`, live-verified 2026-08-20** — every `Last,First` variant returned no rows, which is why the probe silently fell open from 2026-07-01 to 2026-08-20 and why the list was wrongly believed not to carry an unprocessed hire: `Hao Sun` returns `T002216675 HIR Pending`). A **single** match auto-opens the Transaction Details page instead of the grid; `readSsSmartHrSearchOutcome` detects that (Transaction ID span) and reads txn/status/`Effdt:`/action straight off it (`detailPageEffdt`, `detailPageHireAction`, unit-pinned on live page text); the grid path is unchanged and matches a `HIR`/`REH` action via the pure `pickHireRow`.
- **HIGH-CONFIDENCE gate (2026-07-01 — READ THIS).** A NAME search is a PeopleSoft **begins-with** match, so it can return a DIFFERENT same-named person's hire row — name + hire-action alone was NOT enough (it silently skipped legit hires on the FIRST run, and it skipped even when the prior hire was Denied/Error/Pushed Back and needed resubmitting). `found:true` now requires ALL of, via the pure `decideHireDuplicateSkip`: (a) a HIR/REH row; (b) an **in-flight/approved** approval status (`Pending`/`Approved`/`Manually Processed` — `isHireInFlightStatus`; a terminal-failed hire must be resubmitted, so it never trips the skip); (c) the hire's **effective date matches this run's `data.effectiveDate` EXACTLY** — read by drilling the row into Transaction Details (`readHireEffectiveDate`, mirroring separations' `readTerminationEffectiveDate`, reusing the live-verified `ssSmartHRTransactions.transactionResultRow` drill-in + `Effdt:` read) and compared with the pure `hireEffectiveDateMatches`.
- **Fail-open on uncertainty → SUBMIT.** A probe navigation/parse failure, an empty name, an unreadable effdt, a non-matching effdt, or a terminal-failed status all degrade to `found:false` → we submit. This is irreversible hire logic: a false SKIP (never hiring the real person) is worse than the probe-guarded double-submit risk, so any uncertainty resolves to "submit," never "skip."
- **The results grid exposes no effdt/template column** (the effdt comes from the drill-in, not the grid); `TEMPLATE_ID` is carried into the audit log only. **LIVE-VERIFIED 2026-08-20** (`generated/.scratch/probe-live.ts` against real names): `Hao Sun` effdt 09/11/2026 → `found T002216675 Pending` (grid path); `Ali Alnasser` → `T002214646 Approved` and `Emily Robles` → `T002216676 Pending` (single-match detail-page path, `Effdt: 2026-09-11`); `Hao Sun` with effdt 10/01/2026 → not found; an unknown name → none. `readSubmittedHireReceipt` verified the same way (both paths).

`supportsRetry` flags / structured "not retryable" errors remain out of scope — idempotency belongs in the workflow, and this probe is it.

## Submit-time "Person Match Found" page + operator-reviewed `notMatchEids` (2026-08-20 — READ THIS)

Save and Submit can land on PeopleSoft's OWN Search/Match review page — **"Person Match Found"**, a "Possible Person Matches" grid (Person ID, Legal First/Last Name, masked National ID, masked DOB, Gender) with a Select button per row and **"Not a Match - Continue with Hire" / "Save for Later" / "Cancel"** — instead of the confirmation dialog, whenever the hire's name/DOB/SSN resembles an existing person. Until 2026-08-20 the automation watched only the error banner and the confirmation OK, so a submit that reached this page **timed out blind** ("Save and Submit timed out with no error banner and no confirmation OK dialog") and the hire never filed (live: Hao Sun — 10 same-surname candidates; Emily Robles — one namesake with a different SSN + DOB). Nothing is persisted on that page (no Transactions-in-Progress row afterwards), so a re-run recreates the transaction.

`clickSaveAndSubmit` now polls three signals (`classifySubmitSignals`: error banner → Person Match heading → confirmation OK), reads the grid by HEADER text (`readPersonMatchCandidates`, throws if unreadable — never "no candidates"), and decides with the pure, unit-pinned `decidePersonMatchContinue(candidates, hireIdentity, notMatchEids)`:

- **Proceed (click "Not a Match - Continue with Hire") ONLY if every candidate is excluded** by (1) a **hard identifier known on both sides that differs** — DOB month/day (UCPath masks the year) or SSN last-4 (`candidateExcludedByHardIdentifier`; a NAME is never evidence — Search/Match is fuzzy on names by design) — or (2) the operator having **reviewed that exact Person ID** (`notMatchEids`). Unknown on either side (blank DOB / `*****XXXX` / a no-SSN hire) ⇒ not excluded.
- **Otherwise fail loud**: `TransactionResult { success:false, error }` whose message lists the unresolved candidates and the exact `prefilledData.notMatchEids="…"` to re-run with; the run ends `Failed` with that text in `transactionError`. Review each EID in Person Org Summary; if one IS the person, it is a rehire — do not file.
- `hireIdentity` = the hire's REAL SSN last-4 (`ssnLast4(ssnForUcpathEntry(data.ssn))` — none for a 900-999 placeholder) + CRM DOB, threaded by `buildTransactionPlan(..., { notMatchEids })` → `clickSaveAndSubmit(…, { hireIdentity, notMatchEids })`. Separations/EID-bearing callers pass neither ⇒ any Person Match page fails loud there.

**`data.notMatchEids` (operator channel, `prefilledData`)** — comma-separated UCPath EIDs the operator has reviewed and confirmed are **NOT** this hire (`parseEidList`, strict: a token must BE an 8-digit `10…` EID). Supplied via `POST /api/run-with-data { workflow:"onboarding", id:<email>, runId, data:{ notMatchEids:"10416504,10743545" } }` (re-enqueues the original input with the channel) or `/api/enqueue` `inputs:[{ email, prefilledData:{ notMatchEids } }]`. It is consulted at BOTH wrong-person gates and is **exact-EID scoped** (an EID not in the list never gets a pass):

1. **person-search identity gate** — a `different`-name Search/Match hit whose EVERY matched EID is in the list **proceeds as a NEW hire** (stamps `personSearchOverride: "not-this-person:<eids>"`) instead of re-pausing. Needed because HR-Tasks Search/Match keys on DOB with fuzzy first names and ignores the surname (`src/systems/ucpath/LESSONS.md` 2026-08-06), so the same false match recurs on every plain re-run — dismissing the review card alone only stamps the row (2026-08-20: Mia Perez→Mia McKrell 10871985, Juliana Romano→Julian Davey 10884140, Maria Renee Santos→Mariana Herrera 10769454). `eidApproved` (approve = IS a rehire) and `notMatchEids` (dismiss = is NOT) are the two halves of the review decision.
2. **submit-time Person Match page** — as above.

## Post-submit receipt (2026-08-04 — success is proved by the PAIR)

A `T…` transaction NUMBER is issued regardless of outcome — live `T002204014` is **Denied** and carries a well-formed number — so the number ALONE never proves a successful submit. The `transaction` step now reads the receipt PAIR `(transactionNumber, approvalStatus)` and classifies it with the pure `interpretPostSubmitTxnReadback` (`src/systems/ucpath/transaction.ts`, unit-pinned).

- **A dedicated reader, NOT the duplicate guard.** The readback uses `readSubmittedHireReceipt` (`ss-smart-hr.ts`), not `findExistingHireTransaction`. The two are inverses: the pre-submit guard must fail OPEN and therefore only ever reports an in-flight/approved hire, so reusing it made a REFUSED hire indistinguishable from "the number could not be read" — the operator was told to look up a number for a transaction UCPath had rejected. The receipt reader reports whatever status the receipt carries, still effdt-gated to THIS run exactly (a begins-with name search can return a different same-named person's hire).
- **Four outcomes, four tracker rows.** `accepted` (`Approved`/`Manually Processed`) → `status: "Done"`. `pending` (`Pending` — the normal state right after a submit, awaiting an approver) → `status: "Pending Approval"`, a legitimate intermediate that is neither success nor failure. `refused` (`Denied`/`Error`/`Pushed Back`/…) → `status: "Transaction Refused"` + `transactionRefused`, number stamped for the audit trail only. `unknown` (no readable number → `submittedWithoutTxnNumber`; or a number with a blank/unrecognized status → `transactionReceiptUnverified`) → `status: "Needs Review"`. Every non-`Done` branch logs and screenshots. `transactionApprovalStatus` is stamped on all of them.
- **An unreadable status is NEVER "assume approved."** Only positively recognized statuses classify; everything else stays `unknown`.
- **No branch throws.** The hire IS already submitted by the time the receipt is read, and failing the run would invite a retry whose fail-open duplicate probe could file a DUPLICATE hire. Loudness lives in the tracker row + screenshot, not an exception.
- **The detail page's own identity must be asserted.** An UNKNOWN transaction id renders the ordinary SS Smart HR search form with NO error and NO banner, and the bare route URL is byte-identical after a reload — so neither "the page loaded" nor the URL is state evidence. `receiptMatchesRequestedTransaction` (pure, unit-pinned) requires the Transaction ID span to have RESOLVED and to equal the requested id.

## Gotchas

- SSN/DOB are optional (international students) but wage requires `$` prefix
- Appointment field: extracts just the number from "Casual/Restricted 5" → `"5"`
- Department number parsed from parenthesized text: `"Computer Science (000412)"` → `"000412"`
- **Documents land as a plain folder per hire inside a per-day folder: `data/onboarding/<YYYY-MM-DD>/<Last, First Middle EID>/` (local date of the run; `buildCrmDocumentDownloadPath` + `onboardingDateFolder`). No zip (operator decision 2026-08-20 — "group them by date so I can see which were done today"; the 2026-08-18 one-zip-per-person layout is retired, `zipCrmDocumentFolder` is no longer called by onboarding). The "already done" check honours a legacy sibling `.zip` too. `data.pdfArchive`/`pdfFolder` both carry the folder path.**
- PDF downloads run **in-process** against the already-authenticated CRM page (`pdf-download` step), not delegated to `crm-doc-download` — delegating would force a fresh CRM Duo + extra Chromium launch (~30–90 s) per item since the onboarding daemon's CRM session cannot be shared across daemons. The standalone `crm-doc-download` daemon exists for explicit CLI use only. Failed download is non-fatal; UCPath/I-9 continue.
- I-9 creation requires SSN, DOB, and departmentNumber — the workflow throws a clear error if any is missing for non-rehires
- **Expected Job End Date is EXTRACTED FROM CRM** (`expectedJobEndDate`, UCPath Entry Sheet label "Expected Job End Date (if applicable)") — it is a per-hire value, not a per-fiscal-year constant. `ANNUAL_DATES.jobEndDate` (`06/30/2027`, env `ANNUAL_DATES_END`, re-exported as `JOB_END_DATE`) is only the fallback for a record where CRM left it blank. **A stale value is not cosmetic:** UCPath rejects the whole transaction with a BLOCKING modal, "Expected Job End Date cannot be before Job Effective Date", which the automation used to acknowledge as if it were the submit confirmation — so the hire silently never filed and the page stayed at `Transaction ID: NEW` (live 2026-08-18, effdt 09/11/2026 vs a 06/30/2026 default). `buildTransactionPlan` now refuses to build a plan whose end date precedes the effective date (`isOnOrAfter`), and `clickSaveAndSubmit` reads the dialog text and throws on a refusal instead of clicking past it
- Rehire short-circuit (**new-hire mode only** — in Rehire mode the match is the expected path, see "Rehire mode" above): if `searchPerson` returns a match, the workflow records `rehire: "Yes"` + existing EIDs and exits before I-9/transaction. `searchPerson` classifies new-hire-vs-rehire by RACING the confirmation dialog against the results grid (2026-07-01) — it no longer samples a single early dialog probe that could misread a rehire as a new hire (→ duplicate person)
- Triple-browser setup (single mode): CRM page, UCPath page, I-9 page. All three need Duo — I-9 authenticates via UCSD Shibboleth SSO + Duo through the UCOP portal (2026-07-01), reusing the same UCSD (UCPath) credentials
- No Excel tracker — all observability flows through the dashboard JSONL. Run `npm run dashboard` in a separate terminal to watch

## Dry-run boundary

`OnboardingInputSchema` carries an optional `dryRun` flag (mirrors oath-signature / emergency-contact). When set, the handler completes CRM extraction and UCPath person search, then captures `onboarding-dry-run-before-writes`, stamps `status: "Dry Run Complete"` + `dryRun: true` + `i9ProfileId: "Not created — dry run"`, and returns **before the entire `i9-creation` step**. The later Smart HR `transaction` step is therefore unreachable too.

The invariant is strict: **dry run writes to no system of record at all.** CRM auth/search/extraction, iDocs PDF download (a read-only GET to local disk), UCPath person search, and the identity-approval comparison still run. I-9 search and creation currently share one step, so both stay below the boundary; a rehearsal neither creates an I-9 profile nor enters the Smart HR transaction. Live mode (no `dryRun`) is unchanged, including search-first/single-attempt I-9 creation.

Dashboard exposure: onboarding is a dashboard **input-run** start surface (`DASHBOARD_INPUT_RUN_WORKFLOWS` + `INPUT_RUN_REGISTRY`) — typed email(s), comma-separated → a `pool` batch — with a per-page-load dry-run toggle in the input panel's run-settings gear (folds `dryRun: true` onto each enqueued input).

## Rehire mode — UC_CONC_HIRE concurrent hire on an existing Empl ID, no I-9 (2026-08-21 — READ THIS)

The onboarding input panel's **run-settings gear** (beside Workers / Dry run) has a **Hire type** radio section (`INPUT_RUN_REGISTRY.onboarding.modes` with `modesPlacement: "run-settings"` — operator ask 2026-08-21: no extra row above the text box): **New hire** | **Rehire**, folded onto every input as `mode: "new-hire" | "rehire"` (`OnboardingInputSchema.mode`, optional ⇒ new-hire). The same daemon/handler serves both; the row stamps `hireMode` (detail field "Hire type").

The single/approved EID becomes `rehireEmplId` (`data.emplId`). **The `i9-creation` step is skipped entirely** (`i9ProfileId: "N/A (rehire — no I-9)"`; operator rule: "the rehire does not need the i9"). ## Identity-approval gate (2026-07-08 — READ THIS)

Onboarding adopts the shared **identity-approval** pause-on-mismatch gate (extracted from separations — `src/domain/identity-approval.ts`). It lives in the `person-search` handling of the `searchResult.found` (rehire) branch:

- **When it pauses:** person-search matched an existing UCPath person by SSN/DOB/name, but that matched person's name is a **`different`** tier vs the CRM-extracted name (`classifyNameSimilarity`, the SAME order-insensitive confidence separations trusts). A `different` name means the SSN/name search resolved a **different person** (an SSN typo / collision); blindly recording their EID as this person's rehire (or acting on it downstream) is the wrong-person risk. `same`/`similar` tiers proceed as a genuine rehire, unchanged.
- **Pause mechanics:** stamps `buildIdentityApprovalPauseData({ original, proposed })` — `original` = the CRM person (no UCPath EID → `found:false`, so the review card's "Use this EID" is disabled for it), `proposed` = the UCPath match (`emplId` + name) — then `return`s. The run ends `done`; the shared `EidApprovalBanner` renders (LogPanel gates on `data.eidApproval==="pending"`) and the row shows the amber "Awaiting Approval" badge (`statusExtensions: identityApprovalStatusExtensions`, registered in `queue-row-status-index.ts`).
- **Approve/dismiss:** the generic `/api/eid-approval/{approve,dismiss}` routes (onboarding is in `EID_APPROVAL_WORKFLOWS`). Approve re-enqueues the email carrying `prefilledData.eidApproved`; the handler reads `ctx.data.eidApproved` at entry (`eidPreApproved`) and **skips the gate** so an approved re-run never re-pauses.
- **Not this person (2026-08-20):** the review card also offers **"Not this person — run as new hire"** (onboarding only, `NOT_THIS_PERSON_WORKFLOWS`) → `POST /api/eid-approval/not-this-person { workflow, id, runId, eid: proposedEid }` (`buildNotThisPersonHandler`): re-enqueues the original input with `prefilledData.notMatchEids` = prior list ∪ the reviewed EID (`mergeNotMatchEids`) and stamps the paused row dismissed. That is how the operator answers a DOB-keyed false match without curl; plain Dismiss only stamps the row and a bare re-run re-pauses on the same hit.
- **Orthogonal to the duplicate-HIRE probe (2026-07-01):** that guards the new-hire *submit* path (double-submit idempotency, `findExistingHireTransaction`); this guards the *rehire-match* path (wrong-person identity). No overlap — different branch, different failure mode.
- **dry-run unaffected:** the gate is a read/comparison and fires regardless of `dryRun` (surfacing a real mismatch is the point of a dry run); after a no-match result, the dry-run terminal stops before I-9 creation.
- Verified headless (seeded onboarding `eidApproval:"pending"` fixture → real `dashboard:prod`): the row shows "Awaiting Approval", the banner renders both candidates (original "not found in UCPath" / disabled, proposed enabled), and "Use this EID" POSTs `/api/eid-approval/approve` — `.screenshots/eid-approval-onboarding/01-banner.png`.

## Lessons Learned

- **2026-08-21: Rehire mode = UC_CONC_HIRE concurrent hire, no I-9.** Hire type is a dashboard mode picker (`mode` schema field), not a gear preset — the operator sees "New hire | Rehire" on the panel. Rehires go through the same daemon; only person-search semantics (match REQUIRED), the skipped I-9 step, and the transaction plan differ. Wrong-person guards are name READBACKS at two points (Enter Transaction Details + Personal Data legal name), because UCPath resolves a name for any real EID. See the "Rehire mode" section.
- **Lesson maintenance rule:** Search this section plus CRM/UCPath/I9 system docs before adding onboarding lessons. Merge old retry/kernel/selector notes into the current daemon + kernel model instead of preserving obsolete `retryStep` history.
- **2026-08-20: Documents are per-day folders, not zips.** `data/onboarding/<YYYY-MM-DD>/<Last, First Middle EID>/` — the operator reads the directory by day ("which were done today"); existing 08-18/08-20 archives were unzipped into that layout the same day. `crm-doc-download` (CLI-only) still packs its own run archive — separate workflow, untouched.
- **2026-08-20: Submit-time "Person Match Found" page was invisible to the automation.** Two live submits (Emily Robles, Hao Sun) timed out blind because Save and Submit landed on PeopleSoft's Search/Match review page, which the outcome poll did not watch. Now a named third signal; continue only when every candidate is excluded by a hard identifier or an operator-reviewed EID (`notMatchEids`), else fail loud with the candidate table. See the section above; live root-cause screenshots: `.tracker/screenshots/onboarding-*-error-transaction-ucpath-17872471*.png`.
- **2026-07-28: Dry-run stops before I-9 creation.** This supersedes the 2026-06-17/2026-07-16 boundary. A rehearsal may read CRM and UCPath, but it never enters the combined I-9 search/create step and never enters Smart HR. `tests/unit/workflows/onboarding/workflow.test.ts` pins the boundary before both write sites.
- **No tracker-side cache/idempotency — the duplicate guard is a LIVE probe.** CRM extraction re-scrapes on retry. The UCPath Smart HR submit's duplicate guard is a **live** SS-Smart-HR transaction-list probe (`findExistingHireTransaction`, added 2026-07-01 — see "Retry safety" above), like separations. Do NOT restore `stepCacheGet`, `hasRecentlySucceeded`, or `recordSuccess`.
- **2026-07-01: Three hardening fixes against retry/flakiness defects (all with unit-pinned pure cores).** (1) **Duplicate-hire probe** — `transaction` step calls `findExistingHireTransaction` before `buildTransactionPlan(...).execute()`; if a HIGH-CONFIDENCE duplicate hire exists on the SS Smart HR list for the person (searched by name — new hires have no EID) it stamps `status: "Already Submitted"` and skips the submit. **High-confidence = HIR/REH + in-flight/approved status (`Pending`/`Approved`/`Manually Processed`) + effdt matching this run EXACTLY** (the effdt read by drilling the row → Transaction Details, mirroring separations). Name+action alone was a bug — a begins-with name search matched a DIFFERENT same-named person's stale hire → silently skipped a legit hire on the first run, and a Denied/Error/Pushed-Back hire (needing resubmit) also tripped the skip. Fail-open on any uncertainty → SUBMIT (a false skip never hires the real person, worse than the guarded double-submit). Pure `pickHireRow`/`buildHireSearchName`/`isHireInFlightStatus`/`hireEffectiveDateMatches`/`decideHireDuplicateSkip` in `ss-smart-hr.ts`, pinned by `ss-smart-hr.test.ts`. (2) **person-search classification race** — `searchPerson` (`ucpath/navigate.ts`) now RACES {results grid} vs {#ICOK confirmation dialog} and classifies only once one is present, instead of a single early `dismissPeopleSoftDialog` probe that could misclassify a real rehire as a new hire → duplicate person. Pure `classifyPersonSearchSignal`, pinned by `navigate.test.ts`. (3) **submit outcome verification** — `clickCreateTransaction`/`clickSaveAndSubmit` (`ucpath/transaction.ts`) wait for a DEFINITIVE outcome (error banner OR success marker) via `waitForTransactionOutcome` instead of reading `errorBanner.count()` once after a fixed sleep (a late banner read 0 → false success). Pure `classifyOutcomeSignals`, pinned by `transaction.test.ts`. **NEEDS LIVE VERIFY:** SS Smart HR name search returns a pending hire (`Last,First` key); the reason-code dropdown (create) and confirmation-OK (submit) are reliable success markers on the live pages.
- **2026-05-25 / 2026-06-17: Public start path is the dashboard input run.** `npm run onboarding` is retired. The dashboard input run (`DASHBOARD_INPUT_RUN_WORKFLOWS` + `INPUT_RUN_REGISTRY`) was added 2026-06-17 (typed emails, comma-separated → pool batch, with per-page dry-run toggle). Do not re-expose this workflow through package scripts.
