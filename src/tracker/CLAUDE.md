# Tracker Module

JSONL + SQLite projection for workflow observability. Workflow handlers should use `ctx.step`, `ctx.markStep`, and `ctx.updateData`; they should not call tracker primitives directly.

## Directory layout (`.tracker/`)

`src/tracker/paths.ts` is the **single source of truth** for every path under the tracker dir. Never build a `join(trackerDir, ...)` path inline — add a helper there instead.

```
.tracker/
├── state.db (+ -wal, -shm)        SQLite live truth (root; see state/db.ts)
├── rows/      <workflow>-<date>.jsonl   tracker / queue rows
├── logs/      <workflow>-<date>.jsonl   operator log lines (NOTE: no "-logs" suffix)
├── sessions/  <date>.jsonl              session events (NOTE: no "sessions-" prefix)
├── runtime/   rotation-state-*.json     runtime state (OCR key rotation, …)
├── daemons/   <workflow>-<ISO>.log + *.queue.jsonl + *.lock.json
├── debug/     row-lifecycle-<date>.{json,jsonl}
├── pdf-cache/ , uploads/ , captures/   artifacts (captures/ = per-session mobile-capture photos)
├── screenshots/  *.png                 operator audit screenshots (PATHS.screenshotDir)
├── sharepoint/   *.xlsx                 SharePoint roster downloads (sharepoint-download)
├── rosters/      *.xlsx                 emergency-contact pre-flight roster downloads
└── e2e-gates/    *.hold                 HRAUTO_E2E_STUBS hold gates (src/core/e2e/gates.ts)
```

Row **kind is the directory**, not a filename suffix: a `rows/` file and a `logs/` file share the identical `<workflow>-<date>.jsonl` name. Classify by `trackerKindForPath(path)` (parent-dir segment), never by `.endsWith("-logs.jsonl")` or a `sessions-` prefix. Helpers: `rowFilePath` / `logFilePath` / `sessionFilePath` / `runtimeFilePath`, the `*Dir` accessors, and `parseWorkflowDateFilename` / `parseSessionFilename`. All are re-exported from the `jsonl.ts` barrel.

## Row Emission

- New persisted rows go through `emitTrackerRow` in `jsonl-io.ts`.
- Every row must carry `data.archetype`; TypeScript and architecture guards enforce this.
- Workflow rows use `stampArchetypeForRow(data, { workflowArchetype, parentRunId })`.
- `parentRunId` means delegated scope only. It does not change row shape.
- Control-layer replacement rows must inherit archetype and display metadata through `src/control/ops/emit-inherited.ts`.
- `trackEvent` / `trackEventForDate` are deprecated shims kept only for tracker internals and synchronous SIGINT paths.
- **Writers always append at "now" (`emitTrackerRow` → today's partition).** Cross-midnight is solved at the READ layer, not by anchoring writes to a run's origin date — see the cross-midnight lesson. The one deliberate exception is `emitTrackerRowForDate`, used **only** by the save-data overlay (`buildSaveDataHandler`) to land an edit on the same partition as the *terminal* row it overlays; do not "unify" it with the read-layer merge (that merge covers open runs only).

## Live State

- SQLite is live queue/control truth: tasks, attempts, worker heartbeats, commands, browser processes, dependency rows, and projection tables.
- JSONL is append-only audit/history and dashboard visibility. `.tracker/daemons/*.queue.jsonl` is tail/debug output, not queue state.
- Queue/control changes must update SQLite and write expected JSONL audit rows together.
- `watchChildRuns` remains fallback for legacy rows with no SQLite task/dependency records.

## Dashboard Observability

Rows should prefer structured operator subjects over raw ids: `data.__subject`, `data.__subjectKind`, task role/group fields, and structured log fields like `category`, `occasion`, `system`, `step`, `attempt`, `durationMs`, or `childWorkflow`.

`parentRunId` is for dashboard parent/child visualization. Child watching is itemId/dependency based, not parentRunId based.

Failure-pattern scans run from the dashboard server on a short interval, prefer SQLite projection data when ready, and fall back to JSONL scans only when necessary. Notification errors must not stall dashboard streaming.

Workflow rail badge counts (`wfCounts`) are a backend contract, not a React override. Build them from tracker history with `countSidebarRowsFromTrackerHistory(asTracker)` so latest rows, carried EIDs, employee merges, and top-level queue-surface/delegation collapse stay consistent across SQLite and JSONL fallback. Do not prefilter latest rows with `resolved_prep = 0`; the exclusion callback defaults to no-op and owns any count exclusions. Resolved OCR prep rows that still render in the queue must remain in `wfCounts`.

Full reference: `docs/engineering/tracker-reference.md`.

## Gotchas

- ExcelJS loses column key mappings after `readFile()`; reapply keys before `addRow(data)`.
- Tracker filenames, Excel tabs, dashboard date selection, and historical JSONL tests use local-calendar `YYYY-MM-DD`.
- Tracker `.xlsx` files belong under the owning workflow, never project root.
- Port 3838 conflicts should log and skip server start.
- Use both `withLogContext` and `withTrackedWorkflow`; neither replaces the other.
- Do not resurrect `markStaleRunningEntries`; long Duo/Kronos waits can look stale but be valid.
- SIGINT writes must be synchronous because `process.exit` follows immediately.
- Do not wrap synchronous append calls in async mutexes; `appendFileSync` with `O_APPEND` provides the read-after-write behavior tests rely on.
- `emitStepChange` must ALWAYS emit — never dedup it against step logs. It is the only carrier of a daemon's live `currentStep` (`rebuildSessionState` reads nothing else). A prior 50ms "skip if a recent `step:start` log exists" guard silently broke the session card: `Stepper.announce` writes that log immediately before calling `emitStepChange`, so the guard matched every `ctx.step` and `currentStep` stayed null. Dedup the resulting duplicate log/event lines at render time (dashboard `mergeDisplayItems`), not at emit time.
- **2026-06-06: A restart sweep that fails a stuck row MUST carry the row's reached `step` (`...(e.step ? { step: e.step } : {})`).** `step` is a top-level row field, not part of `data`, so spreading `e.data` does not preserve it. `sweepStuckOcrRows` (`dashboard/ocr/sweep.ts`) dropped it and `sweepStuckOathUploadRows` (`dashboard/oath-upload/http.ts`) stamped a `step: "swept"` sentinel — both left the failed row with a step the registry can't resolve. `/api/runs` then reports the run's step as the latest row's `latest_step` (null/unmatched), and the dashboard `StepPipeline` (`computeStepViews`) takes its "failed + unknown step → step 0" fallback, so the timeline marks the failure on the FIRST step (`loading-roster`) regardless of where the run actually was — and the "Dashboard restarted while OCR was in progress" message contradicts the highlighted chip. Fix: preserve `e.step`; a genuinely step-less row (still `pending`) keeps the step-0 fallback correctly. The fallback itself is right — it exists for crashes that died before emitting any `running` step; the sweep just has to stop throwing the step away. Pinned by `ocr-http.test.ts` + `oath-upload-http.test.ts` (running row preserves step, step-less row omits it).

## Adding Tracking

Kernel workflows get tracking for free through `defineWorkflow` + the kernel runners. No non-kernel workflows currently ship under `src/workflows/*`; use `defineWorkflow` for new work.

## Lessons Learned

- **Lesson maintenance rule:** Merge stale tracker lessons into current rules instead of appending another dated variant.
- **2026-06-19: A handler-thrown cancel must carry a cancel SENTINEL step so the terminal row classifies as Cancelled, not Failed (ISS-007).** When an oath-upload ticket is killed by an upstream OCR **discard**, the controller is NOT aborted (the discard route leaves the task to self-unwind via the approval signal), so the kernel's own cancel path never stamps a sentinel — the row froze on its in-flight `lastStep` (`wait-approval`) and `statusKeyForEntry` rendered red **Failed**, while a directly-cancelled ticket (`step=cancelled`) renders orange **Cancelled**. Fix: the oath-upload handler now throws `CancelledError("discarded")` (a cancel sentinel as `stepName`, `cause` = the discard reason) instead of a plain Error, and `withTrackedWorkflow`'s catch honors a carried `cancelled`/`discarded` sentinel as the **terminal step** (`cancelSentinel ?? lastStep`) on both the `run:terminal` log and the `emit("failed", …)`. Same family as the 2026-06-06 sweep-step and 2026-06-19 ISS-006 lessons (a terminal row must carry a step the dashboard/status resolver can classify). The OCR delegated cancel (`CancelledError("awaiting-approval")`) is unaffected — its terminal row is suppressed on the daemon path. Pinned by `tests/unit/core/run-one-item.test.ts` (sentinel-step terminalization) + `tests/unit/workflows/oath-upload/handler.test.ts` (discard → CancelledError("discarded")).
- **2026-06-19: A terminal/failure row that re-emits must INHERIT the prior row's display metadata, never re-stamp a bare `data: { archetype: … }` (ISS-006).** The `approve-batch` dispatch-failure path (`dashboard/ocr/approve.ts`) emitted `emitTrackerRow({ …, status:"failed", step:"approve-failed", data:{ archetype:"preview" } })`. Latest-wins dedup then ate the prior OCR row's `__traceId`/`queueRowKind`/`pdfOriginalName`/`formType`, so the failed row rendered as a cryptic "`<sessionId>` — failed" with no title/trace AND severed the delegation-trace lineage through that node (the e2e auditor found it was the ONLY field-loss point in the whole run, and all broken lineage links traced to it). Same family as the 2026-06-06 sweep-step lesson (a failed row must carry fields the dashboard can resolve). Fix: emit via `emitInheritedRow` (`src/control/ops/emit-inherited.ts`) — it looks up the prior row and inherits archetype + display metadata, applying only the emit-side `status`/`step`/`error`. Keep a bare-emit fallback for the no-prior-row case. Pinned by `tests/unit/tracker/dashboard/ocr-approve-preserves-name.test.ts` (approve-batch failure preserves identity).
- **2026-06-17: `findLatestEntryForPredicate`'s SQLite fast path must reconstruct `parentRunId`, or bulk cancel/retry/discard orphans batch/operation members.** The runs/items fast path rebuilt a `TrackerEntry` from `latest_data_json` etc. but never `SELECT`ed `parent_run_id`, so the reconstructed entry had no `parentRunId`. Bulk ops pass `db`, so `emitInheritedRow`'s `args.parentRunId ?? priorEntry.parentRunId` resolved to `undefined` and the re-emitted (cancel/retry/discard) JSONL row dropped `parentRunId` — while `data.archetype` survived (it rides `latest_data_json`). For a **synthetic** batch anchor (a multi-id input run — the anchor is derived purely from members sharing a `parentRunId`, there is no real `archetype:"batch"` row), every member losing its parent made the anchor evaporate and each member fall through to a standalone `single` surface ("cancel all → batch row disappears, members show as normal rows"; same defect as e2e VQ-001/AUD-C1 on oath-signature). Note the `runs` table COALESCE-preserves `parent_run_id` (`apply.ts`), so the bug surfaces via the JSONL audit row + per-event `run_events` (latest-wins), not via the `runs` projection — which is why a SQLite-`runs`-only check would have missed it. Fix: `find-latest-entry.ts` now selects `parent_run_id` in the runs branch and recovers it via a correlated subquery on `runs.latest_run_id` in the items branch (the `items` table has no `parent_run_id` column). Pinned by `latest-entry-predicate.test.ts` (both branches) + `emit-inherited-db-hint.test.ts` (cancel row keeps parentRunId end-to-end). Precedent that already selected it: `entries-payload.ts`, `ocr/retry-page.ts`.
- **2026-06-13: Row-lifecycle-debug attributes a same-runId re-pend as `cause:"reassign"`, distinct from `"retry"` (VL-004).** A per-instance daemon stop (or dead-worker recovery) un-claims an in-flight item via `returnTaskToQueued`, which re-emits a `pending` row under the SAME runId (running→pending, or failed→pending), then a peer finishes it. The lifecycle-debug cause derivation only knew `"retry"` (a re-pend under a NEW runId), so the reassign transition showed `cause=None`. Now a `pending` whose `runId === currentRunId` AND whose `prev.status !== "pending"` is attributed `"reassign"` (checked AFTER the retry branch, which requires a new runId). Derivation-ONLY — no change to the emitted rows (the lifecycle debug is observational, replays JSONL, and must not mutate classification inputs); `RowCause`/`RowEventType` gained `"reassign"`, and the post-terminal-surface-change flag excludes it (the cause already explains the failed→pending flip). Pinned by `row-lifecycle-debug.test.ts`.
- **2026-06-11: OCR operator-trigger HTTP handlers share `buildOcrTriggerHandler` (BM-6, `dashboard/ocr/trigger-handler.ts`).** `force-research`, `verify-relookup`, and `retry-page` were all "validate → (test-seam override? : dynamic import) → try/catch → respond" — the first two near byte-identical; retry-page adds a per-row lock + a `RetryPageError` code→status map. The factory unifies validate + the test-override dual-path + try/catch + optional lock (with `finally` release) + error mapping; each handler now supplies only its `validate`, `run` (dynamic-import target), `onSuccess`/`onError` body builders, and optionally `mapError` (retry-page: `image-missing`→410 / `row-not-found`→404 / `row-not-mutable`→409, else log + fall through to 400) + `lock` (retry-page's `rowKey` mutex → 409 "already in progress"). The test-seam override (`triggerForceResearch`/`triggerVerifyRelookup`/`runRetryPageOverride`) is spread onto the spec as `override` only when present, so the dual-path is gone. Pinned by `ocr-trigger-handler.test.ts` (validate/override/mapError-fallthrough/lock-release) + the unchanged `ocr-http.test.ts` (the handlers' 200/400/409/410 behavior).
- **2026-06-01: Every workflow needs an `INSTANCE_LABELS` entry (`session-events.ts`).** It maps workflow `name` ↔ session-drawer label both ways (`generateInstanceName` / `workflowNameFromInstance`). A workflow missing from it still launches a session row, but resolves to `workflow: null` — it shows up *unlabeled* in the terminal drawer ("shows up but not hooked in"). `crm-doc-download` was missing. The `tests/unit/architecture/instance-labels-coverage.test.ts` guard now fails loudly if any registered workflow lacks an entry (and checks the label round-trips) — add the new workflow's label there when scaffolding.
- **Projection writes fail loud and recover async.** JSONL writes first, then SQLite projection applies; repeated projection failures should schedule guarded rebuilds rather than block workflow hot paths.
- **DB handles are file-sensitive.** A live dashboard may outlast `.tracker/state.db` deletion/recreation; resolve DB handles at request/tick time.
- **JSONL readers validate at the boundary.** Use focused validators and preserve each caller's public no-match value.
- **Workflow actions are centralized in `src/control/`.** Dashboard routes should be thin wrappers over `performWorkflowAction`.
- **Queue surfaces classify shape x scope.** Use canonical row shape plus `parentRunId`, not legacy archetype strings.
- **OCR discard is a cancel variant.** Keep it routed through central cancel/control paths with OCR context.
- **Row lifecycle debug is observational only.** It replays JSONL and must not mutate classification inputs or become streamed state.
- **Caches are bounded and resettable.** Register test-visible caches in `__resetAllDashboardCachesForTests()`.
- **2026-06-01: `.tracker/` is split into typed subdirs; `paths.ts` owns all path construction.** Rows → `rows/`, logs → `logs/` (dropped the `-logs` suffix), sessions → `sessions/` (dropped the `sessions-` prefix), OCR rotation state → `runtime/`. `state.db` + `daemons/`/`debug/`/`pdf-cache/`/`uploads/` are unchanged. Kind is now conveyed by **directory** (`trackerKindForPath`), so the old suffix/prefix classification special-cases collapsed. `clean:tracker` now also prunes `daemons/*.log` (was unbounded — a fresh timestamped file per daemon launch) via `cleanOldDaemonLogs`. **Gotcha:** raw `appendFileSync`/`writeFileSync` in tests must `mkdirSync(rowsDir(dir)|logsDir(dir)|sessionsDir(dir), {recursive:true})` first — those fns don't create parent dirs (the production `appendJsonlWithSource` does). **Inventory gotcha:** the original touchpoint sweep missed a reader in `src/workflows/` — `oath-upload/duplicate-check.ts` scanned the flat dir; when restructuring tracker paths, grep `src/workflows/` and `src/domain/` too, not just `src/tracker/` + `src/control/`.
- **2026-06-06: Cross-midnight runs are forward-merged at the READ layer for EVERY date-scoped per-run reader (canonical model; centralized in `state/queries/cross-midnight.ts`).** Rows are partitioned by the local calendar day they are *written* (`tracker_date`), and so is the SQLite projection. A run that starts before local midnight but keeps emitting after it (a parked OCR review cancelled/approved next day, a long Duo wait, a multi-hour browser run) writes its later rows to a LATER partition. A reader scoped to the run's start day then misses them and shows the run **stuck at its last pre-midnight state** — classically "Running" with a live timer forever (repro: a standalone OCR `verify` review cancelled after midnight; the `failed/cancelled` row landed in tomorrow's `ocr-<date>.jsonl`). **Canonical fix = read-layer merge, not write-to-origin** (writers stay trivial: "always append now"; this also keeps live-monitoring of overnight runs and date-based retention/pruning correct, both of which a write-to-origin model breaks). For any run whose latest status on `@date` is non-terminal (still OPEN), pull its continuation rows from partitions in `(@date, @today]` (run_ids via `json_each`) and fold them in so the reader's latest-wins dedupe collapses the run to its real terminal state. The **OPEN gate + bounded window** is what makes a reused `run_id` (e.g. person-lookup's `itemId#1`) safe — a run already terminal on `@date` is excluded, so a later same-id run can't bleed backwards. No-op when viewing today (`@date >= today`) — a run can't continue into a partition before its start day — so the hot path stays free of the extra query. **Shared primitives** (`cross-midnight.ts`): `dateCanHaveContinuation`, `openRunIdsFromEvents`, `selectCrossMidnightEventRowsWithRuns` (runs-joined, for cards/summaries — continuation rows inherit the start-day `first_*`/`run_ordinal` so the elapsed span stays whole), `selectCrossMidnightRunEventRows` (plain `RunEventRow`), `selectCrossMidnightLogRowsForRun` (logs carry no status, so it probes `runs.latest_status` on `@date` to gate). **Readers wired:** the queue card (`queryEntriesPayload`), the RunSelector/run-detail summary (`queryRunsForItem`), the run-event timeline (`selectRunEventsForRun`), and the log panel (`selectLogsForRun`). Pinned in `state-queries.test.ts` (one cross-midnight merge + one reused-id guard per reader). **Deliberate, documented consequences (not bugs):** (1) a cross-midnight run appears on BOTH days' queues — its start day via the merge, its action day natively — correctly reflecting that the run touched both days; (2) `wfCounts`/`failureCounts` are per-day and NOT forward-merged: a genuine after-midnight *failure* tallies on the bell on its terminal day (so on the start day the card can read failed while the bell ticks the next day) — this avoids double-counting one failure across two days, and a *cancel* (`failed/cancelled`) is excluded from `computeFailureCounts` anyway; (3) a retry is a NEW run born at "now" (`emitInheritedRow` → today) and shows on the day it was launched, not the origin run's day.
- **2026-06-01: Artifact dirs (`screenshots`/`sharepoint`/`rosters`) moved under `.tracker/` and `paths.ts` now owns their construction too.** The old `src/data/` tree (roster `.xlsx` + an empty `screenshots/`) was retired — files live in `.tracker/sharepoint/`, and the `.gitignore` `src/data/*` block + the legacy `.screenshots/` entry were removed. `paths.ts` gained `screenshotsDir`/`sharepointDir`/`rostersDir` helpers; `config.ts` derives `PATHS.screenshotDir` from `screenshotsDir(".tracker")` (config now imports the pure leaf `tracker/paths.ts` — no cycle, paths.ts imports only `node:path`). `resolveRosterDirs` builds from the helpers, and three dashboard readers (`capture-state.ts`, `oath-signature.ts`, `oath-upload.ts`) that each hand-rolled the `[rosters, sharepoint]` pair now call `resolveRosterDirs()`. **Rule:** never re-spell `.tracker/<subdir>` as a string literal — add/use a `paths.ts` helper.
