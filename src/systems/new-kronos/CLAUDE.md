# New Kronos (WFD) Module

Employee search automation for New Kronos (Workforce Dayforce). Much simpler than Old Kronos.

## Before mapping a new selector

1. Run `npm run selector:search "<your intent>"` and review the top matches across all systems.
2. If a selector matches your intent, USE IT — do not map a new one.
3. If [`LESSONS.md`](./LESSONS.md) has a relevant entry, read it first to avoid repeating a known failure.
4. Otherwise, map a new selector following the conventions in [`selectors.ts`](./selectors.ts):
   a. Add the selector function with JSDoc (one-line summary, `@tags`, `verified YYYY-MM-DD`).
   b. Run `npm run selectors:catalog` to regenerate [`SELECTORS.md`](./SELECTORS.md).
   c. If you discovered a non-obvious failure mode along the way, append a lesson to [`LESSONS.md`](./LESSONS.md) following its template.
   d. Verify the inline-selector test still passes: `npx vitest run tests/unit/systems/inline-selectors.test.ts`.

See [`SELECTORS.md`](./SELECTORS.md) for the auto-generated catalog of every selector this module exports.

Example intents for `npm run selector:search`: [`common-intents.txt`](./common-intents.txt).

## Separation timecard parsing

`getSeparationTimecardData(page, range)` (in `navigate.ts`, re-exported from `index.ts` with its `SeparationTimecardData` type) reads the open timecard grid and returns:

- `lastPunchDate: string | null` — MM/DD/YYYY, the latest day carrying an In/Out punch (the separations workflow uses this as the **Last Day Worked**, overriding Kuali).
- `sickDates: string[]` — MM/DD/YYYY, chronological, the `Sick - Hourly` days.
- `holidayDates: string[]` — MM/DD/YYYY, chronological, the `Holiday - Hourly` days.

Call it AFTER `clickGoToTimecard` + `setDateRange` so the grid shows the right window, and pass the SAME window as `range` (`{ start, end }` Dates — build them from the `setDateRange` strings via `mmddyyyyToDate`): the grid renders dates without a year ("Mon 12/30"), and each parsed month/day resolves its year against that range (`formatTimecardDate`, fail-loud on zero/ambiguous candidates — kills the Dec→Jan year-stamp bug; the pure resolver is `resolveSeparationTimecardDates`, unit-pinned in `tests/unit/systems/new-kronos/navigate.test.ts`). Separations consumes `lastPunchDate` for the LDW and `sickDates` / `holidayDates` for the termination-comment clause only (they never change a date). See `src/workflows/separations/CLAUDE.md` "Date model".

**Verify the employee before reading.** `verifyTimecardEmployee(page, eid)` (call right after `clickGoToTimecard`, before `getSeparationTimecardData`) confirms the OPEN timecard belongs to the searched EID — Go To → Timecard can leave the previous employee's timecard on screen. Both the navigation wait and final gate read only the live-verified `.emp-nav-id` header and require an exact EID; page-wide text is forbidden because search chrome can retain the target EID while the timecard still belongs to someone else. Separations throws on a miss (visible, non-fatal). See LESSONS.md (2026-07-16).

## Gotchas

- Uses modern `getByRole()` API (more maintainable than CSS selectors)
- Dynamic iframe name: `iframe[name^="portal-frame-"]` (suffix changes per session)
- Checks for "There are no items to display." message to detect no results
- Less defensive than Old Kronos — fewer fallback strategies, lets errors propagate
- `setDateRange` enters the custom-range dates into NATIVE `<input type=date>` fields (`#startDateTimeInput`/`#endDateTimeInput`, value held as ISO `YYYY-MM-DD` — a live DOM dump proved they are NOT masked text inputs) via `setRangeDate`: **`fill(toIsoDate(...))` fast path → `js-moment-picker` calendar-grid click fallback → ISO readback verify (fail loud `WFP-00889`)**. A native date input ONLY accepts ISO via `fill()`; feeding it `MM/DD/YYYY` is silently dropped (reverts to today → OBS-006) and per-key typing fights the browser's own segment mask (scramble/`<empty>` → ISS-B05). Calendar fallback: `calendarDayCell` clicks the `td[role=gridcell]` by full-date aria-label (`:not(.out-of-month)`), `calendarPrevMonth`/`calendarNextMonth` + `calendarMonthHeader` step to the target month. Do NOT bring back keystroke typing — the old `typeMaskedDate`/masked-digit machinery is removed. See LESSONS.md (OBS-006 / ISS-B05).
- `navigate.ts` calls `debugScreenshot` during timecard checks (`new-kronos-timecard-01-current` / `02-previous`) — not a blanket debug logger across the whole module
- **Idle-refresh opt-in (2026-06-24):** `new-kronos` is registered in `src/domain/idle-refresh.ts` (default cadence: reload after 5 min idle, 30s tick), so its long-lived daemon session is kept warm by periodic page reloads between separations docs — the same mechanism UCPath uses. Server-side Dayforce sessions expire on their own idle clock; without this a 2nd+ batch doc would hit a logged-out Kronos page. Purely kernel-side — no system-module code; the kernel keys on the `new-kronos` system id. See `src/core/CLAUDE.md` (Per-System Idle-Refresh).

## Lessons Learned

- **2026-07-16: Timecard identity comes from `.emp-nav-id`, never `document.body.innerText`.** Live WFD rendered `<div class="emp-nav-id">10403587</div>` beside the open employee name. A page-wide EID scan could match the target in search chrome while the authoritative header still showed the previous employee. `scanTimecardEmployeeHeader` now drives both wait and verification with exact matching; unit coverage proves body-like text cannot false-pass.

- **2026-07-08: Period switch / custom-range Apply now asserts the displayed period actually changed, not just that the dropdown closed.** Both `switchToPreviousPayPeriod` (option-hidden wait) and `setDateRange` (custom range used by separations' `getSeparationTimecardData` read path) previously trusted a dropdown/option detach or the date-input readback as proof the switch landed — neither proves the timecard GRID re-rendered for the new period. Both now capture `timecard.payPeriodTriggerButton(page)`'s text before the switch/Apply and re-read it after, throwing (via the shared `didPeriodLabelSwitch`, `src/services/timecard/index.ts`) if the label is unchanged (or, for `switchToPreviousPayPeriod`, still literally "Current Pay Period"). **2026-07-16:** a BLANK before-label (the baseline read failed) is also rejected — with no baseline the switch can't be verified, so both sites throw naming the unreadable-baseline case instead of treating any non-blank after-label as a switch. Uses the already-verified (2026-06-18) `payPeriodTriggerButton` selector — no new selector needed. Pinned by `tests/unit/services/timecard/index.test.ts`.
- **2026-06-24: `clickGoToTimecard` waits for the dropdown option to RENDER (condition-based), not a fixed 2s sleep — and a found employee that can't open its timecard FAILS LOUD.** The old fixed `waitForTimeout(2000)` + one-shot `clickIfPresent(timecardItem)` raced the Angular dropdown render: the first found employee in a daemon session rendered within 2s (worked), but every subsequent one rendered slower, so `timecardItem.count()===0` at the checkpoint and it bailed in ~0.1s ("Timecard option not found"), silently returning an empty timecard → the separations handler fell back to the Kuali dates for FOUND HDH employees while the browser sat on the PREVIOUS employee's timecard. Fix: poll `timecardItem.first().waitFor({state:"visible"})` to a 15s deadline with one dropdown re-open retry; `timecardItem` dropped its bare `text=Timecard` substring branches (matched "Employee timecards" chrome) and anchored its role-name to `/^\s*timecards?\s*$/i`; and `runNewKronosTimecard` now THROWS on a found-but-can't-open (visible + non-fatal in the settled parallel block) instead of returning empty. See LESSONS.md (2026-06-24) + `src/workflows/separations/CLAUDE.md`. **NEEDS LIVE RE-VERIFY** on a real multi-doc batch.
- **2026-06-22: Found-detection waits for the result checkbox ATTACHED (not VISIBLE) — the "Select Item" control is a hidden native input.** `searchEmployee` decides found vs not-found, and a `false` there SKIPS the timecard entirely (`runNewKronosTimecard` early-returns before `clickGoToTimecard`). The old found-signal waited for `firstResultCheckbox` to be **visible**, but that checkbox's backing native `<input type=checkbox>` is zero-size / visually hidden, so the wait never resolved even with a result present — a clearly-found employee (EID 10629763, "Total [1]") was mis-resolved NOT FOUND, skipping the timecard AND firing the best-effort "no results surfaced" warning (one root cause, two symptoms). Fix: found when EITHER the checkbox is **attached** OR the new `firstResultSlat` (`menuitemradio`, tight) is visible — `Promise.any([...])` as the found waiter into `resolveSearchResult`. **Rule: always go to the timecard for any employee who shows up; the only skips are a genuine no-results search ("nobody shows up") and the upstream identity-check EID correction ("the eid is incorrect").** See LESSONS.md (same date) + `tests/unit/systems/new-kronos/navigate.test.ts`.
- **2026-06-22: An employee-search timeout is a best-effort NOT-FOUND, not a thrown error (ISS-B04).** `searchEmployee` races the first-result checkbox (→ found) against the "no items to display" sentinel (→ not found) on a 15s timeout. When NEITHER surfaced (slow grid, or the no-results sentinel drifted), it `throw`ew `[New Kronos] Timed out waiting for search results` — a fatal-looking `✗` in the separations parallel block, even though New Kronos is a **best-effort** source (the separations handler falls back to the Kuali Last Day Worked when New Kronos returns no punch). Surfaced on ~6/9 docs of the live 8-worker separations run; non-fatal (docs completed) but noisy + slow. Fix: the race resolution moved into the exported `resolveSearchResult(resultPresent, noResultsVisible, employeeId)` helper, which on a both-waiters-rejected timeout returns `false` with a `log.warn` instead of throwing. The helper takes the two `waitFor` promises directly so it's unit-pinnable without a live page (`tests/unit/systems/new-kronos/navigate.test.ts`). **NOT fully fixed:** a genuinely-absent employee still waits the full 15s before `resolveSearchResult` returns false — the no-results sentinel (`noResultsText`) isn't matching fast (else the race would settle on it). Cutting that wait needs the live no-results message re-mapped into `noResultsText` — requires a live New Kronos page for a no-record employee.
