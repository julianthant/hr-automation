# Core — Workflow Kernel

Declarative workflow runtime. Cross-workflow execution behavior, cancellation, task/control contracts, and new `Ctx` capabilities belong here, not in individual workflow handlers.

## Public Surface

- `defineWorkflow({...})` declares workflow metadata, schema, systems, steps, archetype, runtimePolicy, operator subject, and handler.
- `ctx.page(id)` waits for auth and returns a Playwright Page proxy that injects per-run `ctx.signal` into signal-aware methods.
- `ctx.signal` is the per-run AbortSignal. Pass it to non-Playwright awaits that support cancellation.
- `ctx.step(name, fn)` emits step status, captures screenshots on failure, and maps aborts to the standard cancelled terminal row.
- `ctx.updateData(patch)` writes operator-facing fields into tracker data.
- `ctx.workflowInstance` is the session-drawer instance name owning the run; `ctx.reportPhase(step)` pushes a phase into the terminal-drawer timeline (session `item_start`+`step_change`) **without** a queue row — for handlers that emit their own rows and bypass `ctx.step` (today only OCR). Every other handler drives the timeline for free via `ctx.step`/`ctx.markStep`.
- `ctx.parallel({...})` runs named tasks with `Promise.allSettled`.
- `ctx.delegateTo` / `ctx.delegateToAll` compose workflows. The kernel owns `parentRunId`, pending-row pre-emits, input persistence, and child watching.

Auth is global: one system uses the fast path; multiple systems use parallel prepare + staggered Duo submit. See `src/infra/auth/CLAUDE.md`.

## Audit Screenshots (`ctx.screenshot`)

`ctx.screenshot(opts)` captures pages, writes `{workflow}-{itemId}-{kind}-{label}-{system}-{ts}.png` under `.screenshots/` (or the run's `screenshotDir`), and emits one `screenshot` session event whose `files[]` lists every PNG written (so all land in the dashboard Screenshots tab). Three capture MODES, all on `ScreenshotOpts`, routed in `Session.captureAll` → `captureOnePage`:

- **`systems: string[]`** — restrict capture to specific system page(s) (e.g. `["kuali"]`). **Always set this for an audit shot of one system** — omitting it captures EVERY open page in one event (a 4-system separations run mixes Kuali + both Kronos + UCPath into one label). The legacy default (all systems) stays for genuinely whole-session captures only.
- **`slices: N`** (>1) — capture each targeted page as N equal vertical slices (`{label}-1of{N}`, … via `formatCaptureFilename`'s `sliceIndex`/`sliceTotal`). For TALL forms whose single `fullPage` shot is an unreadable narrow ribbon on a quarter-screen tiled viewport. `Session.capturePageInSlices` strips inner-scroll overflow (shared `expandScrollContainers`, same as `captureFullPage`), widens the viewport, measures `fullHeight`, and shoots `page.screenshot({ fullPage: true, clip:{ x:0, y:i*sliceHeight, width, height } })` per slice. **`fullPage: true` is LOAD-BEARING** with `clip`: a plain `clip` resolves against the *viewport* image and throws "Clipped area is empty or outside the resulting image" for any region below the current viewport; `fullPage: true` makes `clip` resolve against the full-page image so off-screen page-coordinate regions capture real content. No image library is used (the repo depends on `playwright` only — no `sharp`/`jimp`/`pngjs`).
- **`centerSelector: string`** — scroll the matching element to the vertical CENTER (`scrollIntoView({ block:'center' })`) and capture the VIEWPORT (NOT `fullPage`) via `Session.captureViewportCenteredOnElement`. For VIRTUAL-SCROLL grids (Kronos timecards) where `fullPage` only captures the DOM-rendered rows and misses off-screen data. Best-effort scroll — a missing element still captures whatever is shown. Mutually exclusive with `slices` (center wins).

`captureAndStampScreenshot(label, dataKey, { systems })` is the stamp-into-tracker-data variant; it does not take `slices`/`centerSelector` (single stamped filename). Tests: `tests/unit/core/session-slice-capture.test.ts`.

## Daemon Mode

Dashboard input runs use daemon mode when the workflow is registered in `src/core/workflow-loaders.ts`.

- First run with no alive daemon spawns `tsx src/cli-daemon.ts <workflow>`, authenticates once, then enqueues work.
- Later runs insert into SQLite `tasks` and wake alive daemons; no re-Duo.
- Daemons race to claim queued work through SQLite, not JSONL.
- Idle daemons keep sessions warm with periodic `session.healthCheck(system)`.
- `npm run <workflow>:stop` drains in-flight work; `-- --force` marks it failed immediately.
- **Stopping daemons (operator pool model).** The daemon `/stop` body carries `{ force?, reassign? }`. `reassign` decides the IN-FLIGHT item's fate at teardown: with `reassign: true` (dashboard **per-instance** card stop, `/api/daemon/stop-instance`) AND a surviving peer daemon, the item is un-claimed (`returnTaskToQueued`) and the peers are woken so an idle one finishes it; with `reassign` omitted (workflow-scoped "stop all" `/api/daemon/stop`, SIGINT/SIGTERM) or when this is the **last** daemon, the in-flight item **fails** (red — no `step:"cancelled"` sentinel). Queued (never-claimed) items are left for surviving peers, or failed by the last daemon's cleanup. A deliberate per-item `/cancel-current` is unaffected (daemon stays alive → orange Cancelled). The three-way branch lives in the claim loop (`daemon.ts`) and the outer-finally safety net (`shutdown.ts`). This teardown machine is the recurring-bug nest (VQ-003 / 2026-06-07 reassign / 2026-06-04 signal-wait); its full states × intents × where-each-lives map, the gap analysis, and the proposed explicit-transition-table refactor are in `docs/engineering/daemon-teardown-state-machine.md`. The deterministic CI guard for it is `tests/delegation/daemon-teardown-soak.test.ts`.

### E2E stub mode (`HRAUTO_E2E_STUBS=1`)

For the AI e2e test (real dashboard + real daemons, no real external systems), `loadWorkflow` wraps mapped workflows with scripted stub handlers — `src/core/e2e/stub-workflows.ts`. The clone keeps the real metadata/steps/schema/archetype/trace code but sets `systems: []` (no browsers, no Duo) and walks the real step list, stamping the same operator-data fields from the real input plus `data.e2eStub: "true"` for provenance. Steps honor file-based hold gates (`<trackerDir>/e2e-gates/<workflow>[--<step>].hold`, helpers in `tracker/paths.ts`, polling in `core/e2e/gates.ts`) so an e2e driver can deterministically park runs "running" (cancel/reassign tests) and release them; an abort while parked unwinds to the standard cancelled row.

Steps also honor a one-shot **fail gate** (`<trackerDir>/e2e-gates/<workflow>--fail-at--<step>.fail`, `e2eGateFailPath` / `consumeFailGate`): the driver arms it to make the scripted step throw `E2EScriptedFailError` — a genuine **non-cancel** error (NOT a `CancelledError`), so the kernel stepper runs `emitFailed` and the daemon writes a terminal `failed` row (red badge + Retry button), the organic-failure path the retry-coverage leg exercises (`Phase 4`). It is checked AFTER the hold release (park-then-arm) but BEFORE the step's success-data patch (a failed step stamps no success data), and SELF-CONSUMES on fire (deletes the file) so the Retry replay — which replays `tasks.original_input_json`, not accumulated data — sees no gate and walks to `done` with no manual cleanup. Pinned by `gates.test.ts` + `stub-workflows.test.ts`. oath-upload runs its REAL handler (wait-approval/wait-signatures are the machinery under test) with only the ServiceNow legs stubbed via its test seams (`_pageOverride` + overrides). OCR is never stubbed (real Gemini + local PDF); unmapped workflows load REAL with a loud `log.error`. The flag rides `process.env` through `spawnDaemon`'s `{ ...process.env }`, so daemons inherit it from the dashboard backend. Never set the flag outside an isolated `HRAUTO_TRACKER_DIR`.

**Stub data must use canonical workflow values, not display labels (2026-06-13, VP-001).** Scripted stub step data is consumed by the SAME downstream logic as real data — e.g. the OCR orchestrator runs `computeOcrVerification` over the stub person-lookup's `active-status` output. That function lower-cases and exact-matches the canonical `ActiveCheckStatus` enum (`active`/`inactive`/`non-hdh`/…). The stub originally emitted `activeStatus: "A"` (the dashboard's A/IA **display-chip** label), which matched nothing → `lookup-failed` (error `"A"`) → every signed OCR record stayed unverified and the review pane deselected all of them, so approval needed a manual re-check of each record. Fixed to emit `"active"`. Rule: a stub returns the same *value* the real handler would (canonical enum/field shape), never a UI label. AUD-001 (low, observational): a standalone OCR `verify` run leaves a tracker row + person-lookup children but persists **no `ocr` task** in `state.db` (it completes in-handler), so a SQLite-only OCR count undercounts by the verify runs — count from tracker history, not `tasks`.

## Per-System Idle-Refresh

Long-lived daemon sessions sit idle between queued items. Systems with server-side session timeouts (UCPath, I-9 Complete) need periodic page reloads to stay authenticated. The kernel handles this generically — opt a system in by listing it in `src/domain/idle-refresh.ts`; every workflow that declares that system inherits the behavior automatically.

### `src/domain/idle-refresh.ts` — domain API (no Node/Playwright dependencies; safe in the client bundle)

- **`IdleRefreshCadence`** — `{ thresholdMs: number; tickMs: number }`. `thresholdMs`: reload after this much automation inactivity; `tickMs`: how often the idle timer checks.
- **`DEFAULT_IDLE_REFRESH_CADENCE`** — `{ thresholdMs: 5 * 60 * 1000, tickMs: 30 * 1000 }` (5-min threshold, 30-sec tick). Conservative for ≥15-min server timeouts.
- **`IDLE_REFRESH_SYSTEMS`** — `Readonly<Record<string, IdleRefreshCadence>>`. Current entries: `ucpath` and `i9`, both using `DEFAULT_IDLE_REFRESH_CADENCE`. Presence here is the opt-in — add a system here to give it idle-refresh.
- **`isIdleRefreshSystem(systemId)`** — returns `true` when the system is in `IDLE_REFRESH_SYSTEMS`.
- **`idleRefreshCadence(systemId)`** — returns the `IdleRefreshCadence` for the system, or `undefined` if it doesn't opt in.

### `src/core/kernel/idle-refresh-hooks.ts`

- **`buildIdleRefreshHooks(instance, trackerDir?)`** — returns `Pick<SessionObserver, 'onIdleTouch' | 'onIdleRefresh'>`. Bridges the kernel `Session`'s idle touch/reload lifecycle into `idle_signal` session-JSONL events that drive the dashboard countdown ring. `onIdleTouch` emits a `touch` signal; `onIdleRefresh` emits `refresh_start` or `refresh_end`.

### Consumer chain

1. **`Session` (kernel)** — maintains a per-system `IdleRefreshState` map for every system in `IDLE_REFRESH_SYSTEMS ∩ launched systems`. A `setInterval` (period = `tickMs`) checks elapsed time since the last `ctx.page(<system>)` call; once inactivity exceeds `thresholdMs`, it reloads the page and fires `idleTouchCb` / `idleRefreshCb`. `Session.launch` wires those callbacks to the observer's `onIdleTouch` / `onIdleRefresh`.
   - **The idle timer is guarded across the FULL auth chain, not just `ctx.step` bodies.** Two guards suppress a reload: the `ctx.step`-body check (`idleGuard`, wired in `makeCtx` — runs *post*-auth), AND a private `authInProgress` flag set in `Session.launch` from before `loginWithRetry` until every system's readiness settles (covers login retries, the Duo prompt, and the serial Duo queue wait). Without `authInProgress`, an idle tick could fire `page.reload()` mid-Duo — navigating the prompt away (auth fails) and invalidating the armed CDP WebAuthn target while the `armedByPage` WeakMap still reports the page as armed (→ "factor not found" → manual fallback → timeout). The flag is checked in both `tickIdleRefresh` and `scheduleIdleReload`. For the 1-system fast path the flag resets in an inline `finally`; for the ≥2-system path the login IIFEs are NOT awaited by `launch`, so the flag resets when their combined `Promise.allSettled` settles (after `launch` returns). A `forWorker` child never authenticates (the parent does, on a shared context pool), so `isAuthInProgress()` walks up to the parent — the parent's auth window covers the worker's idle timer too. (2026-06-17)
2. **`buildIdleRefreshHooks`** — plugs into the `SessionObserver` (`session-observer.ts` via `buildSessionObserver`, and `batch-lifecycle.ts` via `createBatchObserver` using spread `...buildIdleRefreshHooks(instance, trackerDir)`). Translates the callbacks into `idle_signal` JSONL events.
3. **`daemon.ts`** — after each successful auth (`Session.launch`) and after each `item_complete`, emits a `touch` idle signal for every system in `wf.config.systems` that `isIdleRefreshSystem`, resetting the per-system countdown.
4. **Dashboard `WorkflowBox`** — imports `idleRefreshCadence` / `isIdleRefreshSystem` / `DEFAULT_IDLE_REFRESH_CADENCE` from the domain to render a per-system SVG countdown ring (`IdleCountdownRing`) on each system tile in the session card. The ring drains from full (just touched) to empty (reload due) over `thresholdMs`, then turns amber; a `Loader2` spinner replaces it while a reload is in progress.

## Invariants

- Every run mode constructs `Ctx` via `makeCtx`; never hand-roll a Ctx literal.
- `buildTrackerOpts(wf)` must stay shared across all modes so detail fields, display names, ids, and runtime warnings behave the same.
- New workflows require `operatorSubject`, `archetype`, and `runtimePolicy`.
- `data.archetype` is the canonical row-shape discriminator; delegated scope is `parentRunId`.
- SQLite is live queue/control truth. JSONL is audit/history output during transition.
- `tasks.original_input_json` preserves pristine task input; retries must replay that value, not accumulated tracker data.
- Requeued existing tasks should call `ensureDaemonsAvailable`, not `ensureDaemonsAndEnqueue`, to avoid duplicate rows.
- Delegation must route through `ctx.delegateTo` / `ctx.delegateToAll`; direct child `runWorkflow(... parentRunId ...)` and child `ensureDaemonsAndEnqueue(... parentRunId ...)` are forbidden by architecture guards.
- Cancel is one mechanism: per-run `AbortController` registered on the unified `runRegistry` (`src/core/run-registry.ts`) + Page proxy + stepper remap to `CancelledError`. Every trigger (daemon `cancel_task`, HTTP `/cancel-current`, browser-disconnect, daemon force-stop via `abortLaunchAndKillSession`, daemon shutdown sweep) calls `runRegistry.cancel(runId)`, which aborts the controller, writes the SQLite cancel audit for in-process runs, and watchdog hard-kills chromium after `hardKillAfterMs` if the run hasn't unregistered. Daemon state is a single `state.activeRun: RunHandle | null`. Do not reintroduce force-stop mode, page-navigation tricks, or the legacy `cancelTarget` / `in-process-runs` split (guard: `tests/unit/architecture/cancel-mechanism.test.ts`).
- **Force-stop must abort the in-flight run's signal — not just kill chromium.** A handler parked in a NON-Playwright, signal-only await (the only one today: oath-upload's `wait-approval` → `subscribeToApproval`, which blocks with no live browser) is invisible to the chromium kill. `createAbortLaunchAndKillSession` therefore calls `runRegistry.cancel(state.activeRun.runId, { hardKillAfterMs: 0 })` so all three force-stop entry points (`/stop`, `stop_worker`, SIGINT/SIGTERM/SIGHUP) unblock such a wait. The outer-finally `runDaemonShutdownCleanup` sweep is NOT sufficient on its own: it cannot run until the claim loop's `await runOneItem` settles, which never happens while the handler is parked — a deadlock.
- Daemon queue readers must filter to daemon workflow tasks; OCR/dependency parents can also live in `tasks`.
- `withTrackedWorkflow` owns real-run SIGINT; tests using `trackerStub` are the only `runWorkflow` branch with its own handler.
- `runOrdinal` is backend-assigned from earliest tracker timestamp; never derive it client-side from runId.

## Escape Hatches

- `ctx.session.page(id)` gives the raw authenticated Page.
- `ctx.isBatch` and `ctx.runId` are available for batch-only cleanup or external correlation.
- `runWorkerPool` / shared-context pool modes are for in-handler fan-out sharing authenticated sessions, as in Person Lookup's one-Duo-many-tabs pattern.
- Person Lookup / UCPath date naming: the operator-facing "Start Date" (`data.startDate`) is **CRM First Day of Service**, stamped in cross-verification — NOT a UCPath date. UCPath `EidResult.startDate` (Last Hire) and `effectiveDate`/EFFDT are backend matching context only (ride the row as `ucpathStartDate`/`effdt`). Do not repurpose either UCPath date as the dashboard-facing start date.

Recurring escape hatches should become first-class kernel features.

## Run Isolation

Every per-item row carries `runId` + `workflowInstance`; `filterEventsForRun` trusts `runId` first. Orphan auth/browser events without `runId` are attributed only when `workflowInstance` matches and timestamps fall inside the run window. `itemInFlight` from daemon events is the live-state signal; do not infer live state from tracker rows.

## Lessons Learned

- **Lesson maintenance rule:** Merge dated migration notes into current invariants whenever possible.
- **2026-06-22: A claim lease (`tasks.claim_generation`) stops a re-pended item from being completed by the worker stopped after a peer re-claims it (ISS-005).** Stop-All / per-instance-stop teardown re-pends an in-flight item via `returnTaskToQueued` so a surviving peer can finish it — but the re-pend KEPT the same `current_attempt_id` + runId (intentional: the run continues under the same id on the peer). The hazard: a peer re-claimed the identical attempt while the STOPPED instance was still finishing its run; when that instance then called `markTaskDone(taskId, attemptId)` it landed (the attempt still matched), so TWO workers each transacted the work — a duplicate oath submission outside dry-run, even though the task-store stayed idempotent (one `done` row, an uncaused `done→running→done` in the session/event stream). The same race rides the `recoverClaimsForDeadWorkers` re-pend path. **Fix:** `claimNextTask` now bumps `tasks.claim_generation` on every claim and returns the post-increment value as `ClaimedTask.claimGeneration` — the lease the worker holds. The lease threads daemon-side via `QueueItem.claimGeneration` → `markItemDone`/`markItemFailed`/`markItemCancelled(…, claimGeneration)` → `markTaskTerminal` → the task-store `markTask*({ claimGeneration })`. `markTerminal` adds `AND claim_generation = @claimGeneration` to the task UPDATE when a generation is supplied; a stale generation (the original worker's, behind the peer's re-claim) matches no row and the terminal write is a NO-OP (the attempt row is left untouched too, keeping task+attempt in lockstep). The daemon's normal-completion branch passes `item.claimGeneration` and now gates the dependency settle on the task actually reaching `done`/`failed`, so a stale no-op doesn't settle a dependency the peer owns. **Scope:** ONLY the daemon's normal `r.ok`/`r.err` completion threads the lease — the teardown emitters (`failInFlightItem`, deliberate-cancel) and all `markTask*` callers that pass no generation keep the prior unconditional behavior (the guard is opt-in). Migration 13 adds the column `NOT NULL DEFAULT 0` (next claim advances legacy rows; no backfill). Pinned by `task-store.test.ts` ("a stale worker cannot complete a task a peer re-claimed after re-pend (ISS-005)"). Complements the 2026-06-15 single-terminal-write token (that guards the tracker ROW emit within ONE run; the lease guards the SQLite terminal across a re-pend handoff between two workers).
- **2026-06-13: A retry INHERITS the original run's frozen `__traceId` (trace tail = ORIGINAL runId4, not the new run's) — intended, not a bug (ISS-002).** A retry replays `tasks.original_input_json` under a NEW runId, but `emitInheritedRow` (`control/ops/emit-inherited.ts`) carries the prior row's `data` forward verbatim — including `data.__traceId` — so the new run's pending row already bears the original trace id, and `run-one-item`'s `findFrozenTraceId(newRunId)` then reuses it (frozen-once). Net: every row of a retried run shows `<code>-<HHMMSS>-<originalRunId4>` even though its own `runId` is new (verified in e2e evidence: retry `d96a3b6c` → `os-004634-420d`). This is the CONTRACT: the trace id identifies the logical OPERATION, which a retry continues — continuity wins over per-row greppability-by-trace-tail. The retried run is still individually greppable by its own `runId` (the row's `runId` field, the footer `#run`, and logs all carry the new id); only the trace-id TAIL stays the original. Same inheritance the cancel/shutdown rows do (`preserveFrozenTraceId`). Do NOT "fix" this by composing a fresh tail for retries.
- **2026-06-13: VQ-003 — a force-shutdown of an in-flight signal-only-wait item DOUBLE-terminalized the one run; fix threads a cancel `origin:'shutdown'` through `runRegistry` so the kernel suppresses its own terminal cancelled row.** During a workflow-scoped Stop-All (`/api/daemon/stop`, no reassign) of a daemon parked in a SIGNAL-ONLY wait (oath-upload `wait-approval` → `subscribeToApproval`; e2e: a hold gate), TWO contradictory terminal rows landed ~2ms apart for the ONE in-flight run: (1) `failed/step:"cancelled"` from `withTrackedWorkflow`'s catch — the abort (`createAbortLaunchAndKillSession` → `runRegistry.cancel`, required to unblock a signal-only wait per 2026-06-04) makes the stepper's `mapEscapedHandlerError` `emitStep('cancelled')` + throw `CancelledError`, which the tracker wrapper turns into a terminal cancelled ROW; then (2) `failed` (no `step:cancelled`, the `SHUTDOWN_NO_DAEMON_FAIL_REASON` text) from `failInFlightItem` in the daemon claim loop's `forceShutdown` branch. Latest-wins landed the right red FAILED, but the transient orange chip + "Cancelled by user" cause polluted the row-lifecycle history (violating the 2026-06-07 single-FAILED invariant). **Fix:** `runRegistry.cancel` gained a structured `origin?: 'user' | 'shutdown'` (default `'user'`) recorded per-runId + a `cancelOrigin(runId)` reader (cleared on `unregister` so a reused runId can't inherit a stale origin). The two daemon-teardown abort sites — `createAbortLaunchAndKillSession` and the `runDaemonShutdownCleanup` sweep — pass `origin:'shutdown'`; deliberate cancels (`/cancel-current`, `cancel_task`, browser-disconnect, in-process dashboard cancel, OCR prep discard) keep the `'user'` default. `run-one-item` wires `suppressTerminalRowOnCancel: () => runRegistry.cancelOrigin(runId) === 'shutdown'` INTO `withTrackedWorkflow`'s opts (the callback is the layer boundary — tracker never imports core), and the wrapper's catch SKIPS its terminal cancelled-row emit when that returns true, while STILL re-throwing so `run-one-item` returns `{ ok:false, kind:'cancelled' }` and the daemon's three-way reassign/fail/cancel branch is unchanged. Net: exactly ONE terminal write per run in BOTH cases — the daemon owns it on shutdown/reassign; the kernel owns the single orange row on a deliberate `/cancel-current`. Not a force-stop-mode revival and no new cancel mechanism — `cancel-mechanism.test.ts` stays green. Pinned by `daemon.test.ts` (force-stop signal-only wait → exactly one `failed`, NO `step:cancelled`) + `run-registry.test.ts` (origin default/shutdown/clear-on-unregister) + the existing `run-one-item.test.ts` (deliberate cancel keeps its `step:cancelled` row). **VQ-001/VQ-002 were investigated — WORKING AS DESIGNED, no code change:** a single typed oath-signature EID rendering as a one-member "1 rows batch" with a phantom `parentRunId` is the `runtimePolicy.delegation.alwaysBatchInputRun: true` one-member-batch surface + the projection-synthesized batch anchor every input-run batch uses (`enqueue-dispatch.ts` mints `effectiveParentRunId = randomUUID()`, never emits an anchor row — the dashboard synthesizes it by grouping members); the member rows' `__traceId`s are greppable by their own runId4, only the display-only synthesized anchor uses the phantom id (cosmetic).
- **2026-06-15: E2E-105 + E2E-101 — force teardown ORPHANED never-claimed queued items, and a deliberate cancel of a signal-only wait DOUBLE-wrote the terminal row; both closed by a `shuttingDown` hand-off gate + a runId-keyed terminal-write guard.** **E2E-105 (the headline):** a workflow-scoped force stop-all (`POST /api/daemon/stop`, no reassign) of EVERY alive daemon left never-claimed `queued` tasks stuck `control_state=queued` with 0 daemons alive and NO terminal row (live repro: 3 daemons + 3 queued → 3 in-flight `failed` correctly, 3 queued orphaned; `/stop` reported `queuedCancelled:0`). Root: the queued-item sweep in `shutdown.ts` gated on `otherAlive.length === 0` (peers' lockfiles still on disk), so EVERY dying daemon "left the queued task for a peer" that was ALSO dying → nobody terminalized it. (The dashboard backstop `scanOrphanedQueueItems` recovered them ~5min later — a window of zero terminal state + a dashboard-uptime dependency, not a fix.) **Fix:** `/whoami` now reports `shuttingDown` (from `state.shuttingDown`); the dashboard's `/stop` sets `shuttingDown` SYNCHRONOUSLY in every daemon's `/stop` handler before it responds, so by teardown-sweep time a stopped peer reports `shuttingDown:true` — the happens-before edge that makes the decision deterministic. The queued sweep now gates on `filterPeersAvailableForHandoff(otherAlive)` (`registry.ts` — responsive `/whoami` MATCH **and** `shuttingDown===false`) being EMPTY, not on `otherAlive` being empty. So the effectively-last responsive owner terminalizes the queue (red `failed`), while a genuinely-surviving (not-stopped) peer still reports `shuttingDown:false` and absorbs the items — per-instance stop / partial teardown keep "≥1 live daemon → leave queued" intact. Several dying daemons may each elect themselves owner; the `stillQueued` re-read + the terminal-write guard below keep it to ONE terminal row per item. **E2E-101 (subsumed by the guard):** a deliberate `/cancel-current` of an item parked in a SIGNAL-ONLY wait wrote TWO consistent `failed/step:cancelled` rows ~32ms apart — the kernel's `withTrackedWorkflow` catch (origin:'user', NOT suppressed) AND the daemon's deliberate-cancel branch both emitted. Display was fine (one orange surface) but it violated "exactly one terminal write per run." **Fix:** `runRegistry` gained `claimTerminalWrite(runId)` / `releaseTerminalWrite(runId)` — the FIRST claimer writes the run's sole terminal row, every later caller defers. Wired into BOTH racing emitters: `withTrackedWorkflow` (via the new `claimTerminalWrite` opt, claimed ONLY when it actually emits — i.e. NOT when `suppressTerminalRowOnCancel` is true, or it would steal the token and leave VQ-003 with zero rows) and the daemon's `failInFlightItem` + deliberate-cancel branch. Deliberate cancel → kernel wins, daemon defers → one orange row. Force-shutdown (VQ-003, origin:'shutdown') → kernel suppressed (doesn't claim), daemon's `failInFlightItem` claims+writes the sole red row — unchanged, now structural. **Token lifecycle gotcha:** `unregister` must NOT clear the token (it fires inside `run-one-item`'s finally, BEFORE the daemon's three-way branch reads it — clearing there lets the daemon re-claim and double-write); the daemon's PER-ITEM finally calls `releaseTerminalWrite(runId)` (the real boundary), and `_resetRunRegistryForTests` clears it too. Full map + the deferred transition-table refactor: `docs/engineering/daemon-teardown-state-machine.md` ("open gap" section now CLOSED).
