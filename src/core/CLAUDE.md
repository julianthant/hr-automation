# Core — Workflow Kernel

Declarative workflow runtime. Cross-workflow execution behavior, cancellation, task/control contracts, and new `Ctx` capabilities belong here, not in individual workflow handlers.

## Public Surface

- `defineWorkflow({...})` declares workflow metadata, schema, systems, steps, archetype, runtimePolicy, operator subject, and handler.
- `ctx.page(id)` waits for auth and returns a Playwright Page proxy whose async calls race the per-run `ctx.signal` without changing Playwright arguments. An aborted in-flight call poisons that page; `Session` closes and replaces it before the next caller can receive a page.
- `ctx.signal` is the per-run AbortSignal. Pass it to non-Playwright awaits that support cancellation.
- `ctx.step(name, fn)` emits step status, captures screenshots on failure AND at the end of each successful step (the per-step audit trail — see Audit Screenshots), and maps aborts to the standard cancelled terminal row.
- `ctx.updateData(patch)` writes operator-facing fields into tracker data.
- `ctx.recordData(point | point[])` records data-provenance points — a value EXTRACTED (`direction: "read"`) from a system or INPUTTED (`direction: "write"`) into one. Purely observational (never touches tracker data / control flow); auto-tags the current step and emits an `event: "data:point"` structured log line (`src/domain/data-point.ts`) that the dashboard's gated "View Data" tab groups by step into read/write lanes. Any workflow opts in just by calling it.
- `ctx.workflowInstance` is the session-drawer instance name owning the run; `ctx.reportPhase(step)` pushes a phase into the terminal-drawer timeline (session `item_start`+`step_change`) **without** a queue row — for handlers that emit their own rows and bypass `ctx.step` (today only OCR). Every other handler drives the timeline for free via `ctx.step`/`ctx.markStep`.
- `ctx.parallel({...})` runs named tasks with `Promise.allSettled`.
- `ctx.delegateTo` / `ctx.delegateToAll` compose workflows. The kernel owns `parentRunId`, pending-row pre-emits, input persistence, and child watching.

Auth is global: one system uses the fast path; multiple systems use parallel prepare + staggered Duo submit. See `src/infra/auth/CLAUDE.md`.

## Audit Screenshots (`ctx.screenshot`)

`ctx.screenshot(opts)` captures pages, writes `{workflow}-{itemId}-{kind}-{label}-{system}-{ts}[-cNN].png` under `.screenshots/` (or the run's `screenshotDir`), and emits one `screenshot` session event whose `files[]` lists every PNG written (so all land in the dashboard Screenshots tab). **ONE image per capture by DEFAULT** — a short page is one tight shot; a tall page is scroll-captured band by band and the bands are **stitched into one continuous image** (never a chunked `-cNN` set). A chunked `-cNN` set only appears when a caller explicitly asks (`stitch: false`) or when compositing fails and the capture degrades to raw slices. Capture geometry (width floor / slice height / overlap) is centralized in the exported **`CAPTURE`** object (`src/core/kernel/session.ts`).

**Automatic end-of-step screenshots (`kind: 'step'`) — every workflow, no per-workflow code.** The Stepper takes one audit screenshot at the END of each successful `ctx.step(...)`, so a 5-step run leaves a 5-shot visual trail of what the automation did at each stage (symmetric with the existing `kind: 'error'` capture on step *failure*). It is **scoped to the one system the step actually touched** and **skips steps that touched no browser page**: the `Session` keeps a monotonic `page(id)` access counter + last-accessed system (`Session.pageAccess()`), and the Stepper captures only when that counter advanced while the step body ran — so a pure-compute step (e.g. onboarding `extraction`) and an auth `markStep` phase produce nothing, and a multi-system run yields one shot per step (the last-touched page) rather than one per open page. Only the OUTERMOST step captures (nested `ctx.step` calls roll up to one). Best-effort: a capture failure never fails a step that already succeeded. Wired once in `handler-runner.ts` (`stepper.setPageAccess(() => session.pageAccess())`, beside `setScreenshotFn`), so it covers both the `run-one-item` daemon path and the in-process `run-workflow` path; stub/test runs that don't wire `pageAccess` (and e2e stubs with `systems: []`, which never call `ctx.page`) capture nothing. The dashboard Screenshots tab renders these with an `info`-toned **Step** badge and a dedicated **Steps** filter chip. Workflows that already take a deliberate `kind: 'form'` shot at a critical step (onboarding `transaction`, separations finalize) keep them — those are distinctly labeled moments (e.g. the pre-submit dry-run shot); the per-step trail is additive.

**There is ONE capture mode for every workflow — the unified whole-page/form shot, captured by SCROLLING the real scroll target and screenshotting the PAINTED pixels** (the technique full-page-screenshot browser extensions use, adapted to Playwright). Every `ctx.screenshot()` routes through `Session.captureFullPage`, which captures the ENTIRE page or form — never a clipped portion (the operator's standing requirement) — as one image when it fits one viewport, or by scroll-capturing the tall page band by band and **stitching the bands into one continuous image** (the default; page-height `-cNN` slices only on an explicit `stitch: false` or a compositing-failure degrade). The pipeline (best-effort, reversible, restored in `finally`):

1. **`setCaptureWidth(CAPTURE.width)`** — pin the layout viewport to a FIXED readable column width (1280) so a narrow/normal form captures the SAME width regardless of the tiled daemon window, then widen BEYOND 1280 only for genuinely wide content (the PeopleSoft Person Org grid, ~1600–2200px, measured at the top document AND inside child frames, capped at `CAPTURE.maxWidth` 6000). It's a floor, not a cap.
2. **`planScrollCapture`** — pick the DOMINANT scroll target by comparing hidden overflow (`scrollHeight − clientHeight`) across (a) the window, (b) every visible `overflow:auto/scroll` element that fills a meaningful slice of the viewport (the Kuali document/finalization form scroll container), and (c) every same-origin iframe's scrolling document (the UCPath `#main_target_win0` content frame). Whichever has the most off-screen content wins — **but only among targets that are actually VISIBLE.** A scroll container that is mounted but painted BEHIND another layer is **occlusion-rejected**: for each `overflow:auto` candidate, sample a 3×3 grid of points in its on-screen rect and keep it only if it (or a descendant) is the top `elementFromPoint` somewhere. This is load-bearing for Kuali: the Build **apps catalog** (a `overflow-auto` div ~16000px tall, 379 launcher tiles) stays MOUNTED behind an open document view, so by raw overflow it would win and the capture would walk the hidden catalog instead of the on-screen form (live-verified 2026-06-30: catalog overflow 15452 occluded → rejected; the visible form container chosen). The window doesn't scroll on the Kuali doc page (`winOverflow 0`), so the bug was an occluded ELEMENT, not the window. (window preferred on a tie — it shows everything in one column). Tags the chosen element/iframe (`data-hrcap`/`data-hrcap-frame`) so the scroll loop can drive it across evaluate calls, then HIDES `position:fixed`/`sticky` chrome that isn't part of the target chain (so a sticky banner/header — e.g. Kuali's "unsupported browser" bar — doesn't reprint in every band). Stashes `window.__hrcapRestore`.
3. **scroll + shoot bands** (`computeSliceOffsets`, pure/unit-tested + `scrollCaptureTo`) — band height = the target's visible `clientHeight` (capped at `CAPTURE.sliceHeight` 1200); offsets step at `band − sliceOverlap` (the last anchored to the bottom). For each offset, `scrollCaptureTo(y)` scrolls the tagged target there and returns its live on-screen clip rect; then ONE `page.screenshot({ clip })` of the PAINTED viewport. A content-fits-one-viewport WINDOW page is instead a single tight `fullPage` shot (no scrolling, no whitespace padding). The `-cNN` suffix sorts the slices top→bottom. **Painted-pixel capture can't clip content the renderer never drew** — which is why this is reliable where the old DOM-expand + `screenshot({fullPage})` approach clipped the Kuali modal and the nested UCPath iframe (the renderer never painted the off-screen-in-a-scroll-container content `fullPage` was asked to size to).

The ONE exception, all on `ScreenshotOpts`:

- **`systems: string[]`** — restrict capture to specific system page(s) (e.g. `["kuali"]`). **Always set this for an audit shot of one system** — omitting it captures EVERY open page in one event (a 3-system separations run would mix Kuali + Kronos + UCPath into one label). The legacy default (all systems) stays for genuinely whole-session captures only.
- **`centerSelector: string`** — the ONLY non-`captureFullPage` route. Scroll the matching element to the vertical CENTER (`scrollIntoView({ block:'center' })`) and capture the VIEWPORT (NOT `fullPage`) via `Session.captureViewportCenteredOnElement`. Use ONLY for VIRTUAL-SCROLL grids (the Kronos timecard) where the off-screen rows aren't in the DOM, so NO full-page shot can reach them — physically centering the target row and shooting what's painted is the only faithful capture. Best-effort scroll — a missing element still captures whatever is shown.
- **`stitch: boolean` (DEFAULT true — 2026-07-01, operator request)** — a TALL capture is composed into ONE continuous image, so **every workflow's chunk screenshots come out as a single stitched image, never a chunked `-cNN` set**. The scroll loop captures each band to a buffer, then `stitchCaptureBands` (`src/core/kernel/capture-stitch.ts`, pure + unit-pinned) composites them by **exact scroll geometry** — each band placed at `offsetCss × scale` (`scale` = band-0 PNG height ÷ its clip height, so no DPR assumption), later bands overwriting the overlap. Geometry, NOT pixel correlation, so it can't mis-align or silently drop/duplicate a row of a repetitive PeopleSoft form — which matters for an audit screenshot. **Pass `stitch: false` to force the raw `-cNN` page slices** (nobody does today; the separations Kuali/UCPath captures all stitch). A one-band page is one image either way; any decode/compositing failure degrades to writing the raw slices (capture never lost). Ignored alongside `centerSelector`. Needs `pngjs` (an explicit dep). The decision lives at one point in `captureFullPage` (`stitch = opts?.stitch !== false`).

`captureAndStampScreenshot(label, dataKey, { systems })` is the stamp-into-tracker-data variant; it routes through the same unified `captureFullPage` (single stamped filename). Tests: `tests/unit/core/session-capture-routing.test.ts`, `tests/unit/core/capture-stitch.test.ts`.

**Why scroll-and-capture (2026-06-25, operator request — supersedes the DOM-expand approach):** the earlier path (DOM-mutate to force `document.scrollHeight` tall via `expandScrollContainers`/`growOverflowingIframes`, then trust `screenshot({fullPage, clip})` to render it) kept clipping in live runs — the Kuali finalization modal started mid-form and the UCPath nested iframe (`#main_target_win0`) cut off at the bottom (visible scrollbar) — because `fullPage` renders what the browser PAINTS, and content living in an off-screen scroll-container/iframe region simply isn't painted no matter how tall you make the box. The fix matches what dedicated full-page-screenshot extensions do: find the element that ACTUALLY scrolls, scroll it one band at a time, and screenshot the genuinely-painted viewport at each stop. The operator's three asks are still met: ONE capture type for every workflow that covers the entire page/form, a **consistent readable width** (1280 floor), and **long pages split into readable pages** (`-cNN` slices, not one strip). *(The slice preference was later reversed — 2026-07-01 a tall page is STITCHED into one image by default, not sliced; see the Lessons Learned entry below. The scroll-and-capture mechanism here is unchanged — only what happens AFTER the bands are captured.)* **Verified 2026-06-25:** synthetic Playwright fixtures — a fixed Kuali-style modal with inner overflow + a sticky banner (captured Field 1→24 top→bottom, banner hidden), a UCPath-style nested same-origin iframe (whole in-frame form incl. the bottom "Transaction ID" line), a tall window page (multi-slice), a short page (single tight shot) — AND a **LIVE separations dry-run** (doc #4361, no writes): the real UCPath SS Smart HR nested iframe captured fully top→bottom (the previously-clipped "Invol Termination · Pending" status box + footer buttons are present), and a long real Kuali Build page walked into top→bottom slices. The dashboard Screenshots tab collapses all `-cNN` slices of one capture into a single "folder" tile (`buildScreenshotGroups`, cover = first slice; opening it pages through the slices via the lightbox + thumbnail rail — 2026-06-30, supersedes the one-tile-per-slice `flattenScreenshotTiles`); display is owned by `src/dashboard/components/log-panel/`.

**Gotcha — no NAMED nested function inside `page.evaluate` (2026-06-24):** a named function/arrow defined inside `page.evaluate` (e.g. `const growFramesIn = (...) => {…}`) trips esbuild/tsx's `__name` keep-names helper, which is undefined in the browser → the WHOLE evaluate throws `ReferenceError: __name is not defined`. Since the runtime is `tsx`, this hits production, not just tests; and a swallowing `.catch(() => {})` hides it, so the capture just no-ops. `planScrollCapture`/`scrollCaptureTo` are written as iterative evaluate code (inline loops; the only function is the anonymous `window.__hrcapRestore` arrow, mirroring the existing restore pattern) for exactly this reason — write iterative traversals (explicit queue/stack) inside `page.evaluate`, never a named recursive function.

## Daemon Mode

Dashboard input runs use daemon mode when the workflow is registered in `src/core/workflow-loaders.ts`.

- First run with no alive daemon spawns `tsx src/cli-daemon.ts <workflow>`, authenticates once, then enqueues work.
- Later runs insert into SQLite `tasks` and wake alive daemons; no re-Duo.
- Daemons race to claim queued work through SQLite, not JSONL.
- Idle daemons keep sessions warm with periodic `session.healthCheck(system)`.
- `npm run <workflow>:stop` drains in-flight work; `-- --force` marks it failed immediately.
- **Stopping daemons (operator pool model).** The daemon `/stop` body carries `{ force?, reassign? }`. `reassign` decides the IN-FLIGHT item's fate at teardown: with `reassign: true` (dashboard **per-instance** card stop, `/api/daemon/stop-instance`) AND a surviving peer daemon, the item is un-claimed (`returnTaskToQueued`) and the peers are woken so an idle one finishes it; with `reassign` omitted (workflow-scoped "stop all" `/api/daemon/stop`, SIGINT/SIGTERM) or when this is the **last** daemon, the in-flight item **fails** (red — no `step:"cancelled"` sentinel). Queued (never-claimed) items are left for surviving peers, or failed by the last daemon's cleanup — **except** when that last daemon never finished auth (`state.authCompleted === false`): leave them queued so a newly spawned worker can claim after Duo (otherwise a mid-auth stop / Duo hang mass-fails the whole fan-out and "Add a worker" looks broken). A deliberate per-item `/cancel-current` is unaffected (daemon stays alive → orange Cancelled). The three-way branch lives in the claim loop (`daemon.ts`) and the outer-finally safety net (`shutdown.ts`). This teardown machine is the recurring-bug nest (VQ-003 / 2026-06-07 reassign / 2026-06-04 signal-wait); its full states × intents × where-each-lives map, the gap analysis, and the proposed explicit-transition-table refactor are in `docs/engineering/daemon-teardown-state-machine.md`. The deterministic CI guard for it is `tests/delegation/daemon-teardown-soak.test.ts`.

### E2E stub mode (`HRAUTO_E2E_STUBS=1`)

For the AI e2e test (real dashboard + real daemons, no real external systems), `loadWorkflow` wraps mapped workflows with scripted stub handlers — `src/core/e2e/stub-workflows.ts`. The clone keeps the real metadata/steps/schema/archetype/trace code but sets `systems: []` (no browsers, no Duo) and walks the real step list, stamping the same operator-data fields from the real input plus `data.e2eStub: "true"` for provenance. Steps honor file-based hold gates (`<trackerDir>/e2e-gates/<workflow>[--<step>].hold`, helpers in `tracker/paths.ts`, polling in `core/e2e/gates.ts`) so an e2e driver can deterministically park runs "running" (cancel/reassign tests) and release them; an abort while parked unwinds to the standard cancelled row.

Steps also honor a one-shot **fail gate** (`<trackerDir>/e2e-gates/<workflow>--fail-at--<step>.fail`, `e2eGateFailPath` / `consumeFailGate`): the driver arms it to make the scripted step throw `E2EScriptedFailError` — a genuine **non-cancel** error (NOT a `CancelledError`), so the kernel stepper runs `emitFailed` and the daemon writes a terminal `failed` row (red badge + Retry button), the organic-failure path the retry-coverage leg exercises (`Phase 4`). It is checked AFTER the hold release (park-then-arm) but BEFORE the step's success-data patch (a failed step stamps no success data), and SELF-CONSUMES on fire (deletes the file) so the Retry replay — which replays `tasks.original_input_json`, not accumulated data — sees no gate and walks to `done` with no manual cleanup. Pinned by `gates.test.ts` + `stub-workflows.test.ts`. oath-upload runs its REAL handler (wait-approval/wait-signatures are the machinery under test) with only the ServiceNow legs stubbed via its test seams (`_pageOverride` + overrides). OCR is never stubbed (real Gemini + local PDF); unmapped workflows load REAL with a loud `log.error`. The flag rides `process.env` through `spawnDaemon`'s `{ ...process.env }`, so daemons inherit it from the dashboard backend. Never set the flag outside an isolated `HRAUTO_TRACKER_DIR`.

**Stub data must use canonical workflow values, not display labels (2026-06-13, VP-001).** Scripted stub step data is consumed by the SAME downstream logic as real data — e.g. the OCR orchestrator runs `computeOcrVerification` over the stub person-lookup's `active-status` output. That function lower-cases and exact-matches the canonical `ActiveCheckStatus` enum (`active`/`inactive`/`non-hdh`/…). The stub originally emitted `activeStatus: "A"` (the dashboard's A/IA **display-chip** label), which matched nothing → `lookup-failed` (error `"A"`) → every signed OCR record stayed unverified and the review pane deselected all of them, so approval needed a manual re-check of each record. Fixed to emit `"active"`. Rule: a stub returns the same *value* the real handler would (canonical enum/field shape), never a UI label. AUD-001 (low, observational): a standalone OCR `verify` run leaves a tracker row + person-lookup children but persists **no `ocr` task** in `state.db` (it completes in-handler), so a SQLite-only OCR count undercounts by the verify runs — count from tracker history, not `tasks`.

## Per-System Idle-Refresh

Long-lived daemon sessions sit idle between queued items. Systems with server-side session timeouts (UCPath, I-9 Complete, New Kronos) need periodic page reloads to stay authenticated. The kernel handles this generically — opt a system in by listing it in `src/domain/idle-refresh.ts`; every workflow that declares that system inherits the behavior automatically.

### `src/domain/idle-refresh.ts` — domain API (no Node/Playwright dependencies; safe in the client bundle)

- **`IdleRefreshCadence`** — `{ thresholdMs: number; tickMs: number }`. `thresholdMs`: reload after this much automation inactivity; `tickMs`: how often the idle timer checks.
- **`DEFAULT_IDLE_REFRESH_CADENCE`** — `{ thresholdMs: 5 * 60 * 1000, tickMs: 30 * 1000 }` (5-min threshold, 30-sec tick). Conservative for ≥15-min server timeouts.
- **`IDLE_REFRESH_SYSTEMS`** — `Readonly<Record<string, IdleRefreshCadence>>`. Current entries: `ucpath`, `i9`, and `new-kronos`, all using `DEFAULT_IDLE_REFRESH_CADENCE`. Presence here is the opt-in — add a system here to give it idle-refresh.
- **`isIdleRefreshSystem(systemId)`** — returns `true` when the system is in `IDLE_REFRESH_SYSTEMS`.
- **`idleRefreshCadence(systemId)`** — returns the `IdleRefreshCadence` for the system, or `undefined` if it doesn't opt in.

### `src/core/kernel/idle-refresh-hooks.ts`

- **`buildIdleRefreshHooks(instance, trackerDir?)`** — returns `Pick<SessionObserver, 'onIdleTouch' | 'onIdleRefresh'>`. Bridges the kernel `Session`'s idle touch/reload lifecycle into `idle_signal` session-JSONL events that drive the dashboard countdown ring. `onIdleTouch` emits a `touch` signal; `onIdleRefresh` emits `refresh_start` or `refresh_end`.

### Consumer chain

1. **`Session` (kernel)** — maintains a per-system `IdleRefreshState` map for every system in `IDLE_REFRESH_SYSTEMS ∩ launched systems`. A `setInterval` (period = `tickMs`) checks elapsed time since the last `ctx.page(<system>)` call; once inactivity exceeds `thresholdMs`, it reloads the page and fires `idleTouchCb` / `idleRefreshCb`. `Session.launch` wires those callbacks to the observer's `onIdleTouch` / `onIdleRefresh`.
   - **The idle timer is guarded across the FULL auth chain, not just `ctx.step` bodies.** Two guards suppress a reload: the `ctx.step`-body check (`idleGuard`, wired in `makeCtx` — runs *post*-auth), AND a private `authInProgress` flag set in `Session.launch` from before `loginWithRetry` until every system's readiness settles (covers login retries, the Duo prompt, and the serial Duo queue wait). Without `authInProgress`, an idle tick could fire `page.reload()` mid-Duo — navigating the prompt away (auth fails) and invalidating the armed CDP WebAuthn target while the `armedByPage` WeakMap still reports the page as armed (→ "factor not found" → manual fallback → timeout). The flag is checked in both `tickIdleRefresh` and `scheduleIdleReload`. For the 1-system fast path the flag resets in an inline `finally`; for the ≥2-system path the login IIFEs are NOT awaited by `launch`, so the flag resets when their combined `Promise.allSettled` settles (after `launch` returns). A `forWorker` child never authenticates (the parent does, on a shared context pool), so `isAuthInProgress()` walks up to the parent — the parent's auth window covers the worker's idle timer too. (2026-06-17)
2. **`buildIdleRefreshHooks`** — plugs into the `SessionObserver` (`session-observer.ts` via `buildSessionObserver`, and `batch-lifecycle.ts` via `createBatchObserver` using spread `...buildIdleRefreshHooks(instance, trackerDir)`). Translates the callbacks into `idle_signal` JSONL events.
3. **`daemon.ts`** — after each successful auth (`Session.launch`) and after each `item_complete`, emits a `touch` idle signal for every system in `wf.config.systems` that `isIdleRefreshSystem`, resetting the per-system countdown.
4. **Dashboard `WorkflowBox`** — imports `idleRefreshCadence` / `isIdleRefreshSystem` / `DEFAULT_IDLE_REFRESH_CADENCE` from the domain to render a per-system SVG countdown ring (`IdleCountdownRing`) on each system tile in the session card. The ring drains from full (just touched) to empty (reload due) over `thresholdMs`, then turns amber; a `Loader2` spinner replaces it while a reload is in progress.

## Per-Browser Health Monitor + Controls

Each system browser has a health lifecycle, bound to the dashboard tile by `browserId` (=== systemId today) — NOT by tile order — so a tile always reflects its own browser's state regardless of which sibling failed.

- **Verdict, not a boolean** — `inspectSystemHealth(id)` gathers three raw observations (closed? what url? does `evaluate(()=>1)` round-trip?) and maps them via the pure `classifyBrowserHealth` (`src/domain/browser-health.ts`) onto a verdict: `ok` / `soft` (chrome-error → refreshable) / `wedged` (dead iframe context, stalled about:blank, or a closed tab — session still valid) / `expired` (url on the SSO host → session gone) / `closed` / `dead`. `healthCheck(id)` is now `inspect(...).kind === 'ok'`. The verdicts are grounded in the UCPath taxonomy (`src/systems/ucpath/LESSONS.md`).
- **`Session` health monitor — the recovery LADDER.** A root-session timer (`HEALTH_MONITOR_TICK_MS`, default 30s; `healthMonitorOverride` for tests), skipped while auth is in progress, while a `ctx.step` body owns the page (`idleGuard`), or while an idle reload is mid-flight — so it only acts between steps / when parked. Per tick: `ok`→`healthy`; `expired`/`dead`→surface `failed` (refresh/reopen would just re-land on login); `soft`→**Refresh** (rung 1) up to `HEALTH_MONITOR_MAX_AUTO_REFRESH` (10); `wedged`/`closed`→straight to **Reopen** (rung 2) up to `HEALTH_MONITOR_MAX_REOPEN` (3); both rungs exhausted→`failed`. A hard `onBrowserDisconnect` emits `failed` separately. **No relaunch / no auto-Duo by policy** — an expired session is surfaced for re-auth, never auto-fixed.
- **`reopenSystem(id)`** — the rung-2 recovery: open a FRESH tab on the system's existing authenticated `BrowserContext` (inherits cookies → **no Duo**), navigate to `sys.resetUrl` (else the old url), verify it's usable, then **swap `slot.page`** and close the wedged one. Safe because handlers fetch `ctx.page(id)` fresh each step and reopen only fires between steps. **Doubles as the expiry probe**: if even the fresh tab lands on the SSO host, surface `failed` ("re-auth needed"). Serialized against Refresh + idle-refresh via `reloadInFlight`. `refreshSystem(id)` (rung 1, in-place reload), `focusSystem(id)` (`bringToFront`), `probeSystemHealth(id)` (one-shot probe + emit), `currentUrl(id)` round out the surface.
- **Emission** — `SessionObserver.onBrowserHealth(systemId, status, reason?, url?)` → `buildBrowserHealthHooks` → `emitBrowserHealth` writes a `browser_health` session event (wired into BOTH `buildSessionObserver` and the batch observer). `emitHealth` auto-attaches the system's `currentUrl`. `rebuildSessionState` routes it to the bound `BrowserState` (`health`/`lastError`/`url`) by `browserId` — drops a browserId-less event (no positional fallback).
- **Controls path** — `refresh_browser` / `reopen_browser` / `focus_browser` / `set_auto_recovery` worker commands + a systemId-scoped `health_check` (systemId rides the command payload; migrations 14 + 15 + 16 widened the `command_type` CHECK) → `buildRefreshBrowserHandler` / `buildReopenBrowserHandler` / `buildFocusBrowserHandler` / `buildHealthCheckBrowserHandler` / `buildSetAutoRecoveryHandler` (`control/ops/worker-control.ts`) resolve `(workflow, instance, systemId)` → worker via `workflow_start.pid` → `POST /api/browser/{refresh,reopen,focus,check,auto-recovery}`.
- **Auto-recovery pause** — `pauseAutoRecovery`/`resumeAutoRecovery`/`isAutoRecoveryPaused` let the operator freeze the monitor's auto-refresh/reopen for ONE browser (it still probes + surfaces the fault as `unhealthy`, just doesn't act) so they can inspect it. The `paused` flag auto-attaches to `browser_health` (like `url`) → `BrowserState.autoRecoveryPaused`.
- **Live peek** — `Session.screenshotSystem(id)` returns the current viewport PNG; the daemon's `GET /screenshot?system=X` returns it synchronously; the dashboard `GET /api/browser/screenshot` (resolves the daemon port via `resolveBrowserDaemonPort`) proxies + streams it to the tile's peek modal — see the broken page without finding the window.

## Invariants

- Every run mode constructs `Ctx` via `makeCtx`; never hand-roll a Ctx literal.
- `buildTrackerOpts(wf)` must stay shared across all modes so detail fields, display names, ids, and runtime warnings behave the same.
- New workflows require `operatorSubject`, `archetype`, and `runtimePolicy`.
- `data.archetype` is the canonical row-shape discriminator; delegated scope is `parentRunId`.
- SQLite is live queue/control truth. JSONL is audit/history output during transition.
- `tasks.original_input_json` preserves pristine task input; retries must replay that value, not accumulated tracker data.
- Requeued existing tasks should call `ensureDaemonsAvailable`, not `ensureDaemonsAndEnqueue`, to avoid duplicate rows.
- One active run per queue row: a fresh input run supersedes prior non-terminal runs for the same item. `enqueueFromHttp` exposes an injected `supersedePriorRuns` callback fired via `onPreparedItems` (before pre-emit/enqueue); the cancellation itself lives in `src/control/ops/supersede.ts` (core must not import control). Delegated/fan-out enqueues that call `ensureDaemonsAndEnqueue` directly never supersede.
- Delegation must route through `ctx.delegateTo` / `ctx.delegateToAll`; direct child `runWorkflow(... parentRunId ...)` and child `ensureDaemonsAndEnqueue(... parentRunId ...)` are forbidden by architecture guards.
- Cancel is one mechanism: per-run `AbortController` registered on the unified `runRegistry` (`src/core/run-registry.ts`) + Page proxy + stepper remap to `CancelledError`. Every trigger (daemon `cancel_task`, HTTP `/cancel-current`, browser-disconnect, daemon force-stop via `abortLaunchAndKillSession`, daemon shutdown sweep) calls `runRegistry.cancel(runId)`, which aborts the controller, writes the SQLite cancel audit for in-process runs, and watchdog hard-kills chromium after `hardKillAfterMs` if the run hasn't unregistered. Daemon state is a single `state.activeRun: RunHandle | null`. Do not reintroduce force-stop mode, page-navigation tricks, or the legacy `cancelTarget` / `in-process-runs` split (guard: `tests/unit/architecture/cancel-mechanism.test.ts`).
- **Force-stop must abort the in-flight run's signal — not just kill chromium.** A handler parked in a NON-Playwright, signal-only await (the only one today: oath-upload's `wait-approval` → `subscribeToApproval`, which blocks with no live browser) is invisible to the chromium kill. `createAbortLaunchAndKillSession` therefore calls `runRegistry.cancel(state.activeRun.runId, { hardKillAfterMs: 0 })` so all three force-stop entry points (`/stop`, `stop_worker`, SIGINT/SIGTERM/SIGHUP) unblock such a wait. The outer-finally `runDaemonShutdownCleanup` sweep is NOT sufficient on its own: it cannot run until the claim loop's `await runOneItem` settles, which never happens while the handler is parked — a deadlock.
- Daemon queue readers must filter to daemon workflow tasks; OCR/dependency parents can also live in `tasks`.
- **The claim lease must be RENEWED while an item runs — there are two independent liveness signals and they must agree.** A claim sets `tasks.claim_expires_at = now + leaseMs` (60s) at claim time; `recoverClaimsForDeadWorkers` re-pends a `claimed`/`running` task whose lease has expired **OR** whose worker is not in the alive set (`claim.ts`). The worker's OWN liveness is a *separate* signal — `workers.last_heartbeat_at` (15s TTL), renewed every ~5s. These diverge unless the lease is also renewed: a live worker processing an item longer than the lease (a separation easily exceeds 60s) keeps heartbeating yet its lease silently expires, so any recovery sweep (a freshly added worker's startup recovery in `daemon.ts`, or an idle peer's keepalive tick) treats the in-flight item as orphaned, re-pends it, and a second worker claims and runs the SAME item — double execution against UCPath/Kuali (masked with a single worker: no peer to claim the re-pend, and the busy daemon never runs recovery). Fix: `createEmitWorkerHeartbeat` calls `taskStore.renewClaim({ taskId, workerId })` for `state.activeRun` on every heartbeat (same 5s cadence), so a live worker's lease never looks expired; `renewClaim` is scoped `WHERE claimed_by_worker_id = @workerId AND control_state IN ('claimed','running')`, so a reassigned/terminalized task is never kept alive. The store primitive still recovers on raw lease expiry (it can't see renewal) — that's the safety net for a genuinely wedged worker (stops heartbeating → goes stale → dropped from the alive set anyway). Pinned by the `renewClaim` cases in `tests/unit/core/task-store.test.ts`. Do NOT make recovery ignore lease expiry for alive workers instead — that removes the leaked-stale-claim safety net; renew the lease at the source.
- `withTrackedWorkflow` owns real-run SIGINT; tests using `trackerStub` are the only `runWorkflow` branch with its own handler.
- `runOrdinal` is backend-assigned from earliest tracker timestamp; never derive it client-side from runId.

## Escape Hatches

- `ctx.session.page(id)` gives the raw authenticated Page.
- `ctx.isBatch` and `ctx.runId` are available for batch-only cleanup or external correlation.
- `runWorkflowPool` (per-worker Session) / `runWorkflowSharedContextPool` (one-Duo-many-tabs, as in Person Lookup) are the in-handler fan-out modes. Both are thin `WorkerStrategy` suppliers over the shared shell `runPooledBatch` (`kernel/pool-core.ts`) — the shell owns validation, `withBatchLifecycle`, the work-stealing `queue.shift()` loop, the result tally, and worker-failure isolation; the strategy supplies only how a worker acquires/releases its session. Change the worker loop once, in `pool-core.ts`. (The generic `utils/worker-pool.ts` was a third, unused skeleton — deleted 2026-06-24.)
- Person Lookup / UCPath date naming: the operator-facing "Start Date" (`data.startDate`) is **CRM First Day of Service**, stamped in cross-verification — NOT a UCPath date. UCPath `EidResult.startDate` (Last Hire) and `effectiveDate`/EFFDT are backend matching context only (ride the row as `ucpathStartDate`/`effdt`). Do not repurpose either UCPath date as the dashboard-facing start date.

Recurring escape hatches should become first-class kernel features.

## Run Isolation

Every per-item row carries `runId` + `workflowInstance`; `filterEventsForRun` trusts `runId` first. Orphan auth/browser events without `runId` are attributed only when `workflowInstance` matches and timestamps fall inside the run window. `itemInFlight` from daemon events is the live-state signal; do not infer live state from tracker rows.

## Workflow Presentation Override System

`WorkflowMetadata.presentation` (`WorkflowPresentationConfig`) is the **effective** presentation for a workflow — always present after registry normalization (`defineWorkflow` → `mergePresentation(defaultPresentationFromMetadata(...), config.presentation)`). The default mirrors today's kind-dispatch behavior so unconfigured workflows round-trip unchanged.

The serve layer merges a second override layer on top via `effectiveMetadata(meta, repoRoot)` (`src/tracker/workflow-presentation/effective.ts`), which calls `applyOverride(meta, readOverride(repoRoot, name))` → `mergePresentation`. This means `WorkflowMetadata.presentation` from `/api/workflow-definitions` is the code-default-merged value; the dashboard's Workflow Modifier page POSTs to `/api/workflow-presentation/:workflow` to write a JSON override file that `effectiveMetadata` layers on every request.

**Override store contract:** `config/workflow-presentation/<workflow>.json` — git-tracked (the directory is intentionally checked in via `.gitkeep`). Reads are fail-soft (bad JSON logs a warn and returns `null`; the dashboard keeps working). Writes are fail-loud (`WorkflowOverrideSchema.parse` throws on invalid). File location built via `workflowPresentationDir` / `workflowPresentationFile` in `src/tracker/paths.ts`.

**Apply-time semantics:**
- **Display overrides** (`naming`, `steps`, `delegation`, `label`, `category`, `iconName`, `detailFields`) apply at serve-time: `effectiveMetadata` re-reads the JSON on every `/api/workflow-definitions` request — no backend restart needed for naming/label/step-display changes.
- **Execution-affecting config** (`presets`, `skipSteps`) applies at the **next daemon spawn** — an alive daemon reads workflow config at launch, not per-item.

**Trace-scheme override caveat:** changing a workflow's `presentation.naming.trace` scheme is display/preview only in the Modifier page's `SampleRowPreview`. It changes how NEW runs compose their `__traceId` (stamped once at pre-emit), but **never recomputes an existing row's frozen `data.__traceId`** — that field is written once and never overwritten even on retry or cancel.

- **2026-07-15: One claimed run has one controller, and an aborted Playwright call poisons its page.** The daemon now creates and registers the `RunHandle` at claim time, and `runOneItem` consumes that exact caller-owned controller/session instead of constructing a second cancellation identity. A run handle is retained until the SQLite task transition is confirmed. `page-proxy.ts` never fabricates `signal` options for Playwright; it races promise-returning calls against the signal, then `Session.poisonPage` closes the suspect page with a 500ms bound and creates/navigates/verifies a replacement. Replacement failure fails loud and leaves the system poisoned until an explicit replacement/reopen succeeds; the rejected replacement promise is cleared only after `page()` observes it. `poolSize` must be a positive integer before any browser launches, and failed delegated session launch always detaches its parent abort listener. Pinned by `run-one-item.test.ts`, `page-proxy.test.ts`, `session.test.ts`, `pool.test.ts`, and `ctx-signal.test.ts`.
- **Lesson maintenance rule:** Merge dated migration notes into current invariants whenever possible.
- **2026-07-06: Three race guards — retry TOCTOU, concurrent-enqueue supersede, terminal resurrection (2026-07-04 audit).** **(1) Retry double-execution.** The control retry pre-check (`ACTIVE_STATES_BLOCKING_RETRY` in `control/ops/retry.ts`) reads `control_state` NON-transactionally; JSONL I/O (`findInheritedPriorEntry`) sits between it and the reset, so a daemon claim landing in that window used to get reset to `queued` while the worker kept running the old attempt. `retryTaskFromAttempt` now takes `blockedControlStates` and guards the reset UPDATE itself (`AND control_state NOT IN (...)`); a 0-row match throws `RetryTaskBecameActiveError` (the attempt INSERT rolls back), which `ops/retry.ts` maps to a structured “item became <state> while retrying” refusal — the same path serves `buildRetryBulkHandler` per item. The reset also bumps `claim_generation` (mirrors `returnTaskToQueued`, ISS-005) so a stale worker's lease-guarded terminal write can't overwrite the fresh retry. **(2) Concurrent enqueue supersede.** `supersedePriorRuns` is read-then-cancel and `enqueueTasks` never adopts a fresh runId, so two same-instant input runs for one item could both go live. `enqueueFromHttp` now holds a per-WORKFLOW `KeyedMutex` (`utils/keyed-mutex.ts`) across the supersede→pre-emit→enqueue critical section — in-process is sufficient because the single dashboard process owns every supersede-guarded enqueue; delegated/fan-out enqueues (no supersede option) don't take the lock. **(3) Terminal resurrection.** `markTerminal` NULLs `claimed_by_worker_id`, so `markTaskRunning`'s claimed_by-only stomp guard let a misordered caller flip a done/failed/cancelled task back to `running`. The UPDATE now also requires `control_state IN ('claimed','queued','running')`; a 0-row match on a TERMINAL row throws loud, while a non-terminal miss (peer stomp, or a cancel landing between claim and mark-running — which the old guard silently stomped back to `running`, erasing `cancel_requested`) stays a benign no-op. Pinned by `task-store.test.ts`, `retry-state-guard.test.ts`, `enqueue-dispatch-supersede.test.ts`, `keyed-mutex.test.ts`. Test gotcha: two SIMULTANEOUS first `await import()`s of a `vi.mock`ed module race vitest's interception and the loser gets the REAL module (observed: a real daemon spawned from a unit test) — stagger the first dynamic imports in concurrency tests.
- **2026-07-05: Three shutdown/recovery robustness fixes — bounded `Session.close()`, a non-silent health-monitor catch, and process-group SIGKILL — close an audit-found zombie-daemon path.** (1) **Bounded close.** `Session.close()` (`session.ts`) awaited `context.close()`/`browser.close()` per slot with NO timeout — a hung Playwright/CDP RPC wedged it forever, so `runDaemonShutdownCleanup` never ran (lockfile never unlinked, the daemon kept heartbeating as a zombie with its claimed item stranded). Fixed generically: new `withTimeout(promise, ms, label)` (`src/utils/with-timeout.ts`, `TimeoutError` on trip, timer `unref()`'d) wraps the graceful-close body; on `SESSION_CLOSE_TIMEOUT_MS` (default 15s, `HRAUTO_SESSION_CLOSE_TIMEOUT_MS`) `close()` falls back to `killChromeHard` (no Playwright RPC, so it can't hang the same way) with a `log.warn` naming the hang — a non-timeout rejection still rethrows unchanged (callers already treat `close()` as best-effort). Fixing `close()` itself (not each call site) means every caller benefits for free — daemon drain-exit, `pool.ts`/`shared-context-pool.ts` release, in-process `workflow.ts`/`run-workflow.ts` teardown. (2) **No silent monitor catch.** `tickHealthMonitor`'s outer `catch { /* best-effort */ }` swallowed a genuinely unexpected throw from `inspectSystemHealth`/`refreshSystem`/`reopenSystem` with zero trace, silently halting the recovery ladder forever (the timer keeps firing into the same silent catch every tick). Still best-effort (a monitor failure must never break the run) but now `log.warn`s the system id + error first. (3) **Process-group kill.** `killChromeHard` only SIGKILL-escalated the single captured chromium PARENT pid; in exactly the wedged case where SIGKILL fires, a parent that dies without reaping its own renderer/GPU children can leave them orphaned (darwin has no `/proc` cgroup to catch them after the fact). Fix: right before escalating (not at the earlier SIGTERM step, so a child forked during the grace period is still caught), enumerate the parent's full descendant tree and SIGKILL the set immediately after the parent. The BFS traversal (`walkDescendantPids`, exported) takes an injected child-lookup function so it's unit-testable without spawning real processes; the pgrep-backed wrapper (`listDescendantPids`) is defensive — an enumeration failure falls back to parent-only kill (today's behavior) with a `log.warn`, and `listChildPids` itself already swallows its own `pgrep` failures. Pinned by `tests/unit/utils/with-timeout.test.ts` (resolve/reject passthrough + timeout + no dangling rejection) and new `session.test.ts` cases (`close()` timeout→`killChromeHard` fallback via `vi.useFakeTimers`, health-monitor catch logs system+error via an instance monkey-patch, `walkDescendantPids` BFS/cycle-safety/empty-tree). Verified: `typecheck:all` + `test` (3655) + `test:architecture` (83) + `lint` (0 errors) all green. Not live-verified (reproducing a genuinely wedged CDP RPC or a surviving orphan renderer needs an artificially hung/wedged live browser) — the fixes are structural bounds on paths that are unreachable-but-catastrophic today, not behavior changes on the happy path.

- **2026-06-29: A lost `/wake` stranded an idle daemon's claimable queued work for the full 15-min idle window (ISS-008) — fixed with a `wakePending` latch + a bounded idle re-poll backstop.** The claim loop's `resolveWake` (HTTP `/wake`) was a bare `state.wakeResolve?.()` — a NO-OP whenever no idle waiter is armed, i.e. while the loop is suspended at a top-of-iteration await, mid-processing, or in the SYNCHRONOUS window between `claimNextItem()` returning null and the idle-wait arming its waiters. - **2026-06-24: Parallel-worker review — throughput, start-time, and teardown-accuracy fixes.** A subsystem pass over the daemon/pool/task-store concurrency machinery. **(1) Claim is an index seek, not a sort.** `claimNextTask`'s `ORDER BY` dropped `COALESCE(enqueued_at, created_at)` → plain `enqueued_at` (daemon `workflow_item` rows ALWAYS stamp `enqueued_at` at enqueue, and re-pend preserves it).
