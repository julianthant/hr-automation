# Core — Workflow Kernel

Declarative workflow runtime. Cross-workflow execution behavior, cancellation, task/control contracts, and new `Ctx` capabilities belong here, not in individual workflow handlers.

## Public Surface

- `defineWorkflow({...})` declares workflow metadata, schema, systems, steps, archetype, runtimePolicy, operator subject, and handler.
- `ctx.page(id)` waits for auth and returns a Playwright Page proxy that injects per-run `ctx.signal` into signal-aware methods.
- `ctx.signal` is the per-run AbortSignal. Pass it to non-Playwright awaits that support cancellation.
- `ctx.step(name, fn)` emits step status, captures screenshots on failure, and maps aborts to the standard cancelled terminal row.
- `ctx.updateData(patch)` writes operator-facing fields into tracker data.
- `ctx.workflowInstance` is the session-drawer instance name owning the run; `ctx.reportPhase(step)` pushes a phase into the terminal-drawer timeline (session `item_start`+`step_change`) **without** a queue row — for handlers that emit their own rows and bypass `ctx.step` (today only OCR). Every other handler drives the timeline for free via `ctx.step`/`ctx.markStep`.
- `ctx.parallel({...})` runs named tasks with `Promise.allSettled`.
- `ctx.delegateTo` / `ctx.delegateToAll` compose workflows. The kernel owns `parentRunId`, pending-row pre-emits, input persistence, and child watching.

Auth is global: one system uses the fast path; multiple systems use parallel prepare + staggered Duo submit. See `src/infra/auth/CLAUDE.md`.

## Daemon Mode

Dashboard input runs use daemon mode when the workflow is registered in `src/core/workflow-loaders.ts`.

- First run with no alive daemon spawns `tsx src/cli-daemon.ts <workflow>`, authenticates once, then enqueues work.
- Later runs insert into SQLite `tasks` and wake alive daemons; no re-Duo.
- Daemons race to claim queued work through SQLite, not JSONL.
- Idle daemons keep sessions warm with periodic `session.healthCheck(system)`.
- `npm run <workflow>:stop` drains in-flight work; `-- --force` marks it failed immediately.
- **Stopping daemons (operator pool model).** The daemon `/stop` body carries `{ force?, reassign? }`. `reassign` decides the IN-FLIGHT item's fate at teardown: with `reassign: true` (dashboard **per-instance** card stop, `/api/daemon/stop-instance`) AND a surviving peer daemon, the item is un-claimed (`returnTaskToQueued`) and the peers are woken so an idle one finishes it; with `reassign` omitted (workflow-scoped "stop all" `/api/daemon/stop`, SIGINT/SIGTERM) or when this is the **last** daemon, the in-flight item **fails** (red — no `step:"cancelled"` sentinel). Queued (never-claimed) items are left for surviving peers, or failed by the last daemon's cleanup. A deliberate per-item `/cancel-current` is unaffected (daemon stays alive → orange Cancelled). The three-way branch lives in the claim loop (`daemon.ts`) and the outer-finally safety net (`shutdown.ts`).

### E2E stub mode (`HRAUTO_E2E_STUBS=1`)

For the AI e2e test (real dashboard + real daemons, no real external systems), `loadWorkflow` wraps mapped workflows with scripted stub handlers — `src/core/e2e/stub-workflows.ts`. The clone keeps the real metadata/steps/schema/archetype/trace code but sets `systems: []` (no browsers, no Duo) and walks the real step list, stamping the same operator-data fields from the real input plus `data.e2eStub: "true"` for provenance. Steps honor file-based hold gates (`<trackerDir>/e2e-gates/<workflow>[--<step>].hold`, helpers in `tracker/paths.ts`, polling in `core/e2e/gates.ts`) so an e2e driver can deterministically park runs "running" (cancel/reassign tests) and release them; an abort while parked unwinds to the standard cancelled row.

Steps also honor a one-shot **fail gate** (`<trackerDir>/e2e-gates/<workflow>--fail-at--<step>.fail`, `e2eGateFailPath` / `consumeFailGate`): the driver arms it to make the scripted step throw `E2EScriptedFailError` — a genuine **non-cancel** error (NOT a `CancelledError`), so the kernel stepper runs `emitFailed` and the daemon writes a terminal `failed` row (red badge + Retry button), the organic-failure path the retry-coverage leg exercises (`Phase 4`). It is checked AFTER the hold release (park-then-arm) but BEFORE the step's success-data patch (a failed step stamps no success data), and SELF-CONSUMES on fire (deletes the file) so the Retry replay — which replays `tasks.original_input_json`, not accumulated data — sees no gate and walks to `done` with no manual cleanup. Pinned by `gates.test.ts` + `stub-workflows.test.ts`. oath-upload runs its REAL handler (wait-approval/wait-signatures are the machinery under test) with only the ServiceNow legs stubbed via its test seams (`_pageOverride` + overrides). OCR is never stubbed (real Gemini + local PDF); unmapped workflows load REAL with a loud `log.error`. The flag rides `process.env` through `spawnDaemon`'s `{ ...process.env }`, so daemons inherit it from the dashboard backend. Never set the flag outside an isolated `HRAUTO_TRACKER_DIR`.

**Stub data must use canonical workflow values, not display labels (2026-06-13, VP-001).** Scripted stub step data is consumed by the SAME downstream logic as real data — e.g. the OCR orchestrator runs `computeOcrVerification` over the stub person-lookup's `active-status` output. That function lower-cases and exact-matches the canonical `ActiveCheckStatus` enum (`active`/`inactive`/`non-hdh`/…). The stub originally emitted `activeStatus: "A"` (the dashboard's A/IA **display-chip** label), which matched nothing → `lookup-failed` (error `"A"`) → every signed OCR record stayed unverified and the review pane deselected all of them, so approval needed a manual re-check of each record. Fixed to emit `"active"`. Rule: a stub returns the same *value* the real handler would (canonical enum/field shape), never a UI label. AUD-001 (low, observational): a standalone OCR `verify` run leaves a tracker row + person-lookup children but persists **no `ocr` task** in `state.db` (it completes in-handler), so a SQLite-only OCR count undercounts by the verify runs — count from tracker history, not `tasks`.

## Per-System Idle-Refresh

Long-lived daemon sessions sit idle between queued items. Systems with server-side session timeouts (UCPath, I-9 Complete) need periodic page reloads to stay authenticated. The kernel handles this generically — opt a system in by listing it in `src/domain/idle-refresh.ts`; every workflow that declares that system inherits the behavior automatically.

### `src/domain/idle-refresh.ts` — domain API (no Node/Playwright dependencies; safe in the client bundle)

- **`IdleRefreshCadence`** — `{ thresholdMs: number; tickMs: number }`. `thresholdMs`: reload after this much automation inactivity; `tickMs`: how often the idle timer checks.
- **`DEFAULT_IDLE_REFRESH_CADENCE`** — `{ thresholdMs: 5 * 60 * 1000, tickMs: 30 * 1000 }` (5-min threshold, 30-sec tick). Conservative for ≥15-min server timeouts.
- **`IDLE_REFRESH_SYSTEMS`** — `Readonly<Record<string, IdleRefreshCadence>>`. Current entries: `ucpath` and `i9`, both using `DEFAULT_IDLE_REFRESH_CADENCE`. Presence here is the opt-in — add a system here to give it idle-refresh.
- **`isIdleRefreshSystem(systemId)`** — returns `true` when the system is in `IDLE_REFRESH_SYSTEMS`.
- **`idleRefreshCadence(systemId)`** — returns the `IdleRefreshCadence` for the system, or `undefined` if it doesn't opt in.

### `src/core/kernel/idle-refresh-hooks.ts`

- **`buildIdleRefreshHooks(instance, trackerDir?)`** — returns `Pick<SessionObserver, 'onIdleTouch' | 'onIdleRefresh'>`. Bridges the kernel `Session`'s idle touch/reload lifecycle into `idle_signal` session-JSONL events that drive the dashboard countdown ring. `onIdleTouch` emits a `touch` signal; `onIdleRefresh` emits `refresh_start` or `refresh_end`.

### Consumer chain

1. **`Session` (kernel)** — maintains a per-system `IdleRefreshState` map for every system in `IDLE_REFRESH_SYSTEMS ∩ launched systems`. A `setInterval` (period = `tickMs`) checks elapsed time since the last `ctx.page(<system>)` call; once inactivity exceeds `thresholdMs`, it reloads the page and fires `idleTouchCb` / `idleRefreshCb`. `Session.launch` wires those callbacks to the observer's `onIdleTouch` / `onIdleRefresh`.
2. **`buildIdleRefreshHooks`** — plugs into the `SessionObserver` (`session-observer.ts` via `buildSessionObserver`, and `batch-lifecycle.ts` via `createBatchObserver` using spread `...buildIdleRefreshHooks(instance, trackerDir)`). Translates the callbacks into `idle_signal` JSONL events.
3. **`daemon.ts`** — after each successful auth (`Session.launch`) and after each `item_complete`, emits a `touch` idle signal for every system in `wf.config.systems` that `isIdleRefreshSystem`, resetting the per-system countdown.
4. **Dashboard `WorkflowBox`** — imports `idleRefreshCadence` / `isIdleRefreshSystem` / `DEFAULT_IDLE_REFRESH_CADENCE` from the domain to render a per-system SVG countdown ring (`IdleCountdownRing`) on each system tile in the session card. The ring drains from full (just touched) to empty (reload due) over `thresholdMs`, then turns amber; a `Loader2` spinner replaces it while a reload is in progress.

## Invariants

- Every run mode constructs `Ctx` via `makeCtx`; never hand-roll a Ctx literal.
- `buildTrackerOpts(wf)` must stay shared across all modes so detail fields, display names, ids, and runtime warnings behave the same.
- New workflows require `operatorSubject`, `archetype`, and `runtimePolicy`.
- `data.archetype` is the canonical row-shape discriminator; delegated scope is `parentRunId`.
- SQLite is live queue/control truth. JSONL is audit/history output during transition.
- `tasks.original_input_json` preserves pristine task input; retries must replay that value, not accumulated tracker data.
- Requeued existing tasks should call `ensureDaemonsAvailable`, not `ensureDaemonsAndEnqueue`, to avoid duplicate rows.
- Delegation must route through `ctx.delegateTo` / `ctx.delegateToAll`; direct child `runWorkflow(... parentRunId ...)` and child `ensureDaemonsAndEnqueue(... parentRunId ...)` are forbidden by architecture guards.
- Cancel is one mechanism: per-run `AbortController` registered on the unified `runRegistry` (`src/core/run-registry.ts`) + Page proxy + stepper remap to `CancelledError`. Every trigger (daemon `cancel_task`, HTTP `/cancel-current`, browser-disconnect, daemon force-stop via `abortLaunchAndKillSession`, daemon shutdown sweep) calls `runRegistry.cancel(runId)`, which aborts the controller, writes the SQLite cancel audit for in-process runs, and watchdog hard-kills chromium after `hardKillAfterMs` if the run hasn't unregistered. Daemon state is a single `state.activeRun: RunHandle | null`. Do not reintroduce force-stop mode, page-navigation tricks, or the legacy `cancelTarget` / `in-process-runs` split (guard: `tests/unit/architecture/cancel-mechanism.test.ts`).
- **Force-stop must abort the in-flight run's signal — not just kill chromium.** A handler parked in a NON-Playwright, signal-only await (the only one today: oath-upload's `wait-approval` → `subscribeToApproval`, which blocks with no live browser) is invisible to the chromium kill. `createAbortLaunchAndKillSession` therefore calls `runRegistry.cancel(state.activeRun.runId, { hardKillAfterMs: 0 })` so all three force-stop entry points (`/stop`, `stop_worker`, SIGINT/SIGTERM/SIGHUP) unblock such a wait. The outer-finally `runDaemonShutdownCleanup` sweep is NOT sufficient on its own: it cannot run until the claim loop's `await runOneItem` settles, which never happens while the handler is parked — a deadlock.
- Daemon queue readers must filter to daemon workflow tasks; OCR/dependency parents can also live in `tasks`.
- `withTrackedWorkflow` owns real-run SIGINT; tests using `trackerStub` are the only `runWorkflow` branch with its own handler.
- `runOrdinal` is backend-assigned from earliest tracker timestamp; never derive it client-side from runId.

## Escape Hatches

- `ctx.session.page(id)` gives the raw authenticated Page.
- `ctx.isBatch` and `ctx.runId` are available for batch-only cleanup or external correlation.
- `runWorkerPool` / shared-context pool modes are for in-handler fan-out sharing authenticated sessions, as in Person Lookup's one-Duo-many-tabs pattern.
- Person Lookup / UCPath date naming: the operator-facing "Start Date" (`data.startDate`) is **CRM First Day of Service**, stamped in cross-verification — NOT a UCPath date. UCPath `EidResult.startDate` (Last Hire) and `effectiveDate`/EFFDT are backend matching context only (ride the row as `ucpathStartDate`/`effdt`). Do not repurpose either UCPath date as the dashboard-facing start date.

Recurring escape hatches should become first-class kernel features.

## Run Isolation

Every per-item row carries `runId` + `workflowInstance`; `filterEventsForRun` trusts `runId` first. Orphan auth/browser events without `runId` are attributed only when `workflowInstance` matches and timestamps fall inside the run window. `itemInFlight` from daemon events is the live-state signal; do not infer live state from tracker rows.

## Lessons Learned

- **Lesson maintenance rule:** Merge dated migration notes into current invariants whenever possible.
- **2026-06-13: ISS-001 — `ensureDaemonsAndEnqueue` woke daemons BEFORE writing SQLite task rows, so an idle daemon's `/wake`-triggered re-poll found nothing claimable and re-idled; the task then sat `queued` until the 15-min keepalive tick (`POST /wake` was the manual workaround, including for the OCR person-lookup enrichment pipeline).** Fix: `ensureDaemonsAvailable` gained `skipWake?: boolean` (default `false`); `ensureDaemonsAndEnqueue` passes `skipWake: true` and calls `await wakeDaemons(daemons)` AFTER `enqueueItems` succeeds, so the daemon's claim loop finds claimable work on its first re-poll. The requeue/retry caller (`retry.ts` → `ensureDaemonsAvailable` direct) keeps the immediate wake because its task row already exists in SQLite. Distinct from the 2026-06-12 `wakeDaemonsForReleasedParents` lesson (that covers dependency-RELEASE sites; this is the fresh-ENQUEUE site). Pinned by `daemon.test.ts` ("ensureDaemonsAndEnqueue wakes an idle daemon after enqueue (no manual /wake) — ISS-001").
- **2026-06-12: Dependency release wakes the released parents' daemons, and a `task_kind=ocr` anchor terminalizes at the release site (E2E-017/E2E-003).** `markDependencyFromChildTerminal` / `releaseParentsIfDependenciesSatisfied` (core/task-store/child-state.ts) return the parents they flipped `waiting_dependencies→queued` (`ReleasedParentTask[]`), and every settle site — the daemon claim loop's done/failed/cancelled branches, the shutdown queued-item sweep, and the dashboard queued-cancel — fires the best-effort `wakeDaemonsForReleasedParents` (daemon/client.ts). Without the wake, a released task (an oath-upload ticket whose signers finished) sat queued until the parent daemon's 15-min keepalive tick; `POST /wake` was the manual workaround. The wake only pokes already-alive daemons — a released task with no daemon is the orphan sweep's concern, never a spawn trigger. A parent whose `task_kind` is `ocr` is a dependency ANCHOR, not daemon work: the release terminalizes it (`done`) instead of queueing it — the generic settle usually wins the race against the OCR scheduler's tick, and a queued `ocr` task is unclaimable (a zombie per prep). Pinned by `task-store.test.ts`.
- **2026-06-07: Reassign-to-peer health-checks the peer first; a wedged peer fails the item LOUD (fail-loud over eventual-recovery).** `findAliveDaemons` deliberately TRUSTS an unreachable-but-PID-alive lockfile (probe `unreachable` + PID alive → keep it) so it won't orphan a momentarily-busy daemon and spawn a duplicate. But the per-instance-stop reassign decision treated `peers.length > 0` as "a peer will finish this item" — so a stop whose only peer was a wedged/zombie daemon (PID alive, event loop never wakes to claim) re-queued the in-flight item, which then sat `queued` FOREVER. Fix (F5): `registry.ts` exports `isDaemonResponsive(daemon)` / `filterResponsiveDaemons(daemons)` — a STRICT `/whoami` probe that returns true only on `match` (NOT the lenient `unreachable && PID-alive` that `findAliveDaemons` accepts). Both reassign sites — the claim-loop `isCancelOutcome` branch (`daemon.ts`) and the outer-finally safety-net (`shutdown.ts`) — now `filterResponsiveDaemons(peers)` before reassigning; only a positively-responding peer absorbs the item. If reassign was requested but NO peer responds, the item FAILS loud (terminal red, retriable — same shape as a no-peer force-stop) instead of parking. The claim loop fires first, so it MUST carry the check too (a shutdown-only fix leaves the item `queued`). Pinned by `daemon.test.ts` (responsive peer stands up a real `/whoami` server → re-queue; wedged peer with a dead port → `task.state === 'failed'`).
- **2026-06-07: Reassign/fail-in-flight logic is shared between the claim loop and the shutdown sweep (`in-flight-shutdown.ts`).** The two teardown paths (`daemon.ts` claim-loop + `shutdown.ts` outer-finally) mirrored ~120 lines each; they MUST agree on row shape / error text / dependency-settle or they silently drift. `src/core/daemon/in-flight-shutdown.ts` owns `emitShutdownRow`, `reassignInFlightItem`, `failInFlightItem`, and the two canonical fail strings (`SHUTDOWN_NO_DAEMON_FAIL_REASON` / `SHUTDOWN_NO_RESPONSIVE_PEER_FAIL_REASON`). Two flags preserve the paths' pre-existing differences: `bestEffort` (shutdown wraps each step in try/catch for the SIGINT grace window; the claim loop lets them throw) and `settleDependency` (the claim-loop fail branches settle the child→parent dependency edge; shutdown's in-flight fail branches do NOT — only its QUEUED-item sweep settles). `buildShutdownTrackerData` (+ `preserveFrozenTraceId` / `ShutdownTrackerDataOpts`) moved into this module to break the shutdown↔helpers cycle; `shutdown.ts` re-exports it so `daemon.ts` + the shutdown test keep their import path.
- **2026-06-07: Per-instance daemon stop reassigns the in-flight item to a surviving peer (else fails) — reverses the 2026-04-28 "always fail, never requeue" rule.** Operators now run a POOL of daemons (e.g. 4 idle Person Lookup), so the session card's stop is **per-instance** (`/api/daemon/stop-instance` → `buildStopDaemonInstanceHandler` → the one daemon's `/stop` with `{ reassign: true }`), not the old workflow-scoped tear-down (that's still the queue toolbar's StopAllButton → `/api/daemon/stop`). The daemon `/stop` body gained `reassign` (`http.ts` parses it → `state.reassignInFlight`; the `force` field still always force-tears-down). An aborted controller now resolves THREE intents in the claim-loop `isCancelOutcome` branch (and the `shutdown.ts` outer-finally safety net): (1) **reassign** — `state.reassignInFlight && otherAlive.length > 0` → `taskStore.returnTaskToQueued({taskId})` (the un-claim primitive already used by dead-worker recovery; preserves the attempt/runId so the run continues on the peer), emit a `pending` row so the dashboard shows it back in queue, `wakeDaemons(peers)`; no terminal row, no dependency settle. (2) **fail (red)** — `state.forceShutdown` with no spare (stop-all, SIGINT, or the last daemon) → `markItemFailed` + a `status:'failed'` row with NO `step:"cancelled"` sentinel (operator asked to SEE these fail). (3) **cancel (orange)** — neither flag set (deliberate `/cancel-current`, daemon stays alive) → unchanged `step:"cancelled"`. `otherAlive` is `findAliveDaemons(workflow).filter(d => d.instanceId !== self)` computed before the lockfile unlink (self still in the alive set). Why gate reassign on an EXPLICIT flag, not just `forceShutdown`: a workflow-scoped "stop all" would otherwise have every daemon try to bounce its item to peers that are ALSO dying → items orphaned. Queued (never-claimed) items needed no new logic — `shutdown.ts` already leaves them for peers when `otherAlive>0` and only the last daemon terminalizes them (now as failed, not cancelled). Pinned by `daemon.test.ts` ("per-instance /stop with a surviving peer RE-QUEUES the in-flight item" + the updated signal-wait test now asserting `failed` for a lone-daemon force-stop). Not a force-stop-mode revival — no new cancel mechanism, so `cancel-mechanism.test.ts` stays green.
- **2026-06-04: Daemon force-stop deadlocked on a signal-only wait (oath-upload `wait-approval`).** The dashboard session-card **stop** (`/api/daemon/stop` → daemon `/stop`) appeared to do nothing for an oath-upload daemon parked in `wait-approval`: the toast said "Stop sent — 1 session cleared" but the daemon stayed alive (lockfile present, heartbeating), the session card persisted, and the queue row stayed `running` with the elapsed timer climbing. Root cause: the force-stop path (`/stop` HTTP handler, `stop_worker` worker command, SIGINT/SIGTERM/SIGHUP) tore the daemon down by setting `shuttingDown`/`forceShutdown`, resolving the idle-wait promises (no-ops during `processing`), and `abortLaunchAndKillSession` (abort the LAUNCH controller + `killChromeHard`). That unwinds an in-flight item ONLY if the handler is blocked inside a Playwright call (chrome death → "browser closed" rejection). oath-upload's `wait-approval` step parks on `subscribeToApproval` — a pure in-memory promise + unref'd JSONL poll, gated solely on `ctx.signal` — with NO live browser (ServiceNow auth is deferred until after the wait). So killing chrome did nothing; the claim loop stayed blocked on `await runOneItem`, never re-observed `shuttingDown`, and never reached the outer-finally `runDaemonShutdownCleanup` sweep (the one place that would `runRegistry.cancel` the active run). Fix: `createAbortLaunchAndKillSession` now also `runRegistry.cancel(state.activeRun.runId, { hardKillAfterMs: 0 })`, mirroring the browser-disconnect path — so every force-stop entry point aborts `ctx.signal`, which rejects `subscribeToApproval` (`OcrApprovalCancelledError`) and lets the daemon exit and terminalize the item (now **Failed** for a lone-daemon force-stop per the 2026-06-07 reassign-or-fail rule above; the underlying signal-abort/unwind is what this lesson is about). Manual unstick for a wedged daemon: `POST /cancel-current {itemId,runId}` to its port (that path already aborts the signal), or discard/approve the OCR prep (the JSONL backstop poll picks it up within ~10s). Pinned by `daemon.test.ts` ("/stop force-cancels an in-flight handler parked in a signal-only wait").
- **2026-06-02: `ensureDaemonsAndEnqueue` derives the item id from the CLEANED logical input, and an empty id fails loud.** `delegateTo`/`delegateToAll` wrap every input with `__runtimeOptions` (rowShape/rootCode/rootTracePrefix) before id derivation, so the daemon enqueue's `idFn` now runs `splitPrefilled(input)` and calls `deriveItemId(cleaned)` (matching the HTTP `enqueue-dispatch.ts` path) and **throws** if the derived id is empty. Bug it fixed: OCR's verify/i9 fan-out (and force-research) build an identity map keyed by `JSON.stringify(originalInput)` and look up by `deriveItemId(wrappedInput)`; the `__runtimeOptions` made the JSON differ → miss → `?? ""` → empty `item_id`. Empty ids are rejected by `isTrackerEntry` (id must be non-empty) → rows invisible in the queue + `[jsonl] skipping invalid line` spam, while the rail's amber badge (control-DB `readQueueDepth`) still counted the queued tasks ("items in queue but nothing in the panel"). Custom `deriveItemId`s should key on a stable input field, never object identity, and never return `""`. Guidance lives in the `workflow-scaffold` skill's `references/pitfalls.md` ("Item identity").
- **2026-06-02: `ctx.parentRunId` exposes delegated scope to self-emitting handlers.** The kernel stamps `parentRunId` on the rows IT emits, but a delegation never injects it into the child *input* (it's a `runWorkflow` option, not an input field). A handler that owns its own tracker emission (today only OCR's orchestrator, which bypasses `ctx.step`) therefore had no way to re-stamp it and its latest-wins rows looked standalone — which hid OCR's Approve button. `parentRunId` is now threaded `run-workflow`/`run-one-item` → `runWorkflowHandler` → `makeCtx` and surfaced on `Ctx`. OCR forwards `ctx.parentRunId` into its orchestrator input so every self-emitted row carries it. Normal handlers don't need it — `ctx.step`/`delegateTo` already stamp parentRunId for free.
- **2026-05-31: `queueRowKind` + `__traceId` must ride EVERY row, not just `pending`.** They were stamped only by `buildPendingTrackerData` (the pre-emit path); live rows (`running`/`done`/`failed` + the synthetic auth-timing rows) build their `data` from `stringifiedSeed` → `withTrackedWorkflow`, which carries `__subject`/`archetype` but not these two. Because the dashboard collapses a run to its *latest* row (`dedupeLatestByIdWithCarriedEmplId`), the kind/trace-id vanished the instant the run left `pending`, and the kind-driven title/subtitle fell back. **There are TWO seed paths and both needed the fix:** `run-one-item.ts` (the daemon-worker path; also what `tests/scenarios` exercise) AND `run-workflow.ts` (the in-process `runWorkflow` real-run path used by non-daemon `delegateTo` children — OCR preview, sharepoint-download — and `delegateToAll`). Both build a seed via `buildInitialTrackerData` then hand it to `withTrackedWorkflow`; the fix seeds `queueRowKind` (recomputed via `resolveQueueRowKindFromValue`) and `__traceId` onto that seed so they propagate to every emission. The trace id is **frozen once** — read back from the run's first pending row via `findFrozenTraceId` (shared helper in `find-latest-entry.ts`), falling back to a fresh `buildTraceId`. For a bare in-process `runWorkflow` with NO `preAssignedRunId` (e.g. SharePoint "Onboarding Roster"), `withTrackedWorkflow` now receives `traceCode` from `run-workflow.ts` and freezes `__traceId` after it mints the run id but BEFORE its own pending emit; use the UUID suffix after `#` for the tail, not the stable item id. The daemon worker's own `pending` re-emit passes the frozen id to `buildPendingTrackerData`'s new `traceId` opt so it doesn't recompute a time-drifted one. **Gotcha:** `withTrackedWorkflow` SKIPS its own pending emit when `preAssignedRunId` is provided — so don't synthesize a runId just to stamp the trace id, or you'd suppress the pending row. Pinned by `find-frozen-trace-id.test.ts`, `pending-data-root-code.test.ts`, `run-workflow-kind-trace.test.ts`.
- **2026-05-31: Cancel/shutdown rebuilt rows must inherit the frozen `__traceId`.** `buildShutdownTrackerData` re-derives a cancelled/terminalized row's `data` from `input`, which reproduces name/EID/archetype/queueRowKind but NOT `data.__traceId` — the trace id is stamped once at pre-emit with the original timestamp, so rebuilding would mint a *different* id than the pending row showed. It now accepts `{ runId, trackerDir }` and copies the frozen trace id forward from the run's pending row via the shared `findFrozenTraceId` helper (`preserveFrozenTraceId` wrapper). All three callers pass it: the daemon claim-loop cancel emit and both `shutdown.ts` terminalize sites (in-flight + queued). Invariant: cancellation changes `status` only, never the row's trace-id identity. Pinned by `tests/unit/core/daemon/shutdown.test.ts`.
