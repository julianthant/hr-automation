# Dashboard

React SPA for real-time workflow monitoring: queue on the left, log/detail surface on the right.

## Stack

- React 19, Vite 8, Tailwind CSS v4, shadcn/ui primitives, lucide-react, sonner.
- HeroUI is only used for the date calendar and its stylesheet.
- Theme tokens live in `index.css`; fonts are Inter and JetBrains Mono.
- No framer-motion.

## UI editing rules

Follow these when adding or editing ANY dashboard component. Items marked **[guarded]** fail `tests/unit/architecture/frontend-tailwind-compliance.test.ts` — run `npm run test:architecture` before declaring UI work done.

- **Color = design tokens only. [guarded]** Never use Tailwind palette classes (`text-sky-500`, `bg-amber-400`, `border-slate-700`) or raw `#hex` / `rgb()` / `hsl()` literals in `.tsx`. Use the semantic tokens — `primary`, `secondary`, `muted`, `accent`, `destructive`, `info`, `success`, `warning`, `border`, `ring`, `foreground`/`background`, `sidebar*` — or the categorical log accents `log-cyan|log-teal|log-violet|log-slate`. House tint pattern: `bg-<token>/12–15` + solid `text-<token>` + `border-<token>/30` (see `shared/status-styles.ts`). Need a color the tokens don't cover? **Add a token** to `index.css` (light `:root` + `.dark` + the `@theme inline` `--color-*` map), don't inline it. The ONLY sanctioned raw hex is `#4ade80` / `#fbbf24`.
- **Icons = lucide, never glyphs.** Use `lucide-react` components — never unicode/emoji characters (`▲ ← ● ⚠ ✓ ✗`) as icons. An icon-only button needs an `aria-label` (or `title` / sr-only text); a decorative icon inside an already-labeled control gets `aria-hidden`.
- **Interactive = real elements.** Use `<button>` / `<a>`, not `<div onClick>`. If a non-button must be clickable, add `role`, `tabIndex={0}`, AND an `onKeyDown` (Enter/Space) plus `cursor-pointer`. Any `<button>` that is not a form submit gets `type="button"`.
- **Focus stays visible.** Don't `outline-none` without a replacement. The global base (`index.css`) gives native elements an `outline-ring/50` focus ring; if you override it, add `focus-visible:ring-2 focus-visible:ring-ring` — a background-tint-only focus state is too weak.
- **Async / live regions announce.** Streaming logs, live counts, validation, and status that change without a user action need `aria-live="polite"` (or `role="alert"` for blocking errors). Buttons firing async actions disable while pending.
- **Contrast + labels.** `text-muted-foreground` (and any `/NN` opacity on it) is for secondary/hint text only — primary titles and meaningful values use `text-foreground`. Every form control needs a `<label htmlFor>` or `aria-label`; a placeholder is not an accessible name.
- **Motion / layout. [guarded]** Animations use Tailwind utilities with `motion-safe:` / `motion-reduce:animate-none` (no `@keyframes`, no inline `animation:`); z-index stays on the `z-*` scale (no `z-[...]`); `<img>` needs `srcSet` + `sizes` + `loading`/`fetchPriority`; use `shrink-0`, not `flex-shrink-0`.

## Operator Text

Use the shared operator subject (`data.__subject`) as primary text for toasts, queue rows, delegation batches, and batch members. Raw run ids/session ids are fallback or debug detail only.

Dashboard controls mutate SQLite control state first and let workers observe commands. JSONL writes are audit/history. Do not add controls that only flip React state or indiscriminately kill Chromium processes.

## Backend

The SSE/API server is Hono under `src/tracker/dashboard/hono/`, created by `src/tracker/dashboard/server.ts`. Vite dev runs on `:5173` and proxies `/api/*` + `/events/*` to `:3838`; prod serves the built dashboard from the Hono server.

Full API and event reference: `docs/engineering/dashboard-api-reference.md`.

## Workflow Metadata

Frontend labels, detail fields, steps, and display helpers come from the server-side workflow registry via `/api/workflow-definitions`. Do not add frontend-side workflow label/detail hardcoding.

For a new workflow:
- Declare `label`, `getName`, `getId`, and `detailFields` in `defineWorkflow`.
- Add log icon patterns only if new message patterns need icons.
- Run the dashboard and verify entries, steps, and detail fields populate from `ctx.updateData`.

- **2026-06-04: A batch card's footer id identifies the PARENT run, derived from `parentRunId` — members keep their own.** `buildProjectionFromQueueSurface` no longer borrows `members[0]`'s trace as the batch anchor subtitle (`deriveBatchAnchorSubtitle` in `projection.ts`): for a `batch` surface it composes `<sharedPrefix>-<runIdFragment(parentRunId)>` from the anchor's trace prefix + the parent runId4. With a real parent row this equals the parent's own trace (no-op); the fix matters for a cross-workflow delegated batch with NO parent row in panel (person-lookup / oath-signature fan-out under an OCR operation), which previously leaked the member's tail as the parent footer id. - **2026-06-04: Operation children are `operation-member`, the operation analogue of `batch-member`.** The OCR approve fan-out stamps `operation-member` (via the `rowShape` runtime option, gated on `isOperationCoordinatorWorkflow(operationWorkflow)`) so signer/contact rows nest inside the `operation` coordinator's expand section instead of becoming standalone rows or separate batch anchors. They still render as full `EntryItem` single rows (`operation-member` → `single` surface type in `entrySurfaceType`); the change is the shape/taxonomy + trace-id parity (coordinator footer = its own trace, members keep their tails). This also fixed a latent EC bug: emergency-contact (archetype `batch`) operation children were previously stamped `batch` → would have become separate anchors instead of nesting.
- **Unified footer contract (2026-06-01, status-gated):** Every flat queue footer (`EntryItem`, including batch members) renders one ordered button schema — `time · #run · id · ⟨spacer⟩ · elapsed/duration · ▲ bump · ↻ retry · × cancel · 🗑 delete`. Each button self-hides on its kernel action descriptor's `enabled` flag; **the projection sets `enabled` per status** via `rowActionEnabledForStatus` (`src/domain/workflow-runtime/projection.ts`), the single source of truth for the matrix: **running → ×** · **queued → ▲ ×** · **done/failed → ↻ 🗑** (a queued row has no delete — cancel it first, which makes it terminal, then 🗑 appears; cancelled is `failed`+`step=cancelled` → terminal → ↻ 🗑). The buttons (`BumpButton`, `RetryButton`, `RowCancelButton`, `DeleteButton` in `shared/`) still never branch on `entry.status` themselves — they only read descriptors — so the schema stays kernel-driven; status-gating lives in the projection, not the component. The default policy carries all four row actions (`DEFAULT_ROW_ACTIONS`, `default-policy.ts`); workflows inherit them. `RowCancelButton` routes by the cancel target's status (running → `status:"running"`, queued → queued handler, OCR-prep → discard) via the pure `buildRowCancelDispatchArgs` (`lib/row-cancel-request.ts`). This **replaces** the prior "always retry+delete, no status gating" rule and the dead `CancelRunningButton`/`QueueItemControls` (removed). The toolbar Stop + drawer `StopPill` remain the daemon-scoped stop; the footer × is the per-row cancel.
  - **Batch/group footers** (`DaemonBatchRow`/`DelegationRow` via `BatchFooterActions`/`ApprovalDelegationFooterActions`) keep their own bulk selection (retry-all / delete-all / cancel-all over members); they are not status-gated per the matrix above (a group spans mixed-status members). Don't bump a group.
- **2026-06-01: 0-member batch footers fall back to the anchor.** `DaemonBatchRow` derived footer time / elapsed / retry+delete from `memberEntries`, so a `batch` anchor with no members yet (e.g. the oath-signature PDF row during OCR approval — visible under the "all" filter via `queueGroupMatchesStatusFilter(null, []) === true`) rendered a degenerate footer (bare `#run`, no time/elapsed/actions). Fix: `DaemonBatchRow` takes an `anchorEntry` prop and uses `footerEntries = members.length ? members : [anchor]` for `firstTimestamp`, `elapsedEntries`, and `BatchFooterActions` targets; `members` stays empty so the count badge/progress bar still read 0/0. `QueuePanel` passes `anchorEntry={surface.parent}`. Surfaced by the dev UI gallery's ("?view=ui-gallery") "0 members (pre-fan-out)" variant — the gallery reuses the real component, so footer regressions show up there.
- **Prep and delegation cards:** OCR rows are `preview`; batch rows are real batch anchors. Multi-file upload is N independent preview runs, not one grouped parent card.
- **Status:** Queue row status semantics resolve from per-workflow **`statusExtensions`** (declared on `defineWorkflow`) via `src/domain/queue-row-status.ts` — the single source for `EntryItem`'s derived status (`notFound`, `needsReview`) and supplemental tag (person-lookup A/IA). `EntryItem` is workflow-agnostic: it calls `resolveQueueRowStatus(entry, { isDone })` and renders whatever comes back; the universal `cancelled` override + 5 base statuses stay in the component. Rule objects live client-bundle-safe in the domain/tracker layers (`person-lookup-status.ts`, `tracker/dashboard/ocr-status.ts`) and are registered for the client via the side-effect import `domain/queue-row-status-index.ts` (defineWorkflow never runs in the bundle). - **Titles:** Queue row title/subtitle resolve from **kind** (`data.queueRowKind`: person/file/catalog) via `src/domain/queue-row-presentation.ts` — the single source for `resolveEntryName`/`resolveEntryId` (`shared/entry-display.ts`) and projection `batchGroupTitle`. person → resolved name (subtitle EID, else trace id); file → PDF filename; catalog → spec label; **person batch anchor → no title** (count badge + member preview identify it). - **2026-06-02: Member/preview footer subtitle falls to the TRACE ID, not the EID.** The subtitle rule "EID if present, else trace id" is correct **only for a flat single** person row (its footer is the only place the EID shows — unchanged). On surfaces where the EID/name is already shown elsewhere — a **batch / preview group anchor** (the member-name preview in `group-row-base.tsx` shows each person's EID on the title-line right) — the footer subtitle must NOT repeat the EID; it falls through to the **trace id**. This is the `preferTraceIdSubtitle` option on `resolveQueueRowPresentation` (person kind only; `file`/`catalog` already yield the trace id), set by the group-anchor branch of `buildProjectionFromQueueSurface` (`src/domain/workflow-runtime/projection.ts`). Two bugs this fixed: (1) a one-member `alwaysBatchDelegatedMembers` batch (oath-signature / person-lookup) has **no parent row**, so the old `batchParent`-gated `subtitle: ... ? anchorProjection.subtitle : undefined` left the group footer **blank** — now the anchor falls back to `members[0]` and resolves the trace id; (2) `DelegationRow`'s footer fell back to `parent.data.__name` when `projection.subtitle` was undefined, leaking the literal `"OCR"` workflow label — removed (a stale pre-trace-id row now just shows no id). Pinned by `tests/unit/domain/workflow-runtime-projection.test.ts` (member-batch trace id, OCR file preview trace id ≠ "OCR", flat single keeps EID). Drilled-in member `EntryItem`s keep the EID subtitle (no EID on their own title line).
- **No title ordinals:** Session-local ordinals (`OATH 1`, `<label> · #1234`, `Roster 2`) are retired. Disambiguate by the footer's time + `#run`. `resolveDaemonBatchQueueTitle` → titleOverride, else a member's `pdfOriginalName`, else `""`. The terminal-drawer session card's title **always** drops the trailing ordinal (`WorkflowBox.displayInstance` strips `\s\d+$` — every instance, not just a lone ` 1`); instances stay numbered internally for start/end pairing but the number never reaches the title.
- **2026-06-01 (rev. 2026-06-04): Session-card subtitle = the running run's trace id, but ONLY while in flight.** `WorkflowBox`'s subtitle shows `WorkflowInstanceState.currentTraceId` — the frozen `data.__traceId` of the in-flight run, identical to that run's queue-row subtitle — **only when `itemInFlight` is true**. The daemon worker resolves the id with `findFrozenTraceId({workflow, runId, trackerDir})` at claim time and passes it as the `traceId` arg to `emitItemStart`; it rides the `item_start` session event's `traceId` field into `session-state.ts`, which sets `currentTraceId` on `item_start` and (like `currentItemId`) does not clear it on `item_complete`. **The card no longer DISPLAYS that retained id once the item finishes** — when not in flight (idle, keepalive, complete, failed, or a fresh authenticating daemon) the subtitle falls back to the phase subline from `deriveSessionCardCopy` (`idle — waiting for work`, `Run complete`, `Authenticating 1/2`, …) rather than leaving a stale trace id sitting in the description. (The earlier rev. kept the trace id visible after completion; that read as a confusing leftover id on an idle card, so display is now gated on `itemInFlight` — `currentTraceId` is still retained in state for any future correlation use.) The field must be carried in both the backend (`tracker/dashboard/session-state.ts`) and frontend (`shared/types.ts`) `WorkflowInstanceState` mirrors AND in `session-state-equal.ts` (`workflowEqual`) or the drawer won't re-render on a new trace id. The footer's bottom-right shows the current step (`footerStep`) — never a raw item id (see the step_change lesson below). UI gallery: the in-flight variant sets `currentTraceId` + `currentStep`; the "idle (had a run)" variant sets `currentTraceId` but is idle, exercising that the id is hidden.
- **2026-06-04: Session-card `currentStep` was silently broken by the `emitStepChange` dedup — fixed by always emitting + render-time dedup.** The session card's footer step text and micro step pipeline read `WorkflowInstanceState.currentStep`, which `rebuildSessionState` derives SOLELY from `step_change` session events. Those events were being **suppressed for every `ctx.step`** by a 50ms dedup in `emitStepChange` (`tracker/session-events.ts`): `Stepper.announce` writes a `step:start` log line (`Phase: X`) immediately *before* calling `emitStepChange`, so the "is there a recent matching step log?" guard always matched and dropped the event. Result: `currentStep` stayed `null` the whole run → the footer fell back to `currentItemId` (an opaque derived id, "random numbers like an id") and the pipeline never advanced. Fix: `emitStepChange` now **always emits** (the dedup machinery + its dead imports were removed); the duplicate-line concern it was solving — the log-panel **"all" tab** showing both the `Phase: X` log line AND a bare `step_change` event line — is now handled at render time in `mergeDisplayItems` (`log-panel/LogStream.tsx`), which drops `step_change` events from the merged stream (they stay in the dedicated **Events** tab and keep flowing to session state). The `WorkflowBox` footer also no longer falls back to `currentItemId` — never show an item id as the "step". Pinned by `tests/unit/tracker/step-change-emit.test.ts` (always-emits) + `tests/unit/dashboard/log-stream-merge.test.ts` (render dedup).
- **2026-06-04: `StepPipeline` cancellation no longer snaps the highlight back to step 0.** A cancelled run is `status="failed"` + `step="cancelled"` (the sentinel) — so `currentStep` no longer names the reached step. The old code's "failed + unrecognized step → step 0" fallback fired for the sentinel, lighting **Loading Roster** (red, with a live timer) even though the run was stopped at, say, **Awaiting Approval**. Fix: the step derivation is now the exported pure fn `computeStepViews(steps, currentStep, status, stepDurations)` (extracted from the component for testability). For a cancelled run it recovers the reached step from `stepDurations` — every COMPLETED step has a recorded duration (see `computeStepDurations` in `tracker/dashboard/run-timelines.ts`; the in-flight step at cancel time has none), so the cancellation point is the step just after the furthest timed step (clamped to the last step). That step is marked a new `cancelled` `StepStatus` rendered in the **`warning` (amber)** token — matching the row's "Cancelled" badge (`EntryItem` `STATUS_CONFIG.cancelled`) — not a misleading red `failed`. The genuine "failed with no/unknown step → step 0 red" fallback is preserved for real crashes. `AuthSuperChip`/`authGroupStatus` handle the cancelled status too (workflows whose steps include `auth:*`). Pinned by `tests/unit/dashboard/step-pipeline.cancelled.test.ts`. No live component harness — also verified by `build:dashboard` (warning opacity utilities emit) + architecture token guards.
