# Dashboard

React SPA for real-time workflow monitoring: queue on the left, log/detail surface on the right.

## Stack

- React 19, Vite 8, Tailwind CSS v4, shadcn/ui primitives, lucide-react, sonner.
- HeroUI is only used for the date calendar and its stylesheet.
- Theme tokens live in `index.css`; fonts are Inter and JetBrains Mono.
- No framer-motion.

## UI editing rules

Follow these when adding or editing ANY dashboard component. Items marked **[guarded]** fail `tests/unit/architecture/frontend-tailwind-compliance.test.ts` — run `npm run test:architecture` before declaring UI work done.

- **Color = design tokens only. [guarded]** Never use Tailwind palette classes (`text-sky-500`, `bg-amber-400`, `border-slate-700`) or raw `#hex` / `rgb()` / `hsl()` literals in `.tsx`. Use the semantic tokens — `primary`, `secondary`, `muted`, `accent`, `destructive`, `info`, `success`, `warning`, `border`, `ring`, `foreground`/`background`, `sidebar*` — or the categorical log accents `log-cyan|log-teal|log-violet|log-slate`. House tint pattern: `bg-<token>/12–15` + solid `text-<token>` + `border-<token>/30` (see `shared/status-styles.ts`). Need a color the tokens don't cover? **Add a token** to `index.css` (light `:root` + `.dark` + the `@theme inline` `--color-*` map), don't inline it. The ONLY sanctioned raw hex is `#4ade80` / `#fbbf24`.
- **Icons = lucide, never glyphs.** Use `lucide-react` components — never unicode/emoji characters (`▲ ← ● ⚠ ✓ ✗`) as icons. An icon-only button needs an `aria-label` (or `title` / sr-only text); a decorative icon inside an already-labeled control gets `aria-hidden`.
- **Interactive = real elements.** Use `<button>` / `<a>`, not `<div onClick>`. If a non-button must be clickable, add `role`, `tabIndex={0}`, AND an `onKeyDown` (Enter/Space) plus `cursor-pointer`. Any `<button>` that is not a form submit gets `type="button"`.
- **Focus stays visible.** Don't `outline-none` without a replacement. The global base (`index.css`) gives native elements an `outline-ring/50` focus ring; if you override it, add `focus-visible:ring-2 focus-visible:ring-ring` — a background-tint-only focus state is too weak.
- **Async / live regions announce.** Streaming logs, live counts, validation, and status that change without a user action need `aria-live="polite"` (or `role="alert"` for blocking errors). Buttons firing async actions disable while pending.
- **Contrast + labels.** `text-muted-foreground` (and any `/NN` opacity on it) is for secondary/hint text only — primary titles and meaningful values use `text-foreground`. Every form control needs a `<label htmlFor>` or `aria-label`; a placeholder is not an accessible name.
- **Motion / layout. [guarded]** Animations use Tailwind utilities with `motion-safe:` / `motion-reduce:animate-none` (no `@keyframes`, no inline `animation:`); z-index stays on the `z-*` scale (no `z-[...]`); `<img>` needs `srcSet` + `sizes` + `loading`/`fetchPriority`; use `shrink-0`, not `flex-shrink-0`.

## Operator Text

Use the shared operator subject (`data.__subject`) as primary text for toasts, queue rows, delegation batches, and batch members. Raw run ids/session ids are fallback or debug detail only.

Dashboard controls mutate SQLite control state first and let workers observe commands. JSONL writes are audit/history. Do not add controls that only flip React state or indiscriminately kill Chromium processes.

## Backend

The SSE/API server is Hono under `src/tracker/dashboard/hono/`, created by `src/tracker/dashboard/server.ts`. Vite dev runs on `:5173` and proxies `/api/*` + `/events/*` to `:3838`; prod serves the built dashboard from the Hono server.

Full API and event reference: `docs/engineering/dashboard-api-reference.md`.

## Workflow Metadata

Frontend labels, detail fields, steps, and display helpers come from the server-side workflow registry via `/api/workflow-definitions`. Do not add frontend-side workflow label/detail hardcoding.

For a new workflow:
- Declare `label`, `getName`, `getId`, and `detailFields` in `defineWorkflow`.
- Add log icon patterns only if new message patterns need icons.
- Run the dashboard and verify entries, steps, and detail fields populate from `ctx.updateData`.

## Lessons Learned

- **Lesson maintenance rule:** Keep current UI contracts here; move reference tables to `docs/engineering/dashboard-api-reference.md`.
- **2026-06-04: Input-run "settings gear" consolidated into `RunSettingsMenu`; `StepPresetMenu` removed.** The `InputRunPanel` gear is now a single `RunSettingsMenu` (`navigation/`) holding TWO ephemeral, per-page-load run settings: **Automation workers** (always shown) and **Run mode** presets (shown only when the workflow declares `presets`). It supersedes `StepPresetMenu` (deleted); the shared `StepPreset` type + `FULL_PRESET_ID` const moved to `src/dashboard/lib/run-settings.ts` (the new home for worker choices too — `WORKER_CHOICES` = Auto/1/2/4/6/8 + `workerChoiceToParam`). The gear shows the primary-accent + dot "active" treatment when EITHER setting is non-default. `InputRunPanel` POSTs `parallelWorkers` to `/api/enqueue` only when not Auto. `RunModal` carries the same setting as an inline **Automation workers** section gated by a new `RunModalSections.workers` flag (emergency-contact / ocr / oath-upload), self-hidden in oath-upload upload-only mode (single ticket, nothing to parallelize); it appends `parallelWorkers` to the upload `FormData` only when not Auto and only for the `/api/ocr/prepare` path. Backend contract + read-back: `src/workflows/ocr/CLAUDE.md` (2026-06-04 worker lesson) and `src/domain/run-options.ts`. No component test harness exists — verified by typecheck + `build:dashboard` + architecture guards.
- **Workflow definitions require eager registration.** `/api/workflow-definitions` reads the in-process `defineWorkflow` registry, so `src/tracker/dashboard/workflows.ts` must import every dashboard workflow barrel.
- **Queue surfaces and actions:** Extend classifier/projection layers and `GroupRowBase` wrappers for new row types. Dispatch row/bulk controls through `useWorkflowActionDispatcher` so scope/source reach `performWorkflowAction`.
- **2026-06-03: `operation` coordinator surface renders via `OperationRow` (queue-panel).** The `operation` archetype (target-workflow coordinator for OCR-backed oath-signature / emergency-contact runs) projects through the shared surface/projection layers (`queue-surface-classifier.ts` `OperationSurface`, `buildProjectionFromQueueSurface`). `QueuePanel` renders it via `OperationRow`: before approval (0 members), it renders as a selectable `EntryItem` with row-scoped cancel/delete actions plus a compact OCR status line (`data.ocrStatus`) and an "Open OCR review" link; after approval, when signer/contact members exist, the same coordinator row stays selectable for its own log timeline and exposes an inline expand/collapse strip that renders the fanned-out member `EntryItem` rows underneath. The link calls `onOpenOcrReview({ sessionId, runId })` → `App.handleOpenOcrReview` switches to the OCR workflow, selects the OCR review row (by `sessionId` = the row id), AND arms the Preview/review gate by setting `reviewingPrepId` to the OCR `runId`. Setting `selectedId` alone is not enough: the right-pane gate is `reviewingPrepId === (selectedEntry.runId ?? selectedEntry.id)`, so without the `runId` the link would land on the default Events tab, not the Preview/review tab. The review row + Preview tab live in the OCR panel, never duplicated here. The `RunModal` sends `targetWorkflow` (from `RUN_MODAL_REGISTRY.targetWorkflow`) only to `/api/ocr/prepare` so the backend can tell an oath-signature PDF run from an oath-upload full run (both `formType=oath`).
- **Unified footer contract (2026-06-01, status-gated):** Every flat queue footer (`EntryItem`, including batch members) renders one ordered button schema — `time · #run · id · ⟨spacer⟩ · elapsed/duration · ▲ bump · ↻ retry · × cancel · 🗑 delete`. Each button self-hides on its kernel action descriptor's `enabled` flag; **the projection sets `enabled` per status** via `rowActionEnabledForStatus` (`src/domain/workflow-runtime/projection.ts`), the single source of truth for the matrix: **running → ×** · **queued → ▲ ×** · **done/failed → ↻ 🗑** (a queued row has no delete — cancel it first, which makes it terminal, then 🗑 appears; cancelled is `failed`+`step=cancelled` → terminal → ↻ 🗑). The buttons (`BumpButton`, `RetryButton`, `RowCancelButton`, `DeleteButton` in `shared/`) still never branch on `entry.status` themselves — they only read descriptors — so the schema stays kernel-driven; status-gating lives in the projection, not the component. The default policy carries all four row actions (`DEFAULT_ROW_ACTIONS`, `default-policy.ts`); workflows inherit them. `RowCancelButton` routes by the cancel target's status (running → `status:"running"`, queued → queued handler, OCR-prep → discard) via the pure `buildRowCancelDispatchArgs` (`lib/row-cancel-request.ts`). This **replaces** the prior "always retry+delete, no status gating" rule and the dead `CancelRunningButton`/`QueueItemControls` (removed). The toolbar Stop + drawer `StopPill` remain the daemon-scoped stop; the footer × is the per-row cancel.
  - **Batch/group footers** (`DaemonBatchRow`/`DelegationRow` via `BatchFooterActions`/`ApprovalDelegationFooterActions`) keep their own bulk selection (retry-all / delete-all / cancel-all over members); they are not status-gated per the matrix above (a group spans mixed-status members). Don't bump a group.
- **2026-06-01: 0-member batch footers fall back to the anchor.** `DaemonBatchRow` derived footer time / elapsed / retry+delete from `memberEntries`, so a `batch` anchor with no members yet (e.g. the oath-signature PDF row during OCR approval — visible under the "all" filter via `queueGroupMatchesStatusFilter(null, []) === true`) rendered a degenerate footer (bare `#run`, no time/elapsed/actions). Fix: `DaemonBatchRow` takes an `anchorEntry` prop and uses `footerEntries = members.length ? members : [anchor]` for `firstTimestamp`, `elapsedEntries`, and `BatchFooterActions` targets; `members` stays empty so the count badge/progress bar still read 0/0. `QueuePanel` passes `anchorEntry={surface.parent}`. Surfaced by the dev UI gallery's ("?view=ui-gallery") "0 members (pre-fan-out)" variant — the gallery reuses the real component, so footer regressions show up there.
- **Prep and delegation cards:** OCR rows are `preview`; batch rows are real batch anchors. Multi-file upload is N independent preview runs, not one grouped parent card.
- **Status:** Queue row status semantics resolve from per-workflow **`statusExtensions`** (declared on `defineWorkflow`) via `src/domain/queue-row-status.ts` — the single source for `EntryItem`'s derived status (`notFound`, `needsReview`) and supplemental tag (person-lookup A/IA). `EntryItem` is workflow-agnostic: it calls `resolveQueueRowStatus(entry, { isDone })` and renders whatever comes back; the universal `cancelled` override + 5 base statuses stay in the component. Rule objects live client-bundle-safe in the domain/tracker layers (`person-lookup-status.ts`, `tracker/dashboard/ocr-status.ts`) and are registered for the client via the side-effect import `domain/queue-row-status-index.ts` (defineWorkflow never runs in the bundle). Never branch on `entry.workflow === "..."` for status in the dashboard.
- **Titles:** Queue row title/subtitle resolve from **kind** (`data.queueRowKind`: person/file/catalog) via `src/domain/queue-row-presentation.ts` — the single source for `resolveEntryName`/`resolveEntryId` (`shared/entry-display.ts`) and projection `batchGroupTitle`. person → resolved name (subtitle EID, else trace id); file → PDF filename; catalog → spec label; **person batch anchor → no title** (count badge + member preview identify it). Never promote technical ids to primary text; do not hardcode workflow titles in the dashboard.
- **2026-06-02: Member/preview footer subtitle falls to the TRACE ID, not the EID.** The subtitle rule "EID if present, else trace id" is correct **only for a flat single** person row (its footer is the only place the EID shows — unchanged). On surfaces where the EID/name is already shown elsewhere — a **batch / preview group anchor** (the member-name preview in `group-row-base.tsx` shows each person's EID on the title-line right) — the footer subtitle must NOT repeat the EID; it falls through to the **trace id**. This is the `preferTraceIdSubtitle` option on `resolveQueueRowPresentation` (person kind only; `file`/`catalog` already yield the trace id), set by the group-anchor branch of `buildProjectionFromQueueSurface` (`src/domain/workflow-runtime/projection.ts`). Two bugs this fixed: (1) a one-member `alwaysBatchDelegatedMembers` batch (oath-signature / person-lookup) has **no parent row**, so the old `batchParent`-gated `subtitle: ... ? anchorProjection.subtitle : undefined` left the group footer **blank** — now the anchor falls back to `members[0]` and resolves the trace id; (2) `DelegationRow`'s footer fell back to `parent.data.__name` when `projection.subtitle` was undefined, leaking the literal `"OCR"` workflow label — removed (a stale pre-trace-id row now just shows no id). Pinned by `tests/unit/domain/workflow-runtime-projection.test.ts` (member-batch trace id, OCR file preview trace id ≠ "OCR", flat single keeps EID). Drilled-in member `EntryItem`s keep the EID subtitle (no EID on their own title line).
- **No title ordinals:** Session-local ordinals (`OATH 1`, `<label> · #1234`, `Roster 2`) are retired. Disambiguate by the footer's time + `#run`. `resolveDaemonBatchQueueTitle` → titleOverride, else a member's `pdfOriginalName`, else `""`. The terminal-drawer session card's title **always** drops the trailing ordinal (`WorkflowBox.displayInstance` strips `\s\d+$` — every instance, not just a lone ` 1`); instances stay numbered internally for start/end pairing but the number never reaches the title.
- **2026-06-01: Session-card subtitle = the running run's trace id.** `WorkflowBox`'s subtitle shows `WorkflowInstanceState.currentTraceId` — the frozen `data.__traceId` of the in-flight (or most-recent) run, identical to that run's queue-row subtitle. The daemon worker resolves it with `findFrozenTraceId({workflow, runId, trackerDir})` at claim time and passes it as the new `traceId` arg to `emitItemStart`; it rides the `item_start` session event's `traceId` field into `session-state.ts`, which sets `currentTraceId` on `item_start` and (like `currentItemId`) **does not clear it on `item_complete`** so an idle daemon keeps showing its last run's id. When there's no run yet (fresh authenticating/idle daemon) `currentTraceId` is `null` and the subtitle falls back to the phase subline (`deriveSessionCardCopy`). The field must be carried in both the backend (`tracker/dashboard/session-state.ts`) and frontend (`shared/types.ts`) `WorkflowInstanceState` mirrors AND in `session-state-equal.ts` (`workflowEqual`) or the drawer won't re-render on a new trace id. The footer's bottom-right still shows the current step (`footerStep`). The UI gallery's running/done/failed and idle-with-last-run Session-Card variants set `currentTraceId`; the authenticating/duo/keepalive variants leave it null to exercise the fallback.
- **SSE:** Real-time streams use one `/events/hub` EventSource. Listener errors must not kill other listeners, and projection-backed topics must resolve the current `state.db` handle each tick.
- **2026-06-02: WorkflowRail badge counts are backend-authoritative.** `App.tsx` passes SSE `wfCounts` through `buildWorkflowRailEntryCounts`; do not override the active workflow with QueuePanel's local "ALL" count. The backend owns cross-workflow badge semantics via `countSidebarRowsFromTrackerHistory(asTracker)`, including latest-row dedupe, EID merge, top-level queue-surface collapse, and visible OCR prep rows. QueuePanel status strips may still compute local per-filter counts, but rail badges must track the `entries` payload contract.
- **Run launchers:** Operators start workflows through upload runs (`RunModal` + `RUN_MODAL_REGISTRY`) or input runs (`InputRunPanel` + `INPUT_RUN_REGISTRY`).
- **Input-bar row shape is count-based.** One parsed value is flat; multiple parsed values become one batch row.
- **2026-05-30: `buildDisplayNameMap` ordinal machinery removed (dead since queue row kind landed).** Stamped rows resolve title via `resolveQueueRowPresentation` (queue row kind), which wins inside `resolveEntryName` before the displayNames map is consulted — so the session-local "<base> <n>" numbering (the `ordinal` flag, the `totals` counting pass, the `counters` loop) was dead for every production row. The map now only emits bare base names for legacy/unstamped rows + the delegated-label inheritance walk. The one preserved nuance: a lone bare workflow-label fallback (e.g. a single "Separation" doc with no person name) is still omitted from the map so `resolveEntryName` falls through to its richer `__subject`. Behavior-neutral: scenario snapshots unchanged; the OATH/EMPL unit assertions dropped their ` 1` suffix (the map output, never seen in prod where OCR rows are kind `file`).
- **2026-05-30: Per-workflow status rules moved out of EntryItem into `statusExtensions`.** `EntryItem` no longer branches on `entry.workflow` for the A/IA tag or the `notFound`/`needsReview` derived statuses. The rules live in `WorkflowConfig.statusExtensions` (`derivedStatus` + `secondaryTag`), resolved generically by `resolveQueueRowStatus` (`src/domain/queue-row-status.ts`). Client registration is via the side-effect import `domain/queue-row-status-index.ts`. Behavior-neutral refactor — pinned by `tests/unit/domain/queue-row-status.test.ts`. Gotcha: `statusExtensions` is OPTIONAL, so no "every workflow must declare it" guard (that would be wrong).
- **2026-05-28: Retired workflows are filtered at the dashboard payload boundary.** `active-check` and `eid-lookup` tracker history can remain on disk, but `/events` workflow metadata and `/api/workflows` filter them out so the rail only exposes Person Lookup.
- **OCR review UI:** Preserve source-page ordering, retry/re-OCR page isolation, and `data-pair-index` instrumentation.
- **Testing gap:** There is no browser/component harness yet. Pure projection logic has unit tests; visual changes need lint, typecheck, dashboard build, and manual dashboard verification.
- **2026-05-31: Desktop Tailwind compliance is guarded by architecture tests.** `tests/unit/architecture/frontend-tailwind-compliance.test.ts` blocks dashboard regressions for custom keyframes/inline animation, arbitrary `z-[...]`, old `flex-shrink-0`, motion-unsafe Tailwind animations, `<img>` tags without `srcSet`/`sizes` plus explicit loading priority, and (2026-06-04) **raw color** — Tailwind palette classes (`text-sky-500`, `bg-amber-400`, …) and raw hex in `.tsx` components are rejected; use design tokens. The dashboard remains desktop-only; do not add mobile-only layout requirements unless the product scope changes.
- **2026-06-04: Color is token-only; semantic + categorical tokens live in `index.css`.** A UI/UX audit found state/auth/log colors bypassing the theme via Tailwind palette classes and inline hex (terminal-drawer, log-panel, status badges) — invisible to the light/dark token system. Fix: added semantic state tokens **`info`/`success`/`warning`** (light `:root` + `.dark` + `@theme inline`, alongside existing `destructive`) and a small **categorical** accent set **`log-cyan`/`log-teal`/`log-violet`/`log-slate`** for the log/event legend, then migrated every component onto them (`text-info`, `bg-success/15`, `border-warning/40`, `text-log-violet`, …). Mapping: blue/sky→info, green/emerald→success, amber/yellow/orange→warning, red/rose→destructive; distinct log hues→`log-*`; neutrals→`foreground`/`muted-foreground`. The **only** sanctioned raw hex is `#4ade80`/`#fbbf24` (documented in `shared/status-styles.ts`). The audit also: gave `LogLine` event rows lucide icons (was unicode glyphs) + keyboard-accessible copy; swapped `⚠`/`←`/`●` glyphs for lucide/CSS; added `aria-label` to the search input and `aria-live` to the streaming-log + failure-bell count regions; added a real focus ring to the terminal-drawer toggle. Token additions live in `index.css` (light/dark + the `@theme inline` `--color-*` map that generates the utilities). Verified by typecheck + `build:dashboard` (utilities + opacity variants emit correctly) + architecture guards; no component test harness exists.
