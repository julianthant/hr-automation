# Dashboard Components Organization

This folder is organized by dashboard area. Keep files near the UI surface that owns them; use `shared/` only when more than one area uses the same piece.

## Folders

| Location | Belongs here | Examples |
|---|---|---|
| `navigation/` | Navbar, workflow rail, search, failure popover, and top-bar run/capture affordances. | `TopBar.tsx`, `WorkflowRail.tsx`, `SearchBar.tsx`, `FailureBell.tsx`, `InputRunPanel.tsx` |
| `queue-panel/` | Queue list, queue grouping surfaces, batch drill-in, shared `GroupRowBase`, and queue surface classification. | `QueuePanel.tsx`, `group-row-base.tsx`, `queue-surface-classifier.ts`, `batch-queue-view.tsx`, `EntryItem.tsx`, `StatPills.tsx`, `queue-status.ts` |
| `log-panel/` | Right detail/log column, run selector, step pipeline, screenshots, and edit/retry data view. | `LogPanel.tsx`, `LogStream.tsx`, `LogLine.tsx`, `StepPipeline.tsx`, `ScreenshotsPanel.tsx` |
| `terminal-drawer/` | Bottom session/daemon drawer and browser/session chips. | `TerminalDrawer.tsx`, `WorkflowBox.tsx`, `BrowserChip.tsx`, `LiveIndicator.tsx` |
| `run-modal/` | Generic PDF/file-upload run modal and modal-specific controls. | `RunModal.tsx`, `SharePointDownloadButton.tsx` |
| `capture/` | Capture/photo UI and capture types. Modal internals live in `capture/modal/`. | `CapturePhotoTile.tsx`, `CapturePhotoLightbox.tsx`, `capture-types.ts`, `modal/index.tsx` |
| `ocr/` | OCR/prep review UI and OCR record renderers. `DelegationRow` remains a compatibility wrapper around queue-panel grouping primitives. | `OcrReviewPane.tsx`, `OcrQueueRow.tsx`, `lookup-status.ts`, `DelegationRow.tsx`, `delegation-row-helpers.ts`, `record-renderers.tsx`, `preview-gate.ts`, `prep-record-overlay.ts` |
| `oath-upload/` | Oath-upload-only UI pieces. Promote to `shared/` when another workflow starts using them. | `DuplicateBanner.tsx` |
| `shared/` | Cross-area components, shared display helpers, row action buttons, styles, and tracker/dashboard API types. | `EmptyState.tsx`, `RetryButton.tsx`, `RowCancelButton.tsx`, `BumpButton.tsx`, `DeleteButton.tsx`, `PdfPagePreview.tsx`, `MediaLightbox.tsx`, `types.ts`, `entry-display.ts` |
| `hooks/` | React hooks that own client-side state, polling, SSE subscriptions, cache warming, or toast effects. Hooks should not render JSX. | `useEntries.ts`, `useLogs.ts`, `useSessions.ts`, `useRosters.ts` |
| `ui/` | Local shadcn/HeroUI-style primitives only. These should stay generic and workflow-agnostic. | `dialog.tsx`, `popover.tsx`, `tooltip.tsx`, `calendar.tsx` |

## Lessons Learned

- **2026-06-11 (rev. 2026-06-16, E2E-103): Row-variant count/status/elapsed helpers are consolidated; batch member counts fold skipped→done (BM-4).** The batch + operation coordinator rows each carried their own `aggregateMemberCounts` (byte-identical) that diverged from the canonical `aggregateBatchCounts` (`ocr/delegation-row-helpers.ts`): the copies folded **skipped→queued**, the canonical folds **skipped→done**. Both copies are deleted; `BatchRowUnified` + `OperationRowUnified` now use the canonical `aggregateBatchCounts`. **Decision: skipped→done.** Skipped is terminal — it will never run — so counting it as pending work spins a forever-incomplete header. (Pinned by `tests/unit/dashboard/batch-row.test.ts` "skipped as done" + `delegation-row-helpers.test.ts`.) The shared failed+`step==="cancelled"`→cancelled override moved to `statusKeyForEntry` (`shared/status-styles.ts`), routed by `EntryItem` `STATUS_CONFIG`, operation `HEADER_STATUS`, and the batch member status map (`memberStatusSpec`, also in `status-styles.ts`) — each keeps its own class/tone map keyed on the shared status string. `useBatchElapsedLabel` (was byte-identical in `batch-row-variants` + `group-row-base`) now lives once in `delegation-row-helpers.ts` next to `computeBatchElapsed`. **E2E-103 (2026-06-16): `BatchCounts` now has a `cancelled` bucket.** `aggregateBatchCounts` routes `failed`+`step==="cancelled"` through `statusKeyForEntry` (the same classifier used by per-member chips) so a cancelled member lands in `cancelled`, not `failed`. `StatusCounts` renders a `Ban` icon + amber `cancelled` count when non-zero (like `failed`, hides at 0). `computeProgressSegments` in `group-row-base.tsx` adds a `bg-warning/60` amber segment for cancelled. The "accepted gotcha" from the 2026-06-11 note is resolved — the mini-badge, the progress bar, and the per-member chip are now all consistent.
- **2026-06-11: Per-record lookup "running" needs per-record evidence, not the parent's step.** `deriveOcrRecordLookupTracker` (`ocr/lookup-status.ts`) used the parent OCR row's step (`entryStatus === "running" && step === "person-lookup"/"verification"`) as the per-record signal, so EVERY preview row showed "Person lookup running" — even paper-resolved rows that never get a child — and the optimistic i9 branch showed "I-9 lookup running" before any i9 dispatch. Fix: a record only shows a lookup "running" label when it has its OWN evidence — a `person-lookup` dependency child for its `recordIndex`, a stamped `personLookupStatus`/`personLookupTraceId`, or a `lookup-running`/`lookup-pending` matchState (`recordIsLookupCandidate`). The parent-step fallback and the optimistic-i9 branch are both gated on that predicate, so a paper-only record stays quiet (`person`/`i9` undefined → falls through to "Lookup completed"). Pinned by `tests/unit/dashboard/ocr/lookup-status.test.ts` (no-leak + still-shows-for-candidate cases).
- **2026-06-08: Verify prep overlays must let server enrichment own lookup/check fields.** `OcrReviewPane` persists per-record local edits by run, but verify review rows are read-only server-enriched records. If a stale local snapshot is merged over a fresh terminal OCR row, fields like `i9LookupStatus`, `officialSignerStatus`, and `checks` can incorrectly keep showing "I-9 lookup running..." after the backend has completed with `unable-to-access`. The overlay now lives in `ocr/prep-record-overlay.ts`: verify-shaped records (`"checks" in record`) take the fresh server record wholesale and preserve only local `selected`; editable oath/EC records still keep local form fields while refreshing server-owned lookup fields (`verification`, `matchState`, `matchSource`, `warnings`). `lookup-status.ts` also keeps an oath verify record that still needs I-9 in a top-level `running` phase after person lookup completes, and ignores stale in-progress stamped lookup statuses once the parent OCR row is terminal. Pinned by `tests/unit/dashboard/ocr/prep-record-overlay.test.ts` and `tests/unit/dashboard/ocr/lookup-status.test.ts`.
- **2026-06-08 (rev. 2026-06-12, E2E-006): Run Modal roster mode has three states while SharePoint is active — and the auto-flip is TWO-WAY, gated on choice provenance.** The auto-flip effect tracks whether the current `rosterMode` was operator-clicked or auto-applied (`rosterModeSource` ref in `RunModal`): an auto-applied `download`/`wait` (from a momentarily-empty `useRosters()` on open) flips BACK to `existing` when rosters load; an operator-clicked choice is never undone. Previously the flip was one-way, so the modal could silently submit a fresh SharePoint download while the operator believed the local roster was in effect. `RunModal` polls `/api/sharepoint-download/status` while roster-backed upload modals are open. If a SharePoint job is current or queued, it shows **Wait for queued SharePoint** (`rosterMode:"wait"`) between local roster and fresh download; fresh download remains available and queues a new job behind the current queue. On SharePoint completion the modal refreshes `useRosters()` so the wait option disappears once the downloaded roster is listed as "Use latest roster."
- **2026-06-08: OCR record screenshots reuse the singleton screenshot card UI.** `RecordScreenshotStrip` still owns OCR-specific child item-id lookup (`ocr-oath|ocr-ec|ocr-verify...`, plus verify I-9), but rendering uses the same `log-panel/ScreenshotCard` and `ScreenshotLightbox` as singleton screenshot tabs. Keep future thumbnail/metadata styling changes in the shared card/lightbox rather than reintroducing OCR-specific thumbnail markup.
- **2026-06-07: OCR read-only card — wrong-form hint is symmetric, and field-reads branch on SHAPE, not `formKind` (F6/F12d).** `readonly-record.ts` projects a standalone oath/EC record onto a read-only `VerifyPreviewRecord`. A record has TWO orthogonal axes: its **shape** (which fields exist — set by the OCR RUN: oath run → `printedName`/`employeeId` top-level; EC run → `employee`/`emergencyContact`) and the model's **`formKind`** classification. The old code branched the field-reads on `formKind`, so an EC-shaped record (real EC run) re-classified `"oath"` hit the `formKind === "oath"` branch, read undefined oath fields, and rendered an empty oath card with NO wrong-form hint; re-classified `"unknown"` it rendered a plain EC card, also no hint. Fix: branch on shape via the extracted `isOathShapedRecord(record): record is OathPreviewRecord` (F12d — replaces the duplicated `"printedName" in record` guard + the repeated `as OathPreviewRecord` casts), read fields by shape, and attach the wrong-form hint whenever `formKind` ≠ the run's native form — now symmetric across BOTH directions. `wrongFormKindHint` gained the EC-run ("looks like an oath form") branch. **Type coupling:** `PreviewRecord.formKind` was widened from the literal `"emergency-contact"` to the backend `"oath" | "emergency-contact" | "unknown"` enum so the EC-run case is type-FORCED to be handled; that made `formKind` no longer a unique union discriminant, so `ocr-downstream-registry.ts`'s oath `recordName` re-narrows by shape (`"printedName" in r`) instead of `=== "oath"`. Paired with the backend schema-tolerance + carry-forward fixes in `src/services/ocr/CLAUDE.md` (2026-06-07). Pinned by `tests/unit/dashboard/ocr/readonly-record.test.ts` (both mis-classification directions). No component harness — verified by `typecheck:all` + lint + scoped tests.
- **2026-06-08: OCR card footer + header phase = per-row lookup-state tracker (`lookup-status.ts`), not identity confidence.** `OcrReviewPane.tsx` derives one `OcrRecordLookupTracker` per preview row via `deriveOcrRecordLookupTracker` and passes it into downstream renderers as `lookupTracker` (`ocr-downstream-registry.ts` `renderEditor` signature; wired from `renderFormCard`). The footer chip shows the tracker `label` + child `traceId` when present — labels cover the full prep lifecycle: **`OCR in progress`** / **`Roster loading`** while the OCR row is still at matching/roster steps; **`Person lookup pending|running|completed|failed`** when a person-lookup child exists (or when verify stamps `personLookupStatus`); **`Lookup completed`** when no lookup was needed. `deriveRecordWorkflowPhase(tracker)` drives the nav header phase badge — **`failed` lookup maps to a failed header**, not `done`. For oath/EC delegated rows the tracker reads live child metadata from `/api/task-dependencies`; that route resolves each child's `traceId` from the **latest** `runs` projection row (`ORDER BY latest_tracker_ts DESC`), not a stale join of all run attempts. For verify rows, `verify.ts` stamps `personLookupStatus` + `personLookupTraceId` onto each record after dispatch/outcome because verify enrichment is awaited inside the OCR run instead of exposed as a long-lived dependency batch. `deriveLookupInProgress(tracker, checkKey)` suppresses premature "not found" on lookup-backed checks: person-lookup keys wait on `tracker.inProgress`; **`officialSigner` waits on `tracker.enrichmentInProgress`** so i9 enrichment can still run after person lookup completes. `VerifyRecordView` renders the tracker label in aria-live progress text. **Supersedes** the 2026-06-06 footer identity-confidence chip (`getMatchSourceDisplay` / `Identity confirmed` labels — deleted). Pinned by `tests/unit/dashboard/ocr/lookup-status.test.ts`, `tests/unit/dashboard/ocr/verify-record-view.test.ts`, and `tests/unit/tracker/tasks/store.test.ts`.
- **2026-06-06: Prep-card footer employment-status chip removed (superseded 2026-06-08 for footer-left content).** `renderEmploymentStatusBadge` + the `employmentStatusBadge` prop are **deleted** — the verify `ACTIVE STATUS` check row already carries HR status. The footer-left slot now shows the lookup-state tracker chip (see 2026-06-08), not match-source confidence.

- **2026-06-06: OCR review surface — completeness report "Option B" + toolbar "variant B"; dev gallery removed.** Two operator-picked redesigns lifted out of the temporary `?view=ocr-review-gallery` dev page (now deleted, with its App.tsx import + gate), chosen from `OcrReviewGallery.tsx`'s `ReportOptionB` / `TOOLBAR_VARIANTS`:

The **`found` rows** the operator transcribes lift into small raised cards (`rounded-md border border-border bg-card px-3 py-2.5 shadow-sm ring-1 ring-border/60`, value in `font-semibold text-foreground` + `SourceBadge`); **`present`/`missing`/`unavailable` rows stay flat** (status glyph + label + muted value, `(on paper)` tag, `missingLabel` / "Unable to access"). Approve gating unchanged (`submitting`/`selectedCount <= 0`/`hasPendingDependencies`); the whole pill self-hides when neither `onReupload` nor `isDelegation`. No component harness — verified by `typecheck:all` + lint + architecture guards (75/75) + `build:dashboard`.

- **2026-06-06: OCR review-surface cleanups — merged `ocr` pipeline step, doc-kind chip header, no in-body header, no signature header chip.** Four coupled changes to the OCR review pane (paired with the `verify.ts` prompt fix in `src/services/ocr/CLAUDE.md`):

- **2026-06-06: tall screenshots are sliced into newspaper columns in the lightbox, and lightbox chrome moved off the image into gutters.** A full PeopleSoft/CRM record capture is very tall+narrow; under the old `object-contain max-h-[85vh]` it scaled down to an unreadable ribbon with ~55% of the width empty. New `shared/SlicedScreenshot.tsx` measures the image's natural size and picks a column count `N = clamp(round(√((availW/availH)·aspect)), 1, maxColumns=4)` — the value that fills the box most squarely. `N≤1` (landscape/square/mild-portrait) → the original single fit-to-height image, unchanged. `N≥2` → the SAME cached image rendered once per column inside an `overflow-hidden` window offset by `translateY` (pure-CSS slicing, one fetch); columns read top→bottom, left→right with a slim numbered header strip above each slice. Pure geometry helpers `columnCountFor`/`sliceLayout` are exported and pinned by `tests/unit/dashboard/sliced-screenshot-layout.test.ts`. **Chrome restructure (the overlap + legibility fix):** `MediaLightbox`'s `ScreenshotLightboxShell` no longer `absolute`-positions translucent caption/Close/nav over the image (which covered form labels once the columns filled the space, and floated low-contrast over the still-visible dashboard). It's now a **solid modal panel** — `rounded-lg border border-border bg-card p-3 shadow-2xl` over a `bg-black/85` backdrop — laid out as a flex column: a top bar (caption left as plain `text-muted-foreground`, Close right as a `bg-secondary` pill button) + a body row with the prev/next chevrons (lucide `ChevronLeft/Right`, not `‹/›` glyphs; `bg-secondary` buttons) as `shrink-0` side gutters flanking the centered content. Column number strips use solid `bg-muted`. `SlicedScreenshot` reserves `CHROME_W=140`/`CHROME_H=96` (panel padding + nav gutters + top bar) + a per-column `COLUMN_HEADER_H` out of the viewport box so the panel never clips. Capture chrome (`chrome="capture"`) is untouched. No component harness — verified by typecheck + 75/75 architecture guards + `build:dashboard` + live dashboard.
- **2026-06-06: verify record cards gained a footer Retry + an inline labeled screenshot strip; OCR step pipeline drops `verification`/"Review" cosmetically.** Three changes to the OCR review surface:
  - **Step pipeline (cosmetic).** `LogPanel` now routes OCR rows through the pure `computeOcrPipelineView(registeredSteps, currentStep, status, isDelegated)` (exported from `StepPipeline.tsx`): it always hides the `verification` chip and — for STANDALONE (non-delegated, `!parentRunId`) runs — also the `awaiting-approval` ("Review") chip; DELEGATED ("approve") runs keep "Review".
