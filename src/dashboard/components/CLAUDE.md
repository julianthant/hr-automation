# Dashboard Components Organization

This folder is organized by dashboard area. Keep files near the UI surface that owns them; use `shared/` only when more than one area uses the same piece.

## Folders

| Location | Belongs here | Examples |
|---|---|---|
| `navigation/` | Navbar, workflow rail, search, notification center (with filter chips), and top-bar run/capture affordances. | `TopBar.tsx`, `WorkflowRail.tsx`, `SearchBar.tsx`, `NotificationBell.tsx`, `notification-filters.ts`, `InputRunPanel.tsx` |
| `settings/` | The Settings overlay (navbar gear) — a centered Dialog over the dimmed dashboard for tweakable operator constants, notifications, and read-only credential status. The Workflow Editor is launched FROM here into its own full-page takeover (`workflow-modifier/WorkflowEditorScreen.tsx`), not embedded. | `SettingsDialog.tsx`, `SettingsField.tsx` |
| `queue-panel/` | Queue list, queue grouping surfaces, operation drill-in, shared `GroupRowBase`, and queue surface classification. | `QueuePanel.tsx`, `group-row-base.tsx`, `queue-surface-classifier.ts`, `operation-queue-view.tsx`, `EntryItem.tsx`, `StatPills.tsx`, `queue-status.ts` |
| `log-panel/` | Right detail/log column, run selector, step pipeline, screenshots, and edit/retry data view. | `LogPanel.tsx`, `LogStream.tsx`, `LogLine.tsx`, `StepPipeline.tsx`, `ScreenshotsPanel.tsx` |
| `terminal-drawer/` | Bottom session/daemon drawer and browser/session chips. | `TerminalDrawer.tsx`, `WorkflowBox.tsx`, `BrowserChip.tsx`, `LiveIndicator.tsx` |
| `run-modal/` | Generic PDF/file-upload run modal and modal-specific controls. | `RunModal.tsx`, `SharePointDownloadButton.tsx` |
| `capture/` | Capture/photo UI and capture types. Modal internals live in `capture/modal/`. | `CapturePhotoTile.tsx`, `CapturePhotoLightbox.tsx`, `capture-types.ts`, `modal/index.tsx` |

| `dev/` | Dev-only UI gallery for in-browser component review (never shipped to prod). | `UiGallery.tsx` |

## Lessons Learned

- **2026-07-17: Approve N looked stale because Select all selected inactive employees that Approve never counts.** `Approve {selectedCount}` only counts `isApprovable` records — and `verification.state === "inactive"` is a hard block (backend lookup also deselects them). Select all previously checked every non-unknown row, so on a packet with 5 verified + 12 inactive the operator could "Select all", see 17 checkboxes flip, and watch **Approve stay at 5**. Fix: `approval-selection.ts` (`isApprovalSelectionBlocked` / `scrubHardBlockedSelection`) — inactive + unknown disable the per-row checkbox, Select all skips them, merge scrubs stale localStorage `selected:true`, and EC/oath `canFanOut` rejects inactive so a stuck selection can't enqueue a fill/signer. Pinned by `approval-selection.test.ts` + canFanOut inactive cases. Verified live: Select all → still Approve 5 with 12 unavailable checkboxes; Unselect → Approve 0; deselect one → Approve 4 (`.screenshots/debug-approve-stale/`).

- **2026-07-02: Capture photo lightbox now uses the Screenshots-tab chrome; the bespoke `chrome="capture"` shell was retired.** Operator complaint (with screenshot): a captured-photo preview "isn't a modal, it's inside the capture" — the old `CapturePhotoLightbox` passed `chrome="capture"` to `MediaLightbox`, which rendered `CaptureLightboxShell`: an `inline-flex` frame sized to `fit-content` around the image with the close/counter/prev/next chrome positioned ABSOLUTE **on the frame**. Because the frame hugged each image, (a) the arrows sat on the photo and **shifted between differently-sized photos** (the "consistent left/right arrows" ask), and (b) the thin frame + 92%-opaque backdrop let the underlying Run modal bleed through the edges, so it read as embedded rather than a modal. Fix: `CapturePhotoLightbox` now renders exactly like `ScreenshotLightbox` — a solid `bg-card` panel over a `bg-black/85` backdrop, caption + Close on a top bar (never over the image), a Preview-style thumbnail rail once 2+ photos, and prev/next arrows in **fixed side gutters** flanking a **constant-size** view box (`min(88vw,560px) × 84vh`, `object-contain`) so the nav never moves. The lightbox `<img>` also went `loading="lazy"` → `loading="eager"` + `fetchPriority="high"` (it's immediately in view — lazy only delayed it appearing). **The load-bearing fix for "it's inside the capture" was a PORTAL, not the chrome swap:** the capture lightbox opens from *inside* the Run modal's Radix `DialogContent`, which centers itself with a CSS **transform** (`-translate-x/y-1/2`). A transformed ancestor becomes the containing block for `position: fixed` descendants, so the un-portaled `fixed inset-0` overlay was trapped inside the ~760px dialog (overlay measured 760px, not the viewport) — the chrome clipped, the RunModal bleeding through the sides. Fix: `MediaLightbox` now `createPortal(overlay, document.body)` so `fixed inset-0` is viewport-relative (verified overlay = `0,0 1680×1050`). Two follow-on Radix-modal gotchas the portal introduced: (1) Radix sets `pointer-events: none` on `<body>` for a modal dialog, which the body-portaled overlay inherited → **every click swallowed** (`next.pe=none`); re-enabled with `pointer-events-auto` on the overlay. (2) A click on the portaled lightbox reads as "outside" the DialogContent → Radix's `onPointerDownOutside`/`onInteractOutside` would dismiss the whole Run modal; `RunModal` now `e.preventDefault()`s both while `captureMode && captureLightboxOpen` (same guard as its existing `onEscapeKeyDown`). The Screenshots-tab consumer isn't in a dialog, so the portal is a no-op there. **`MediaLightbox` was pruned:** with both consumers (`ScreenshotLightbox` + `CapturePhotoLightbox`) now on the screenshot chrome, the `chrome` prop, the `MediaLightboxChrome` type, the `ariaLabel` prop, the `X` import, and the entire `CaptureLightboxShell` (~110 lines) were **deleted** as unreachable; the screenshot render path + shared `navigate`/keydown logic are byte-identical (`wrapNavigation`/`preventDefaultOnKeys` kept as generic, now-unset options). No component harness — verified by `typecheck` + `test:architecture` (79) + `lint` (0 errors) + `build:dashboard` + a headless playwright-cli pass over a temporary `?view=capture-lightbox-preview` harness (deleted after): modal card + thumbnail rail + fixed-gutter arrows, arrows in identical positions at index 0 (left disabled, non-wrapping) and index 2 (both live, rail highlight moved, "flagged blurry" caption) — `.screenshots/capture-lightbox/after-0{1,2}-*.png`. **Also verified end-to-end through the REAL Run modal** (the portal + Radix-guard half can't be seen in the isolated harness): booted `dashboard:prod`, opened Run Emergency Contact → Capture, pushed 3 JPEGs into the panel session via `/api/capture/upload`, opened a tile → the lightbox measured full-viewport, arrow/rail clicks advanced the photo (2/3) with the Run modal staying open, and Esc closed the lightbox only — `.screenshots/capture-desktop-modal/0{3,4,5}-*.png`.
