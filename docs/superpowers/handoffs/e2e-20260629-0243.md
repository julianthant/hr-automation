## Errors that remain (one block per deferred issue)

### ISS-008 (HIGH) — daemon idle lost-wakeup + spawn block
- **Symptom:** a long-lived idle daemon (oath-signature, ~22 min / 4 items) stopped claiming newly
  enqueued claimable queued work (os-033203's 4 signers sat unclaimed ~5m38s); heartbeat kept
  advancing, `/whoami` responded, `shuttingDown:false`. `POST /wake` returned `ok:true` but triggered
  no claim; removing the hold gate did nothing. `POST /api/daemons/spawn` spawned NO new daemon
  (planner counts the stuck daemon alive). Only a kill + fresh daemon drained it. A FRESH daemon
  claims fine — uptime/idle-cycle dependent.
- **Root cause (high confidence):** `src/core/daemon/daemon.ts:228` `resolveWake` is a bare
  `state.wakeResolve?.()` with **no `wakePending` latch**; the check-before-park guard (~837-840) tests
  only `shuttingDown`. A wake arriving while the idle waiter is `null` (loop suspended in
  `pollWorkerCommands`/`claimNextItem`/keepalive/a hung await) is silently dropped → no re-poll until
  the 15-min `DEFAULT_IDLE_MS` timeout. Heartbeat is a separate ~5s timer (also renews the lease),
  decoupled from the claim loop — the "two independent liveness signals" hazard. Secondary (VS-004):
  a **killed** daemon never self-reconciles its `workers` row (stays `status=alive`, frozen heartbeat),
  so `computeSpawnPlan` counts it alive and blocks the fresh spawn.
- **Fix needed (concretely):** in `daemon.ts` add `state.wakePending` — set it in `resolveWake` when
  `state.wakeResolve===null`, and observe+clear it in the check-before-park guard so a raced wake is
  not lost; add a bounded idle re-poll (defense in depth); in the spawn planner / registry, treat a
  daemon that hasn't claimed despite claimable queued work (or a frozen-heartbeat killed daemon) as
  not-claimable so a peer spawns. Gotcha: the lease-renewal + teardown machinery is the recurring
  bug-nest (`docs/engineering/daemon-teardown-state-machine.md`); keep the existing
  `cancel-mechanism.test.ts` / soak green.
- **Verify:** `tests/delegation/` daemon-soak — (a) a daemon idled past K cycles still claims a
  freshly-enqueued task; (b) a stuck/killed daemon doesn't block a peer spawn. Then the e2e Phase 5
  lease-renewal leg becomes runnable (it is currently blocked by this).

### ISS-005 + ISS-010 (MEDIUM, same file) — StatPills counts don't reconcile / cancelled→Failed leak
- **Symptom:** a fully-done operation (coordinator chip 'done', members all terminal) shows StatPills
  `0 Done / 1 Active / 1 Failed`; rail vs StatPills vs visible surfaces never reconcile for operations
  (oath-upload, `arch=single`, is the clean control that does). A cancelled member shows under Failed,
  Cancel pill reads 0.
- **Root cause (high confidence):** `src/tracker/queue-row-count.ts`. (1) `isApprovedPrepForQueueStrip`
  drops only `archetype==='batch'` prep anchors, never `'operation'` coordinators → each operation
  double-counts (coordinator strip row + synth member-rollup row). (2) the coordinator strip row keeps
  RAW `running`/`step=approved` status (the 4 coordinators are the only runs that never reach terminal
  in row-lifecycle) → Active instead of the done rollup. (3) `rollupBatchMembersToQueueStripSynth`
  decides status with raw `m.status==='failed'`, bypassing `statusKeyForEntry` → cancelled
  (`failed`+`step=cancelled`) → Failed (ISS-010; violates the 2026-06-12 E2E-009 invariant).
- **Fix needed:** drop operation coordinators from the strip (like batch prep anchors) or count their
  rolled-up status; route coordinator/synth status through `operationSurfaceStatus`/`statusKeyForEntry`.
  The rail/surface model (`src/tracker/queue-surfaces.ts` `countTopLevelQueueSurfaceRows`) is the
  correct reference. Display-only (no lost work) but **touches the backend-authoritative counts** — fix
  carefully.
- **Verify:** unit pin on `countEntriesByQueueStatus` over a done-rollup operation fixture → 1 Done,
  0 Active/Failed; a synth rollup with a cancelled member → Cancel++ not Failed++.
