## Task summary
Harden the **onbase** workflow's OWN logic against flakiness, then live-verify end-to-end. OnBase is an OCR-backed **operation coordinator** (`archetype: "batch"` → normalizes to operation; `inputSubject: "eid"`; `code: "ob"`). The upload run merges 1+ PDFs into one combined doc (one page = one person), offers an OnBase doc-type dropdown with only **"Emergency Contact"** wired, and posts `targetWorkflow=onbase`. On approve, OCR fans out **one OnBase import per person** (`operation-member` rows). The real per-person field is `ucpathId` (5+ digits) — the OnBase **Employee Lookup keyset autofills every other keyword** the instant you type the UCPath ID + Tab; the `*Fallback` fields (names, dept, VC) are used ONLY when the keyset comes up empty. `dryRun` walks the whole form (keyset autofill + required-keyword verification) but skips the final Import click.

**Scope boundary:** OCR is a SHARED service — the OCR orchestrator (`src/workflows/ocr/orchestrator.ts`) is hardened separately in **Wave 0** (`2026-07-01-ocr-orchestrator.md`). This task covers onbase's OWN logic (its handler steps + the `src/systems/onbase/` primitives), NOT the orchestrator. Don't touch orchestrator code here — you inherit Wave-0's fixes.

## Audit findings to fix (the actionable seed)
Onbase was not deep-audited — **run the focused pass first**, then fix what you find. Starting hypotheses to confirm/refute against the live page (`handler.ts` steps + `src/systems/onbase/navigate.ts`):
- **Keyset autofill is a race.** `enterUcpathIdAndTab` returns a boolean "did the keyset autofill?" — how is that decided? If it reads keyword values immediately after Tab without waiting for the async keyset round-trip to settle, a slow page → `autofilled=false` → it wrongly falls back to OCR data (or the required-keyword check fires before the keyset lands → false "still empty" throw). Confirm there's a real settle/wait signal, not a fixed sleep or an immediate read.
- **`isImportEnabled` gating.** The `import` step throws if the button is disabled. Is "disabled" a stable terminal state or a transient one while keywords commit? A transient-disabled read would fail a valid import. Verify it waits for enabled with a timeout rather than sampling once.
- **`chooseFile` / `extractPdfPage` per-page split.** Each member splits one page out of the combined PDF and feeds the bytes to OnBase's picker. Confirm the file-picker attach is confirmed (upload completed / filename shown) before proceeding, not fire-and-forget.
- **Doc-type + File-Type + keyset selection ordering** (`selectDocumentType` / `selectFileType` / `ensureKeyset` in `prepare-import`). OnBase re-renders the keyword panel when doc type / keyset change — confirm each select waits for the dependent panel to re-render before the next select, or a later keyword read hits a stale panel.
- **Required-keyword ("red") verification** (`readRequiredKeywordValues`) — good that it fails loud, but confirm it reads AFTER the keyset settles (see the first bullet) so it can't false-negative.
- Sweep the rest of `handler.ts` / `navigate.ts` / `selectors.ts` for un-waited clicks, fixed sleeps, and swallowed `.catch(()=>...)` that hide a real failure. Anything OnBase-specific worth keeping → record with `custom-hr-lesson` into `src/systems/onbase/LESSONS.md`.
